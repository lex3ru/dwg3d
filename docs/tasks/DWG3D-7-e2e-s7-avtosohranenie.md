# DWG3D-7: e2e С7: тест не ждёт автосохранения угла камеры

## Цель

Сценарий С7 в `e2e/tests/stage7.spec.ts` нестабилен: после смены угла камеры на 40° тест ждёт,
пока на экране вырастет зона обзора, и сразу один раз читает предмет через
`GET /api/floors/{floor}/items`. На перегруженном раннере он получает `params["camera.fov"]` =
`undefined` вместо 40 (MR !5, пайплайн #1374, задания 4183 и 4192). Задача делает так, чтобы С7
ждал сохранённое значение, а не читал его один раз, — не ослабляя проверку. Подзадача DWG3D-1
«Исправления по ревью 21.10.2026»; находка заводится как R-050.

Вне рамок: другие падения того же прогона (stage0 «неверный пароль», С18 на телефоне, PDF в
отчётах) — это нехватка CPU у раннера, а не гонка в тесте.

## Решения и находки

- 2026-10-26 — Причина подтверждена по коду. Таблица «Камеры этажа» и зона обзора считаются
  из состояния редактора: `useCalcs` (`web/src/editor/calc.tsx`) шлёт предметы с `params` прямо
  в `POST /api/calc/camera/floors/{floor}`, через 120 мс после правки. Сохранение предмета идёт
  отдельно — очередью `store.sendItems` → `POST /api/floors/{floor}/items/changes`
  (`web/src/editor/Editor.tsx`). Экран может обновиться раньше, чем сервер принял правку.
  Это не «автосохранение плана» (`PUT /plan`), как сказано в задаче, а сохранение расстановки:
  задерживать в воспроизведении нужно `items/changes`.
- 2026-10-26 — Соседние сценарии просмотрены (`grep` по одиночным `page.request.get` в
  `e2e/tests`). Других гонок нет: чтения расстановки в `stage4`, `stage6`, `stage8` идут после
  `expect.poll` по последней операции очереди (очередь шлёт по порядку, значит, и прежние уже
  сохранены) или после синхронного ответа сервера — «Поставлено на учёт» (`/api/link/register`),
  «Проект применён», загрузка пакета в `stage10`. Отрицательная проверка
  `stage4.spec.ts:263` («следующий щелчок ничего не ставит», `waitForTimeout(400)`) при
  медленном сохранении может пройти ложно, но не упасть — вне рамок задачи.
- 2026-10-26 — Задержка +2 с на `items/changes` остаётся в С7 насовсем (решил Yury Mikhailov).
  Так гонка воспроизводится в каждом прогоне: вернут одиночное чтение — С7 упадёт сразу, а не
  изредка на перегруженном раннере. Цена — около 2 с к С7. Вариант «задержка только для
  разового воспроизведения» отвергнут: регрессию снова ловил бы только медленный раннер.
- 2026-10-26 — Воспроизведено локально (чистая база `app_e2e`, как в DWG3D-5). С задержкой
  прежний С7 падает за 5,6 с: `Expected: 40, Received: undefined` на одиночном чтении — то же,
  что в CI #1374. Без задержки тот же тест проходит за 2,7 с. `page.route` перехватывает только
  запросы браузера; `page.request.post(.../items/changes)` при подготовке этажа не задерживается.
- 2026-10-26 — Исправленный С7 (`expect.poll`, таймаут по умолчанию 5 с): с задержкой проходит
  за 5,7 с и трижды подряд по 4,4–4,5 с (`--repeat-each 3`), без задержки — за 3,8 с (блок
  `page.route` убирался на время прогона), весь `stage7.spec.ts` — 2 из 2.
- 2026-10-26 — R-050 — уровень «Н»: приложение не затронуто, CI ложно красный; этап «DWG3D-5»
  (найдена, когда исправляли её); ТЗ 8.7 п. 2.
- 2026-10-26 — Весь e2e локально (Windows, `app_e2e`, с worker): 37 прошли, 7 упали, 7
  пропущены. Ни одно падение не связано с задачей — diff с `main` затрагивает только
  `stage7.spec.ts` и документы:
  - PDF не строится (на Windows нет GTK/Pango, как в DWG3D-5): С2 (`export.pdf`), С11 и С16
    (`labels.pdf`), С9 («PDF для руководства»), «главная, отчёты и полная выгрузка», С18
    (`act.pdf`);
  - 8.2 расчёты: зона обзора 547 мс при норме 200 мс — замер на этой машине;
  - stage4 «Вложение»: и отдельно падает 2 раза из 3. По трассе тест висит не на вкладке
    «Расстановка», как пишет ошибка, а ещё в подготовке: `POST /api/buildings/{id}/floors`
