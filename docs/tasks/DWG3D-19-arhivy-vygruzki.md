# DWG3D-19: Архивы полной выгрузки удаляются по сроку

## Цель

Находка R-027 из ревью 21.10.2026 (подзадача DWG3D-1). Полная выгрузка (ТЗ 7.4) — архив
размером почти со все файлы системы: фото, чертежи, 3D. Архивы остаются в каталоге данных
(`data/exports`) навсегда и попадают в резервные копии, а после удаления живут там ещё до года
(ежемесячные копии). Регулярные выгрузки постепенно займут диск. Недособранный архив
отменённой выгрузки тоже остаётся.

## Критерии готовности

- [x] Архивы старше срока из «Настроек» удаляет задача по расписанию.
- [x] Недособранный архив отменённой или упавшей выгрузки удаляется.
- [x] Каталог выгрузок не попадает в резервные копии.
- [x] Ссылка на удалённый архив даёт понятное сообщение, а не ошибку.
- [x] Справка обновлена.
- [x] Сценарий находки покрыт тестом, который до исправления падал (R-033).
- [ ] CI зелёный (локально — да, конвейер MR ещё не запускался); в FINDINGS у R-027 статус
      «исправлена» со ссылкой на MR — да.

## Решения и находки

<!-- ГГГГ-ММ-ДД — что решили и почему; что пробовали и отвергли. Архитектурное → ADR. -->

- 2026-10-30 — срок хранения по умолчанию 30 дней (решение Yury Mikhailov): за месяц архив
  успевают скачать и унести на отдельное хранение (7.4); в задаче срок не был указан.
- 2026-10-30 — архив пишется сразу в `exports/<job_id>.zip`; что он недособран, видно по
  статусу задачи (`failed`/`cancelled`), поэтому временное имя `.part` не нужно. `on_fail`
  не получает id задачи, но к его вызову статус уже стоит — уборка по статусу находит архив
  сама.
- 2026-10-30 — обработчик убивает процесс задачи до `_fail` (`tasks.py`, ~426 → 450), так что
  `on_fail` удаляет уже закрытый файл; на Windows открытый файл не удалится — `OSError`
  пропускаем, уберёт следующая уборка по расписанию.
- 2026-10-30 — `restore.sh` очищает `/data` целиком: после восстановления копии старых архивов
  не будет, а задачи останутся «готово». Поэтому уборка помечает и выгрузки с пропавшим
  архивом, а интерфейс проверяет архив перед скачиванием.
- 2026-10-30 — у FastAPI маршрут `GET` на `HEAD` не отвечает (405). `api_route(methods=
  ["GET", "HEAD"])` даёт в схеме API повторяющийся operation ID (предупреждение в
  `test_security.py`), поэтому два декоратора — `@router.get` и `@router.head`.
  `FileResponse` в Starlette 1.8 на `HEAD` шлёт только заголовки.
- 2026-10-30 — скачать можно только архив выгрузки со статусом «готово»: раньше
  `export_file` проверял лишь, есть ли файл, и отдал бы недособранный архив идущей выгрузки.
- 2026-10-30 — у HEAD нет тела, поэтому интерфейс на 404 делает ещё GET: на удалённый архив
  ответ — короткий JSON с причиной. Другие ответы (нет связи, 5xx) — ошибка рядом со ссылкой,
  ссылка остаётся.
- 2026-10-30 — проверено на стенде разработки (server, worker, ui с этой ветки): HEAD →
  загрузка; удалённый файл → сообщение «Архива больше нет…» вместо ссылки; отмена выгрузки
  всех зданий на шаге 4 из 1212 — архива нет, ошибок в журнале обработчика нет; выгрузка с
  `finished_at` на 31 день назад — обработчик по расписанию удалил её за ~14 с, пометил
  «истёк срок хранения», запись журнала «Удалено архивов полной выгрузки: 1»; заодно пометил
  выгрузку с пропавшим файлом. `rsync --exclude=/exports/` проверен в контейнере
  `planuchet-backup-1`.
- 2026-10-30 — `transfers/` (загруженные пакеты переноса) тоже лежит в `/data`, но там своя
  уборка через сутки (`transfer/package.py`, `receive`); в рамки задачи не входит.

## Handoff

<!-- Перезаписывается в конце каждой сессии навыком handoff. -->

**Состояние:** готово к ревью (MR !19). Архивы полной выгрузки хранятся срок `export_days`
из «Настроек» (30 дней) и не входят в резервную копию. Уборка `reports.purge_exports` раз в
час удаляет архивы старше срока, архивы упавших и отменённых выгрузок и архивы без задачи.
`on_fail` выгрузки удаляет недособранный архив сразу. Если архива нет, в итоге задачи
пишутся `deleted` и `deleted_at`. Адрес скачивания отвечает на `HEAD`; карточка «Полная
выгрузка» вместо ссылки на удалённый архив пишет, почему его нет. Решение — ADR-0024
(статус «предложено»; перед merge поставить «принято»).

**Следующий шаг:** ревью MR. Перед merge — ADR-0024 в статус «принято» (файл и индекс
`docs/decisions/README.md`).

**Открытые вопросы:** нет.

**Ловушки:**
- `on_fail` не получает id задачи: уборка находит архив по статусу задачи, который к этому
  моменту уже стоит.
- На Windows открытый файл не удаляется (`OSError` пропускается) — уберёт следующая уборка.
- `api_route(methods=["GET", "HEAD"])` даёт повторяющийся operation ID в схеме API, поэтому
  маршрут объявлен двумя декораторами.
- Стенд разработки: инструмент превью не находит `sh` из `.claude/launch.json` (нет в PATH),
  на время проверки пришлось указать `C:/Program Files/Git/usr/bin/sh.exe` и запускать vite
  через `node node_modules/vite/bin/vite.js`; в репозиторий это не попало. Vite слушает
  `[::1]:5190`.

**Как проверить:**

```bash
cd server && uv run pytest tests/test_reports.py tests/test_deploy.py tests/test_tasks.py -k "r027 or scheduled"
cd web && npx vitest run src/reports/ArchiveLink.test.tsx
```

На стенде: собрать выгрузку здания в «Отчётах»; в базе сдвинуть `core.job.finished_at` на
31 день назад и `core.schedule_run.last_run_at` у `reports.purge_exports` на 2 часа назад —
обработчик за ~15 с удалит архив, карточка покажет «Архив удалён … истёк срок хранения».

**За рамками задачи:** `transfers/` (загруженные пакеты переноса) тоже лежит в `/data` и
попадает в копию, но там своя уборка через сутки.
