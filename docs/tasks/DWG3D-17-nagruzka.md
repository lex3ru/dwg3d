# DWG3D-17: Быстродействие при 20 одновременных пользователях

## Цель

Находка R-036 из ревью 21.10.2026 (подзадача DWG3D-1). На объёмах 8.1 при 20 одновременных
пользователях реестр отвечает 2,6 / 4,5 с (медиана / худший), дерево мест — 2,8 / 3,4 с при
норме 1 с (ТЗ 8.2); одним пользователем — 0,35 и 0,49 с. Под большей нагрузкой (50 и 200
одновременных ведомостей стоимости) — обрывы соединений, ответы 500 «QueuePool limit … timed
out» и гибель процессов приложения. ТЗ 8.1: до 20 одновременно работающих — «без замедления
против 8.2».

## Критерии готовности

- [ ] На стенде объёмов 8.1 (приложение — 4 ядра, 8 ГБ) нормы 8.2 выполняются при 20
      одновременных пользователях: реестр, дерево мест, поиск, карточка, план этажа.
- [ ] Пиковая нагрузка не даёт 500 и не роняет процессы: 50 и 200 одновременных запросов
      реестра и ведомости стоимости (как в ревью) — без 500 и обрывов, процессы живы.
- [ ] Сценарий находки покрыт тестом, который до исправления падал (R-033).
- [ ] В FINDINGS у R-036 — статус со ссылкой на MR.
- [ ] Справка и `docs/` (ACCEPTANCE — замеры 8.2, INSTALL — процессы и соединения)
      обновлены; выбор между вариантами — ADR.
- [ ] CI зелёный.

## План

- [ ] 1. Стенд и тест, который падает: база `volume` (`python -m app sample volume`),
      приложение — образ `deploy/Dockerfile` с ограничением 4 ядра / 8 ГБ, 4 процесса, как в
      ревью. В `e2e/tests/volume.spec.ts` — сценарий «20 одновременных»: реестр, дерево мест,
      поиск, карточка, предметы этажа — каждый не дольше нормы 8.2; и «пик»: 50 и 200
      одновременных реестров и ведомостей — без 500 и обрывов. Снять цифры «до».
- [ ] 2. Реестр (`inventory/units.py: registry`): сортировка и страница — в SQL
      (`ORDER BY … LIMIT/OFFSET`), число и сумма цен — агрегатом. Порядок по наименованию и
      месту — через `catalog.api` / `building.api`, без чужих таблиц (test_architecture).
      Pytest: порядок, страницы и итоги — как у прежней реализации, в том числе для
      «просмотра» (R-015: нет сортировки по цене и номеру).
- [ ] 3. Остаточная стоимость в итогах реестра — в SQL, а не по 50 000 строк в Python:
      `rules.residual` — на `Decimal` с округлением «половина вверх», то же выражение — в SQL
      (столбцы своей таблицы `unit`). Pytest: SQL и Python совпадают точно на сетке случаев
      (переоценка, конец срока, без срока, списанные, будущие даты, границы округления).
      ADR: в редких пограничных случаях ведомости сдвигаются на копейку.
- [ ] 4. Дерево мест (`GET /api/inventory/places`): вместо запроса на каждый этаж и склад —
      несколько запросов на всё (`building.api`: этажи и живые помещения зданий одним
      запросом; ячейки складов — одним). Замер; если при 20 одновременных не укладывается в
      1 с — загрузка помещений по этажам по требованию (API + `PlacePicker`, ADR).
- [ ] 5. Пик: потоков обработки запросов в процессе не больше соединений пула — лишние
      запросы ждут очереди, а не 500 по таймауту пула; проверка живости процессов uvicorn
      (`timeout_worker_healthcheck`, 5 с) не убивает процесс, занятый долгим счётом.
- [ ] 6. Ведомость стоимости — фоновой задачей (ТЗ 8.2: «идёт в фоне»): `tasks.task` с
      `timeout`, запуск возвращает задачу, итог (таблица и Excel) — по задаче; одинаковый
      запрос, пока прежний считается, не ставит вторую задачу. Экран «Стоимость» — ход и
      отмена, как у полной выгрузки (`useJob`, `watchJob`, `CancelJob`). Тесты: pytest на
      задачу и права, e2e сценария С19 (`stage*.spec.ts`). ADR (меняется API), справка.
- [ ] 7. Соединения: пул × процессы + обработчик + слушатели укладываются в
      `max_connections` PostgreSQL с запасом; настройки в `deploy/compose.yml`, `core/db.py`;
      описание — `docs/INSTALL.md`.
- [ ] 8. Замер «после» на стенде (тесты шага 1 зелёные); цифры — в `docs/ACCEPTANCE.md`
      (8.2 на стенде объёмов), статус R-036 в `docs/review/FINDINGS.md`; справка
      (`content.ts` → `npm run admin-guide`).
- [ ] 9. Проверки как в CI (ruff, pytest, web, e2e затронутых этапов и `volume`).

## Решения и находки

<!-- ГГГГ-ММ-ДД — что решили и почему; что пробовали и отвергли. Архитектурное → ADR. -->

- 2026-10-29 — причины по коду (строки по `bde552e`):
  - реестр (`units.py:550`) на каждый запрос читает 11 полей всех видимых единиц (50 000),
    сортирует в Python и считает остаточную стоимость каждой (`rules.residual`) — это счёт
    под GIL: 20 запросов на 4 процесса идут по ~5 подряд, отсюда 2,6 с;
  - дерево мест (`routes.py:43`) — запрос на каждое здание, этаж (`live_rooms`) и склад
    (`warehouse_view` — ячейки): на стенде ≈ 450 запросов и 1,2 МБ JSON на каждый вызов;
  - пул `pool_size=10` (+10 сверх) на процесс (`core/db.py:34`), а потоков обработки у
    Starlette — 40 на процесс: при 50+ одновременных лишние ждут соединение 30 с и
    получают 500; 4 × 20 + обработчик + слушатели ≈ 90 из 100 соединений PostgreSQL;
  - «Child process … died»: супервизор uvicorn 0.54 считает процесс мёртвым, если тот не
    ответил на проверку живости (5 с) — процесс, занятый долгим счётом под GIL, не успевает.
- 2026-10-29 — выбрано с пользователем: остаточная стоимость — `Decimal` в Python и то же
  выражение в SQL, сверка точная (а не SQL рядом с прежним `float`-расчётом — копеечные
  расхождения реестра с ведомостью; и не кэш итогов — устаревшие итоги); ведомость
  стоимости — в фоновую задачу, как требует 8.2 (а не ограничение одновременных расчётов в
  процессе — API не менялся бы, но счёт по-прежнему занимал бы процессы приложения); пик
  для критерия — 50 и 200 одновременных, как в ревью.
