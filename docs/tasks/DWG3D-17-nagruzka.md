# DWG3D-17: Быстродействие при 20 одновременных пользователях

## Цель

Находка R-036 из ревью 21.10.2026 (подзадача DWG3D-1). На объёмах 8.1 при 20 одновременных
пользователях реестр отвечает 2,6 / 4,5 с (медиана / худший), дерево мест — 2,8 / 3,4 с при
норме 1 с (ТЗ 8.2); одним пользователем — 0,35 и 0,49 с. Под большей нагрузкой (50 и 200
одновременных ведомостей стоимости) — обрывы соединений, ответы 500 «QueuePool limit … timed
out» и гибель процессов приложения. ТЗ 8.1: до 20 одновременно работающих — «без замедления
против 8.2».

## Критерии готовности

- [ ] На стенде объёмов 8.1 (приложение — 4 ядра, 8 ГБ) нормы 8.2 выполняются при 20
      одновременных пользователях: реестр, дерево мест, поиск, карточка, план этажа.
- [ ] Пиковая нагрузка не даёт 500 и не роняет процессы: 50 и 200 одновременных запросов
      реестра и ведомости стоимости (как в ревью) — без 500 и обрывов, процессы живы.
- [ ] Сценарий находки покрыт тестом, который до исправления падал (R-033).
- [ ] В FINDINGS у R-036 — статус со ссылкой на MR.
- [ ] Справка и `docs/` (ACCEPTANCE — замеры 8.2, INSTALL — процессы и соединения)
      обновлены; выбор между вариантами — ADR.
- [ ] CI зелёный.

## Решения и находки

<!-- ГГГГ-ММ-ДД — что решили и почему; что пробовали и отвергли. Архитектурное → ADR. -->

- 2026-10-29 — причины по коду (строки по `bde552e`):
  - реестр (`units.py:550`) на каждый запрос читает 11 полей всех видимых единиц (50 000),
    сортирует в Python и считает остаточную стоимость каждой (`rules.residual`) — это счёт
    под GIL: 20 запросов на 4 процесса идут по ~5 подряд, отсюда 2,6 с;
  - дерево мест (`routes.py:43`) — запрос на каждое здание, этаж (`live_rooms`) и склад
    (`warehouse_view` — ячейки): на стенде ≈ 450 запросов и 1,2 МБ JSON на каждый вызов;
  - пул `pool_size=10` (+10 сверх) на процесс (`core/db.py:34`), а потоков обработки у
    Starlette — 40 на процесс: при 50+ одновременных лишние ждут соединение 30 с и
    получают 500; 4 × 20 + обработчик + слушатели ≈ 90 из 100 соединений PostgreSQL;
  - «Child process … died»: супервизор uvicorn 0.54 считает процесс мёртвым, если тот не
    ответил на проверку живости (5 с) — процесс, занятый долгим счётом под GIL, не успевает.
- 2026-10-29 — выбрано с пользователем: остаточная стоимость — `Decimal` в Python и то же
  выражение в SQL, сверка точная (а не SQL рядом с прежним `float`-расчётом — копеечные
  расхождения реестра с ведомостью; и не кэш итогов — устаревшие итоги); ведомость
  стоимости — в фоновую задачу, как требует 8.2 (а не ограничение одновременных расчётов в
  процессе — API не менялся бы, но счёт по-прежнему занимал бы процессы приложения); пик
  для критерия — 50 и 200 одновременных, как в ревью.
- 2026-10-29 — стенд замеров: образ `planuchet-perf:dev` из ветки (код = `main`), контейнер
  `--cpus 4 --memory 8g`, 4 процесса, база `volume` в `planuchet-devdb` (без ограничений,
  `max_connections` 100), запросы — e2e по API одной сессией администратора. Не в Windows
  напрямую: там процесс один (ADR-0007). Цифры «до» (`bde552e`) — хуже, чем в ревью, на этой
  машине (Docker Desktop):

  | 20 одновременных | медиана / худший | норма |
  |---|---:|---:|
  | реестр, по номеру | 6,0 / 6,7 с | 1 с |
  | реестр, по наименованию | 5,5 / 7,2 с | 1 с |
  | реестр, по месту | 9,3 / 10,0 с | 1 с |
  | дерево мест | 6,7 / 6,7 с | 1 с |
  | поиск по инв. номеру | 0,17 / 0,18 с | 1 с |
  | карточка единицы | 0,20 / 0,21 с | 1 с |
  | предметы этажа 2 000 | 0,40 / 0,50 с | 2 с |

  | Пик | коды | медиана / худший |
  |---|---|---:|
  | реестр × 50 | 200 × 50 | 7,3 / 13,1 с |
  | реестр × 200 | 200 × 173, **500 × 27** | 20,4 / 36,6 с |
  | ведомость × 50 | 200 × 44, **500 × 6** | 42,1 / 54,9 с |
  | ведомость × 200 | 200 × 77, **500 × 123** | 63,2 / 199,7 с |

  Все 500 — «QueuePool limit … timed out» (317 в журнале приложения). Гибели процессов
  («Child process … died») в этом прогоне не было — в ревью была; по коду причина та же
  (проверка живости 5 с), шаг 5 её всё равно закрывает. После пика приложение отвечает сразу.
- 2026-10-29 — шаг 2, реестр: число и сумма цен — `count`/`sum` по отбору; страница —
  `ORDER BY … OFFSET … LIMIT`. Строки сравниваются `COLLATE "C"` — по кодам символов, как
  прежде в Python. В `postgres:16-alpine` (musl) и языковое сравнение побайтовое, поэтому
  тест разницы не видит, но на другой сборке PostgreSQL порядок без `"C"` поменялся бы.
  Наименование и место — подписи из других модулей: их упорядочивает Python (как прежде), а
  база получает ранг ключа двумя массивами через `unnest` и соединяет с единицами; так нет
  чужих таблиц в SQL учёта и нет параметра на каждый из 8 000 ключей мест. Порядок «прежний»
  проверяет `test_registry.py`: эталон — прежний алгоритм над всеми строками, все сортировки
  в обе стороны, страница, итоги, администратор и «просмотр»; порча направления у ключа
  равных строк тест роняет. Подписи мест: `building.rooms_with_floor` читал помещения
  целиком (контуры) пачками по 5 000 параметров — теперь только поля подписи одним массивом
  (0,43 → 0,17 с на 8 000 помещений). Одиночный запрос администратора: по номеру 0,23 с,
  по месту 0,51 с — из них 0,24 с сумма остаточной стоимости в Python (шаг 3).
  20 одновременных, худший: по номеру 6,7 → 2,3 с, по наименованию 7,2 → 2,3 с, по месту
  10,0 → 3,6 с. Если после шага 3 «по месту» не уложится в 1 с — подписи мест дороги
  (0,17 с на запрос): решать отдельно.
- 2026-10-29 — шаг 3 (ADR-0017): `residual` — в `Decimal`, копейки `ROUND_HALF_UP`;
  `residual_sql` рядом в `rules.py` — те же ветви выражением SQLAlchemy; `units.value_sql` —
  как `value_now` (списанная — 0). Итоги реестра — число, сумма цен и остаточной стоимости
  одним агрегатом; стоимость на главной (`inventory.cost_now`) — тоже, она так же перебирала
  единицы здания в Python. `test_residual.py`: прежний `residual` на 1 ₽ / 8 мес. / 7 прошло
  давал 0,12 (к чётному) — тест требует 0,13; 9 600 случаев сетки — база и Python копейка в
  копейку. Приведение делимого к `numeric(32, 12)` — страховка: PostgreSQL и сам даёт частному
  не меньше 8 знаков на ценах `numeric(14, 2)`, тест без приведения тоже проходит.
  Одиночный запрос: по номеру 0,23 → 0,05 с, по наименованию 0,26 → 0,06 с, по месту
  0,51 → 0,23 с (подписи мест — 0,15 с). 20 одновременных, худший: по номеру и по
  наименованию — 0,31 с (норма 1 с), по месту — 2,2 с, дерево мест — 6,6 с.
- 2026-10-29 — шаг 3а (ADR-0018, выбрано с пользователем против кэша подписей в процессе):
  подпись места для сортировки считает база — `building.room_titles()` отдаёт подзапрос
  подписей помещений, учёт (`places.title_sql`) присоединяет его вместе со складами и
  ячейками; видимость для «просмотра» — как у `Places.get`. Соединение — по строке ключа
  («r:» || id), без приведения ключа места к uuid. Сначала страница читала полные строки
  единиц: база сортировала их для соединений и выливала на диск (6,6 МБ, 80 мс) — теперь
  порядок по узким строкам (ключ и поля сортировки), целиком читается только страница
  (60 мс в базе). Одиночный запрос по месту 0,23 → 0,11 с. 20 одновременных, худший: по
  номеру 0,35 с, по наименованию 0,26 с, по месту 2,2 → 0,41 с — все сортировки в норме.
  Тесты: подпись помещения в базе = `room_title` на краевых номерах и названиях; подпись
  места каждой единицы в базе = в карточке у администратора и «просмотра» («место
  недоступно» для склада без здания); порча подписи ячейки тест роняет.
- 2026-10-29 — шаг 4, дерево мест. Прежде: запрос на каждое здание (`list_buildings` ещё и
  со счётчиками), этаж (`live_rooms`) и склад (ячейки), а `building.floors()` читал этажи
  целиком — с JSON плана каждого из 429 этажей. Теперь `building.rooms_by_floor` — три
  запроса только нужных полей; помещения (10 000) — столбцами таблицы без ORM-слоя, словари
  не собираются второй раз (маршрут дополняет их ключом места на месте); ячейки всех
  складов — одним запросом (`places.warehouse_views`). Тест: дерево равно собранному прежним
  кодом (администратор и «просмотр», архивная ячейка, склад в помещении), а число запросов
  не меняется, когда добавляются 4 этажа и 4 склада (прежний код: 14 → 22). Одиночный
  запрос на стенде — 0,49 → 0,10 с (1,45 МБ). В самой базе помещения — 4,6 мс; остальное —
  Python: получение 10 000 строк ~30 мс, словари, JSON. 20 одновременных, худший: 6,7 →
  0,66–1,09 с по прогонам (медиана 0,5–0,75 с) — на границе нормы. Первый прогон сразу
  после запуска контейнера заметно медленнее (1,34 с): процессы холодные. Ключи текстом
  вместо uuid и Core вместо ORM на этом объёме разницы в замерах не дают (шум сети до базы).
  Кроме сервера, браузер на каждом экране с выбором места получает и разбирает 1,45 МБ, а
  `PlacePicker` — это `<select>` на все 10 000 помещений.
- 2026-10-29 — шаг 4, продолжение (ADR-0019; выбрано с пользователем против помещений по
  требованию — меняет API и шесть экранов, отдельной задачей — и против кэша в процессе —
  администратор не увидел бы только что заведённое): JSON зданий с этажами и помещениями
  собирает база (`json_agg` с `ORDER BY` внутри, `json_build_object`) из подзапросов
  `building.tree_sql` и отдаёт текстом — иначе psycopg разберёт JSON в объекты Python.
  Склады — их единицы — по-прежнему `warehouse_views`; маршрут склеивает части в `Response`.
  Python-версия `rooms_by_floor` убрана. Одиночный запрос 0,10 → 0,06 с; ответ 1,57 МБ
  (PostgreSQL ставит пробелы вокруг «:»; Caddy в установке сжимает). 20 одновременных,
  худший: 0,34–0,42 с в пяти прогонах, и в первом на холодных процессах. Тест «20
  одновременных» проходит целиком: реестр 0,26–0,45 с, дерево 0,40 с, поиск 0,15 с,
  карточка 0,15 с, предметы этажа 0,38 с.
- 2026-10-29 — шаг 5 (ADR-0020). Маршруты — в пуле потоков Starlette (40 на процесс), а
  соединений было 10 + 10: лишние потоки ждали 30 с и получали 500. Ограничить сам пул
  потоков нельзя: вход (зависимость) занимает поток и ждёт соединение, а запросы с
  соединением ждут поток для маршрута — взаимоблокировка. Сделано: очередь ASGI
  (`core/admission.py`) на `APP_DB_POOL` = 15 запросов в процессе, место освобождается с
  началом ответа (сессия уже закрыта, `scope="function"`), сокеты — мимо очереди; пул — 15
  и 2 сверх (`OUTSIDE_QUEUE`) сокетам. Запрос держит одно соединение — вход
  (`access.resolve_actor`) и маршрут в одной сессии; слушатель изменений — своё соединение
  вне пула. Проверка живости uvicorn: отвечает поток процесса, которому нужен GIL, — 5 → 60 с.
  Пик на стенде (до → после): реестр × 200 — 27 × 500 → все 200, худший 36,6 → 2,2 с;
  ведомость × 50 — 6 × 500 → все 200 (худший 109 с); ведомость × 200 — 123 × 500 → 190 ×
  200 и 10 обрывов клиентом теста по его таймауту 300 с; HTTP 500 — ни одного, перезапусков
  процессов нет. Две ошибки «QueuePool limit» в журнале — от сокетов изменений страницы

- 2026-10-29 — шаг 6 (ADR-0021, выбрано с пользователем против ограничения одновременных
