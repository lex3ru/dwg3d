# DWG3D-5: Инвентаризация: зависший запрос не держит очередь отметок

## Цель

На телефоне запрос с отметкой может повиснуть: соединение полуоткрыто или Wi-Fi слабый. Тогда
очередь отметок стоит без всякого сообщения, пока браузер сам не оборвёт запрос, а «Провести»
всё это время недоступно. Повторять отправку просто по тайм-ауту опасно: старый запрос может
дойти до сервера позже нового, перезаписать пересчёт старым числом или снова отметить вещь, с
которой отметку уже сняли. Задача закрывает находку ревью 21.10.2026 (родительская задача
DWG3D-1, `docs/review/FINDINGS.md`): R-049 (Н) — у отправки из очереди нет тайм-аута.

Решение согласовано в Plane: устройство нумерует свои отметки (UUID устройства в браузере и
номер по порядку), сервер хранит последний принятый номер пары «ведомость + устройство» и
пропускает запрос с номером не больше него; отправка обрывается через 15 с → «Нет связи» →
отметка отправляется заново. Меняются схема данных и API — ADR-0006.

## Решения и находки

<!-- ГГГГ-ММ-ДД — что решили и почему; что пробовали и отвергли. Архитектурное → ADR. -->

- 2026-10-26 — предложение для ADR-0006 подтвердил Yury Mikhailov; записано в ADR-0006
  (принят при merge MR !5):
  - устройство и номер — в заголовках `X-Count-Device` и `X-Count-Seq` у всех четырёх
    запросов: у «снять отметку» (`DELETE …/marks/{unit_id}`) нет тела;
  - без заголовков сервер принимает запрос, как раньше (API и тесты без устройства). Отметкам,
    которые остались в очереди от прежней версии, клиент даёт номера при чтении очереди;
  - пропущенный запрос — это успех (2xx), а не ошибка, иначе очередь выбросит отметку с
    сообщением. Скан отвечает `result: "skipped"`: без звука и без «найдена», ведомость
    просто обновляется;
  - номер даётся при постановке в очередь, а не при отправке: повтор после тайм-аута, 5xx или
    входа идёт с тем же номером. Счётчик один на устройство, он растёт и внутри каждой
    ведомости;
  - UUID — через `crypto.getRandomValues`: `crypto.randomUUID` есть только на HTTPS и
    localhost, а телефон в разработке ходит по `http://` на адрес компьютера в сети.
- 2026-10-26 — находка вне задачи: две вкладки одной ведомости досылают одну очередь
  (`busy` — на вкладку). Обе шлют первую отметку, и обе снимают первую из очереди, так что
  вторая может уйти не отправленной. С номерами повтор безвреден, а снимать отметку из
  очереди можно по номеру, а не по позиции, — это мелочь в шаге 5. Тест подтвердил потерю:
  вторая вкладка не дослала b (нет связи), первая, дослав a, сняла b по позиции.
- 2026-10-26 — проверка номера стоит сразу после `_draft`, до проверок места и единицы:
  опоздавший повтор, который сейчас был бы отклонён (единицу успели списать), должен
  получить «пропущено», а не ошибку с сообщением. Скан проверяет номер сам и зовёт `mark`
  без номера, чтобы не проверять дважды.
- 2026-10-26 — e2e локально: пароль администратора базы разработки `app` не совпадает с
  `E2E_PASSWORD` по умолчанию. Менять его не стали: e2e шли на отдельной чистой базе
  `app_e2e` (сервер на :8010, `create-admin --password` + `E2E_TEMP_PASSWORD`); после прогона
  база удалена. `preview_start` на этой машине не находит `sh` из `.claude/launch.json` —
  серверы запускались теми же командами через Bash.

## Итог

**Что сделано.**

- R-049: запрос отметки обхода без ответа 15 с обрывается (`AbortController`). На ведомости
  «Нет связи», отметка досылается заново. «Провести» больше не ждёт зависший запрос минутами.
- Повтор безвреден (ADR-0006). Отметка получает номер при постановке в очередь и шлёт его с
  UUID устройства (`X-Count-Device`, `X-Count-Seq`). Сервер помнит последний принятый номер
  пары «ведомость + устройство» (`inventory.count_device`, миграция 0014) и пропускает запрос
  с номером не больше него. Проверка атомарная, в транзакции отметки. Скан и отметка отвечают
  «skipped», снятие и пересчёт — 204. Без заголовков сервер принимает запрос как раньше,
  неверные заголовки — 400.
- Попутно: из очереди отметка снимается по номеру, а не первая по счёту. Две вкладки одной
  ведомости больше не теряют недосланную отметку. Отметки из прежней версии получают номера
  при чтении очереди.

**Как проверить.**

- `cd server && uv run pytest tests/test_counts.py tests/test_migrations.py`
- `cd web && npm test` — `queue.test.ts`, `CountPage.test.tsx`
- e2e `stage9.spec.ts`: «6.7 п. 1, R-049» и «6.7 п. 1, R-030» (@телефон)
- Вживую: ведомость с остатком → в DevTools сделать `PUT …/stock` зависшим (или подменить
  `fetch`) → ввести пересчёт → через 15 с «Нет связи» → через несколько секунд дослано, на
  сервере введённое число.

**За рамками задачи.**

- Опоздавший скан, который сервер пропустил, не даёт ни звука, ни результата на экране. Что
  вещь найдена, видно в списке места. Так решено в ADR-0006.
- Клиент без заголовков устройства (API, тесты) защиты от опоздавших запросов не получает.
  Новый клиент обхода обязан слать те же заголовки.
- Локально на Windows: `test_events.py::test_admin_receives_changes` падает и на `main`, PDF в
  e2e не строится (нет GTK). Пароль администратора базы разработки не совпадает с
  `E2E_PASSWORD`, поэтому e2e шли на отдельной чистой базе. `preview_start` не находит `sh`
  из `.claude/launch.json`. CI на Linux этого не показывает.
