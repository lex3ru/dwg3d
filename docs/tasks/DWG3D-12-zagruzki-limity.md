# DWG3D-12: Загрузки и фоновые задачи: лимиты, тяжёлые и испорченные файлы

## Цель

Сейчас без входа можно заставить сервер записать на диск файл любого размера. Лимиты из ТЗ 7.3
п. 4 соблюдаются не для всех видов файлов. Испорченный или тяжёлый файл даёт 500 или надолго
останавливает очередь фоновых задач, отменить задачу нельзя. Подзадача DWG3D-1 (ревью
21.10.2026); находки R-014 (З), R-040, R-025, R-026, R-017 (Н), R-013 (С) — в
`docs/review/FINDINGS.md`.

## Критерии готовности

- [x] Большая загрузка без входа отклоняется, не попав на диск (R-014): `test_uploads.py`.
- [x] Лимиты для всех шести видов файлов — по ТЗ 7.3 п. 4 и меняются в настройках (R-040):
      «Настройки» → «Загрузка файлов», `test_uploads.py`.
- [x] Тяжёлый чертёж не останавливает очередь, а задачу можно отменить (R-026): полосы,
      «Отменить», предел памяти (R-056); `test_worker.py`, `test_drawings.py`, браузер.
- [x] Испорченный GLB — понятная ошибка, не 500; «размножающееся» дерево узлов отказывается сразу (R-025).
- [x] `dwg2dxf` — без секретов в окружении и с лимитом памяти и процессора (R-017).
- [x] Перезапуск обработчика возвращает в очередь только задачи «молчащих» обработчиков;
      подписки модулей не удваиваются (R-013).
- [x] Сценарий каждой находки покрыт тестом, который до исправления падал (R-033); у R-056
      тест написан вместе с исправлением — без предела он падает (проверено в Linux).
- [x] CI зелёный: пайплайн #1459 на `130fd40` (последний коммит с кодом) — `server`, `web`, e2e
      и `agent-files`; после него — только документы. В FINDINGS у находок статус со ссылкой на
      MR; справка и `docs/` обновлены.

Вне рамок: отдельный контейнер для `dwg2dxf` без сети (R-017, «при желании»), прочие пункты
R-018 (укрепление) — другие подзадачи DWG3D-1.

- 2026-10-28 — согласовано с Yury Mikhailov: (1) R-026 — задача в дочернем процессе,
  остановка процесса по таймауту и отмене, две полосы (не проверки флага в коде задачи: долгий
  вызов внутри shapely или LibreDWG так не прервать); (2) пакет переноса — своя настройка,
  2 ГБ по умолчанию; (3) лимит числа примитивов не вводим (причина ниже).
- 2026-10-28 — решения записаны: ADR-0011 (задача в дочернем процессе, полосы, отмена,
  пульс; Linux — `fork`, Windows — `spawn`) и ADR-0012 (приём загрузки — зависимостью после
  входа, семь настроек лимитов, Caddy — вторая линия). Проба для ADR-0012 (FastAPI 0.143,
  Starlette 1.8): маршрут с `UploadFile` вытягивает из запроса без входа все 50 МБ, маршрут с
  зависимостью после `Admin` — 0 байт. Прослойку (middleware) отвергли: ядро не знает о
  сеансах, лимит вида пришлось бы определять по пути.
- 2026-10-28 — FastAPI разбирает multipart (`UploadFile`) до зависимостей входа и прав: тело
  целиком ложится во временный файл, только потом 401. Поэтому файл принимает зависимость,
  объявленная после зависимости входа (ADR-0012), а не параметр `UploadFile`.
- 2026-10-28 — пакет переноса здания (`/api/transfer/check`) везёт все файлы здания — фото,
  чертежи, документы — и бывает больше любого лимита 7.3. Один `request_body max_size 110MB` в
  Caddy (предложение R-014) сломал бы перенос: у пакета свой лимит.
- 2026-10-28 — вероятная новая находка: `convert_drawing` падает (например, R-023 `needs_place`)
  → транзакция задачи откатывается целиком, и `drawing.status` остаётся `converting`, записанным
  ещё при постановке в очередь. Чертёж навсегда «переводится», повторный перевод отказывает
  («ещё обрабатывается»). Тест R-023 этого не проверяет. Отмена и таймаут дадут то же — нужен
  обработчик неудачи задачи.
- 2026-10-28 — лимит числа примитивов чертежа (предложение R-026) не вводим: 50 000 случайных
  пересекающихся линий — патология, а у реального плана этажа примитивов бывает столько же и
  больше; чертежей заказчика для калибровки нет. Тяжёлый чертёж останавливает таймаут или
  отмена, очередь не ждёт его благодаря полосам.
- 2026-10-28 — тесты шага 2 до исправления (Windows, база `planuchet-devdb`):
  - R-014: все 8 маршрутов загрузки без входа забирают 20 МБ из 20, затем 401;
  - R-040: настроек `drawing_max_mb`, `underlay_max_mb`, `excel_max_mb`, `model3d_max_mb`,
    `transfer_max_mb` нет; фото для обхода (`/api/files?accept=…heic`) ограничено только 300 МБ;
  - R-025: кривой JSON, узел/сетка/координаты вне списка, цикл — 500; цепочка в 3000 узлов —
    `RecursionError`, 500; общий потомок (2^12 путей) принимается;
  - «переводится» подтверждено: после неудачного перевода `('converting', None)` — новая
    находка, в FINDINGS — на шаге 9;
  - R-026: обработчик `python -m app worker` держит `system.purge_journal` в очереди, пока
    переводится чертёж из 12 000 случайных линий (разбор — 3,6 с, перевод — дольше минуты);
  - R-017: в окружении `dwg2dxf` — все `APP_*`; тест `setrlimit` — только Linux (CI);
  - R-013: второй `create_app()` удваивает подписчиков не только в `building`, но и в
    `core.search._providers`, `files._guest_checks`, `system._checks` и других;
  - `test_worker.py` до исправления не собирается (`task()` без `lane`), и pytest
    останавливается на сборке. Поэтому CI на коммите тестов красный целиком.
- 2026-10-28 — шаги 3–4 сделаны вместе: «проверка до приёма» из R-040 и есть зависимость
  ADR-0012. Что выяснилось по ходу:
  - `files` и `system` на одном уровне, поэтому `/api/files` не может прочитать настройку.
    Лимит по назначению регистрируют модули выше (`files.on_upload_limit`): подложку — модуль
    здания, снимок при обходе — модуль учёта. Назначение — по `accept`: с PDF — подложка,
    без PDF — фото (так вызывают редактор и обход).
  - зависимость с `yield` по умолчанию живёт весь запрос и не может опираться на сессию
    базы со `scope="function"` (`DependencyScopeError`). `uploads.receive` сам возвращает
    `Depends(..., scope="function")`, и файл закрывается, когда маршрут отработал.
  - TestClient при первом `receive()` читает тело запроса целиком (`request.read()`), и
    обрыв приёма на лимите им не измерить. Тест R-040 подаёт тело прямо в ASGI-приложение
    по мегабайту (`stream_post`). Тест R-014 честен и с TestClient: без входа `receive()`
    не вызывается вовсе.
  - маршрут чертежа был `CurrentActor` с проверкой администратора внутри — теперь `Admin`,
    чтобы «просмотр» тоже получал отказ до приёма тела.
  - `uploads.MAX_FILE` (300 МБ) — общий предел в ядре: его видят и `files`, и `system`.
    Предел Caddy 301 МиБ (300 + 1 на форму): в SI-единицах `310MB` меньше 301 МиБ и
    отрезал бы законный файл в 300 МБ.
- 2026-10-28 — R-025: обход узлов GLB — без рекурсии, с множеством пройденных. Узел,
  встреченный дважды, — «GLB повреждён»: по glTF 2.0 у узла один родитель, так что это цикл
  или общий потомок. Глубина — не больше 256. Индексы узлов, сеток, координат и сцены
  проверяются, прочие ошибки разбора — тоже «GLB повреждён». У файла без сцен корни — узлы,
  которые ничьи не потомки: прежний обход шёл от каждого узла и прошёл бы потомков дважды.
  Проверено: 80 моделей базового каталога принимаются; 25 узлов с 2^24 путей
  (`artifacts/stage4-glb-fuzz.txt`) отвергаются сразу, а раньше не было ответа и через 90 с.
- 2026-10-28 — шаг 6 (ADR-0011), что выяснилось по ходу:
  - «готово» и данные задачи пишутся одной транзакцией. Раньше отметку ставила отдельная
    транзакция `_finish`. Тогда процесс, остановленный между двумя транзакциями, оставил бы
    данные без «готово», и `on_fail` вернул бы чертёж в «готов к переводу» поверх уже
    переведённого.
  - `_fail` и `_release` берут строку задачи `FOR UPDATE` и трогают её, только пока она
    `queued` или `running`: задача, успевшая завершиться до остановки, остаётся как есть.
  - `fork` безопасен для соединений обработчика. Процесс задачи бросает пул
    (`engine().dispose(close=False)`), а psycopg 3.3 в `__del__` сверяет pid и не закрывает
    чужое соединение.
  - процесс задачи следит за родителем (`parent_process().join()`) и завершается, если
    обработчик пропал: Windows не останавливает потомков вместе с родителем.
  - в Linux процесс задачи заводит свою группу (`os.setpgrp`), и остановка задачи
    (`killpg`) останавливает и `dwg2dxf`. Осиротевшие процессы подбирает `init: true` у
    `worker` в compose.
  - отмена пишется в журнал (`task.cancel`). Выполняемая задача с просьбой отменить, если
    её обработчик пропал, при возврате в очередь отменяется, а не выполняется заново.
  - подписки: 12 функций `on_*` и `register` теперь не добавляют подписчика повторно.
    Все подписчики — функции модулей, поэтому проверка `not in` работает.
  - на Windows (spawn) тесты `test_worker.py` идут 3–10 с каждый, тест с настоящим
    обработчиком `python -m app worker` — 9,9 с.
- 2026-10-28 — R-017: в окружении `dwg2dxf` только `PATH`, `LD_LIBRARY_PATH` и
  `SYSTEMROOT` (Windows). В Linux `preexec_fn` ставит `RLIMIT_AS` — `APP_DWG2DXF_MEMORY_MB`,
  по умолчанию 4096 — и `RLIMIT_CPU` 900 с, не выше жёсткого предела системы. Размер памяти
  вычисляется до запуска, `resource` импортируется заранее: в процессе задачи есть поток
  надзора, и в `preexec_fn` нельзя ничего, что ждёт блокировку. Проверено в Linux, в образе
  `planuchet-app` (pytest в нём нет, только проба): `ulimit -v 4194304`, `ulimit -t 900`,
  `APP_*` нет. Отдельный контейнер без сети — вне рамок (в FINDINGS — «перенесена»).
- 2026-10-28 — шаг 8, интерфейс. `CancelJob` (`web/src/lib/jobs.tsx`) — у хода разбора и
  перевода чертежа, загрузки здания и полной выгрузки. Статус `cancelled` завершает слежение
  за задачей; уведомление «отменено» — серое: отменил сам человек. Не переведённый чертёж
  показывает причину над частями листа. Попутно: после запуска перевода список чертежей не
  перечитывался, и значок оставался «выберите этажи» вместо «переводится».
  Проверено в браузере на стенде разработки (база `app`, миграция 0016 применилась):
  - чертёж из 12 000 линий разобран обработчиком (`spawn`);
  - перевод → ход и «Отменить» → меньше чем через секунду «Перевод не выполнен: Задача
    отменена…», уведомление «отменено», этаж не заведён;
  - процесс задачи завершён, в базе задача `cancelled`;
  - повторный перевод запускается;
  - «Настройки» → «Загрузка файлов» — семь лимитов со значениями ТЗ.

  На стенде осталось здание «DWG3D-12 — проверка отмены».
  Ловушка стенда: средство запуска не находит `sh` (Git Bash не в PATH приложения), а `sh`
  не запускает `npx` из Windows. На время проверки `.claude/launch.json` был исправлен
  локально (полный путь к `sh.exe`, vite через `node`) и возвращён — в репозиторий правка
  не попала.
- 2026-10-28 — находка: перевод «путаницы» (случайные пересекающиеся линии) ест память
  без предела. В Linux, проба в образе `planuchet-app`:
  - 12 000 линий: ~110 МБ первые 35 с, потом рост ~700 МБ/с, к 60-й секунде — 12 ГБ;
  - 3000 линий: 23 ГБ за 106 с;
  - 6000 линий: 14,7 ГБ за 142 с.

  Таймаут (60 мин) от этого не спасает: процесс задачи съест память сервера, где и база,
  гораздо раньше. В R-017 ограничена только память `dwg2dxf`. Тесты не страдают: отмена
  приходит за секунды, до роста.
- 2026-10-28 — CI: задание `server` на этом раннере идёт ~25 мин (и до задачи: #1450 —
  1165 с), а строка точек pytest попадает в журнал только целиком, после 72 тестов. Это было
  принято за зависание, и пайплайны #1457 и #1458 отменены зря; #1458 перезапущен. #1456
  (коммит шага 6): 180 прошли, упали только оба теста R-017, которые чинит шаг 7. Все
  `test_worker.py` в Linux (`fork`) зелёные, тест тяжёлого перевода — 18 с.
- 2026-10-28 — по находке о памяти (согласовано с Yury Mikhailov) процесс задачи в Linux
  получает `RLIMIT_DATA`: `APP_TASK_MEMORY_MB` (4096) сверх уже занятого. Обработчик после
  `create_app()` занимает по `VmData` 717 МБ (16 потоков OpenBLAS на 16 ядрах), а реально в
  памяти лишь 116 МБ (RSS). Абсолютный предел съел бы эту долю, тем большую, чем больше
  ядер. `MemoryError` даёт отказ «Задаче не хватило памяти — больше N МБ…», и обработчик
  работает дальше. Переменные прокинуты в `deploy/compose.yml`, описаны в
  `docs/INSTALL.md`; ADR-0011 дополнен. Тест тяжёлого перевода в `test_drawings.py` даёт
  обработчику 1024 МБ, чтобы взрыв памяти на медленном раннере не задушил машину. Проверено
  в Linux-контейнере: тест нехватки памяти и оба теста R-017 зелёные.
