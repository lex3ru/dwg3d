# Руководство администратора системы

Это руководство для того, кто устанавливает и сопровождает цифровой двойник:
сервер, вход через Keycloak, резервные копии, обновления, а в самой системе —
здания, каталог и назначение администраторов зданий. Работа внутри здания
описана в [руководстве администратора здания](building-admin.md), работа
сотрудника — в [руководстве пользователя](user.md).

## Что вы можете

Администратор системы — это учётная запись с клиентской ролью Keycloak
`dwg3d.admin` (клиент `twin`, роли из `resource_access.twin.roles`). Эта роль назначается только в Keycloak; из
интерфейса системы её выдать нельзя. В системе вы:

- видите все здания и в каждом можете всё, что администратор здания;
- создаёте здания;
- назначаете администраторов зданий (раздел «Доступ» здания);
- ведёте каталог типов и наборов свойств;
- смотрите «Состояние системы».

В меню у вас есть блок «Система»: «Здания», «Каталог», «Состояние системы».

Остальные права (просмотр, ответственный, администратор здания) хранит
сервис «Доступ»; их выдают людям из справочника, а не учётным записям.
Пользователь без записи в справочнике людей не видит ничего.

## Из чего состоит система

Весь стек — `deploy/docker-compose.yml` (проект Compose `twin`):

| Контейнер | Что делает |
|---|---|
| `web` | Caddy: интерфейс и единая точка входа (`/api`, `/auth`, `/q` → шлюз; `/kc` → Keycloak) |
| `gateway` | шлюз: сессии входа, пропуск запросов в сервисы, события в браузер, отчёты |
| `import`, `import-worker` | чертежи: загрузка и файлы; очередь сборок DWG/DXF → модель |
| `buildings` | здания, этажи, помещения, ревизии, комментарии |
| `catalog` | типы мебели и оборудования, схемы свойств, 3D-модели |
| `assets` | объекты: свойства, состояние, ответственный, файлы, история, QR-метки |
| `people` | справочник людей, привязка к помещениям |
| `access` | права по областям |
| `journal` | лента событий |
| `planning` | варианты расстановки |
| `ping` | сервис-образец (нужен для проверки доставки событий) |
| `db` | PostgreSQL: база и роль на каждый сервис и Keycloak |
| `db-init` | при каждом запуске создаёт недостающие базы и роли |
| `nats` | шина событий (JetStream) |
| `keycloak` | вход; realm `twin` импортируется из `deploy/keycloak/` при первом запуске |
| `kc-init` | при каждом запуске создаёт учётные записи сервисов в Keycloak и выставляет адреса входа по `TWIN_PUBLIC_URL` |
| `s3` | хранилище файлов (RustFS) |

## Установка

### На своей машине (для пробы)

```bash
cp deploy/.env.example deploy/.env
docker compose -f deploy/docker-compose.yml up -d --build
```

Откройте http://localhost:8090. Первый вход — `admin` / `admin`, Keycloak
попросит сменить пароль.

### На сервере

Нужны Docker с Compose и копия репозитория.

```bash
deploy/make-env.sh https://twin.example.com twin.example.com
docker compose -f deploy/docker-compose.yml up -d --build
```

`make-env.sh` пишет `deploy/.env` со случайными паролями и ключами
(существующий файл не перезаписывает). Первый аргумент — адрес, который
открывают пользователи. Второй — домен, для которого Caddy сам получит
сертификат; тогда порты становятся 80 и 443. Без второго аргумента — обычный
HTTP (для работы за другим прокси с TLS).

Первый вход — `TWIN_ADMIN_USER` / `TWIN_ADMIN_PASSWORD` из `deploy/.env`.
Эта учётная запись уже имеет роль `dwg3d.admin`; пароль при первом входе
нужно сменить.

Храните `deploy/.env` в надёжном месте: без него копию не восстановить на
другом сервере.

## Настройки: `deploy/.env`

| Переменная | Что задаёт |
|---|---|
| `TWIN_PUBLIC_URL` | адрес системы для пользователей, без `/` в конце; на него возвращает вход |
| `TWIN_SITE` | `:80` — обычный HTTP; имя домена — автоматический HTTPS |
| `TWIN_HTTP_PORT`, `TWIN_HTTPS_PORT` | порты входа (по умолчанию 8090 и 8453) |
| `KEYCLOAK_ADMIN`, `KEYCLOAK_ADMIN_PASSWORD` | администратор консоли Keycloak |
| `TWIN_OIDC_CLIENT_SECRET` | секрет клиента `twin` в Keycloak |
| `TWIN_ADMIN_USER`, `TWIN_ADMIN_PASSWORD` | первая учётная запись (администратор системы) |
| `TWIN_SECRET` | ключ, которым подписывается вход и шифруются сессии |
| `POSTGRES_PASSWORD`, `TWIN_DB_PASSWORD_<ИМЯ>` | пароль суперпользователя базы и пароли баз сервисов |
| `TWIN_SVC_SECRET_<ИМЯ>` | секреты учётных записей сервисов `twin-svc-<имя>` в Keycloak |
| `TWIN_S3_ACCESS_KEY`, `TWIN_S3_SECRET_KEY` | доступ к хранилищу файлов |
| `TWIN_BACKUP_DIR` | куда складываются резервные копии (по умолчанию `deploy/backups`) |
| `TWIN_ODA` | путь к ODA File Converter внутри контейнеров импорта (необязательно) |

Кроме того, Compose читает из `deploy/.env` (если задать): `TWIN_MAX_UPLOAD_MB`
— наибольший размер файла чертежа (по умолчанию 200 МБ), `TWIN_DB_POOL` и
`TWIN_DB_MAX_CONNECTIONS` — соединения с базой (см. ниже), порты
`TWIN_DB_PORT`, `TWIN_NATS_PORT`, `TWIN_KEYCLOAK_PORT`, `TWIN_S3_PORT`.
Резервный скрипт читает ещё `TWIN_BACKUP_KEEP` — сколько копий хранить
(по умолчанию 14).

Порты служебных частей открыты только на самой машине (127.0.0.1): PostgreSQL —
5433, NATS — 4223, Keycloak напрямую — 8181, S3 — 9002.

`TWIN_OIDC_CLIENT_SECRET` читается импортом realm только при первом запуске.
Если realm уже есть, а секрет вы поменяли, задайте тот же секрет клиенту
`twin` в консоли Keycloak.

## Чертежи DWG

DXF читается напрямую, DWG — через конвертер. В образе `import` есть
LibreDWG. ODA File Converter читает DWG надёжнее и нужен для сохранения DWG
с правками. Чтобы подключить его, смонтируйте исполняемый файл в контейнеры
`import` и `import-worker` (файлом `docker-compose.override.yml`) и укажите
путь внутри контейнера в `TWIN_ODA`. Файл дополнения подключается явно:

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.override.yml up -d import import-worker
```

Скрипты `backup.sh` и `restore.sh` файл дополнения не подключают: после
`restore.sh` выполните эту команду ещё раз.

Если сборок много, добавьте обработчиков очереди:

```bash
docker compose -f deploy/docker-compose.yml up -d --scale import-worker=2
```

## Соединения с базой

Все сервисы и Keycloak работают с одним PostgreSQL. Сервис держит до 5
соединений и при нагрузке открывает ещё до 5 (`TWIN_DB_POOL`); Keycloak —
до 25. Всего 11 процессов × 10 + 25 = 135 при пределе базы 200
(`TWIN_DB_MAX_CONNECTIONS`). Поднимая `TWIN_DB_POOL` или запуская больше
обработчиков, пересчитайте.

## Учётные записи: Keycloak

Консоль Keycloak — `<TWIN_PUBLIC_URL>/kc/admin/`, вход — `KEYCLOAK_ADMIN` /
`KEYCLOAK_ADMIN_PASSWORD`. Пользователи системы живут в realm `twin`.

Самостоятельной регистрации и сброса пароля на странице входа нет — они
выключены в realm. Учётные записи заводите вы.

### Как завести учётную запись сотрудника

1. В консоли Keycloak выберите realm `twin`, откройте пользователей и
   создайте нового: имя пользователя, почта, имя и фамилия.
2. Задайте пароль (временный — тогда при первом входе Keycloak попросит его сменить).
3. Чтобы человек что-то увидел, он должен быть в справочнике людей
   системы («Люди» в любом здании) с той же почтой. При первом входе
   учётная запись свяжется с записью человека сама.
4. Если почта не совпадает или одна почта у двух людей, администратор здания
   связывает их вручную: «Связать вручную» в «Людях» и идентификатор (ID)
   пользователя из консоли Keycloak.

После входа без записи в справочнике пользователь видит пустую страницу с
объяснением, к кому обратиться.

### Администратор системы, пароли, учётные записи сервисов

- Роли приложения — клиентские роли клиента `twin` вида `dwg3d.<role>`; роли realm
  не учитываются. Администратор системы — `dwg3d.admin`, пользователь — `dwg3d.user`.
  Учётная запись без ролей `dwg3d.*` тоже входит как пользователь: что ей видно,
  решают права в зданиях. Роли назначаются и снимаются в консоли Keycloak у пользователя.
- `kc-init` при запуске создаёт роли `dwg3d.admin` и `dwg3d.user`, если их нет, и
  выдаёт `dwg3d.admin` тем, у кого осталась прежняя роль `twin.admin`.
- Новый пароль пользователю задаётся там же, на вкладке учётных данных.
- Клиенты `twin-svc-buildings`, `twin-svc-assets`, `twin-svc-access` нужны
  сервисам для обращений друг к другу. Их создаёт и обновляет `kc-init` при
  каждом запуске по `TWIN_SVC_SECRET_<ИМЯ>`; вручную их трогать не нужно.

## Первые шаги в системе

### Как создать здание

1. Откройте «Здания» (страница «Мои здания»), нажмите «Создать здание».
2. Введите «Название» и, если нужно, «Адрес», нажмите «Создать».
3. Откроется раздел «Чертежи» нового здания: загрузите поэтажные планы
   (DWG или DXF) — см. руководство администратора здания.

Новое здание никому, кроме администраторов системы, не видно, пока в нём
не выданы права.

### Как назначить администратора здания

1. Откройте здание, затем «Люди». Если человека нет — «Добавить» (ФИО и
   почта, совпадающая с почтой в Keycloak).
2. Откройте «Доступ». В «Кому» выберите человека, в «Что может» —
   «администратор», в «Где» — «всё здание». Нажмите «Выдать».
3. После входа он увидит здание и блок «Управление» в меню.

Администратор здания может сам выдавать права в своём здании, в том числе
назначить ещё одного администратора этого здания. Выдать права в чужом
здании или роль администратора системы он не может.

## Каталог

Каталог — типы мебели и оборудования и наборы свойств. Читают его все,
правит только администратор системы. При первом запуске в нём уже есть
разделы, наборы «Учёт», «Медицинское изделие», «Мебель» и пять типов из
приложения А к ТЗ; повторный запуск ваши правки не трогает.

### Как создать или изменить тип

1. «Каталог» → «Тип» (новый) или нажмите на существующий.
2. Задайте «Название», «Раздел», «Ширина, м», «Глубина, м», «Высота, м».
3. Отметьте признаки:
   - «Переносной» — объекты этого типа может перемещать и ответственный;
   - «Контейнер» — в объект можно вкладывать другие.
4. Отметьте «Наборы свойств» и добавьте «Собственные свойства».
5. Если есть свойства с одним значением на тип, заполните «Значения для
   типа» — они показываются в карточке каждого объекта.
6. Нажмите «Сохранить».

### Как описать свойство

Для каждого свойства (в наборе или в типе) задаются:

- «Название» и «Ключ» (латиницей; по ключу значение хранится у объектов);
- «Вид»: текст, число (с «Единицей»), дата, да / нет, выбор (с «Вариантами»
  через запятую), человек;
- «Значение»: «у каждого объекта» или «одно на тип»;
- «Правит»: «система (каталог)», «администратор здания» или «ответственный».

Правила:

- совпадение ключей в схеме типа отклоняется при сохранении;
- свойство, у которого уже есть значения у объектов, нельзя убрать и нельзя
  сменить его вид;
- изменение набора меняет схему всех типов с этим набором; объекты, которые
  не проходят новую схему, получают отметку «требует заполнения».

### Как загрузить 3D-модель типа

У сохранённого типа в блоке «3D-модель» нажмите «Загрузить модель» и
выберите файл GLB. Модель появится в предпросмотре. Файл крупнее 20 МБ или
с габаритами, отличающимися от заявленных больше чем вдвое, принимается с
предупреждением. Без модели объект показывается фигурой по габаритам.
«Заменить модель» и «Убрать» — там же.

### Как убрать тип

«В архив» — тип больше не предлагается при выборе, объекты этого типа
остаются. Архив виден при отметке «архив» в списке; «Вернуть из архива»
возвращает тип. Тип, на который ссылаются объекты, не удаляется.

## Состояние системы

«Состояние системы» показывает по каждому сервису (и шлюзу): «Отвечает»,
«База», «Шина событий», «Ответ, мс». «Обновить» — проверить ещё раз.

Блок «Доставка событий»: «Проверить» создаёт запись в сервисе-образце и
ждёт её событие обратно через шину и шлюз — «Событие получено за N мс» или
«Событие не пришло за 10 секунд». Там же видно, подключён ли поток событий
браузера.

В таблице нет `db`, `nats`, `keycloak`, `s3` и `import-worker` — их состояние
смотрите в Docker:

```bash
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs --tail 200 <сервис>
```

Каждая запись журнала сервера несёт идентификатор запроса, общий для шлюза
и сервисов, — по нему запрос прослеживается через все сервисы.

### Что работает при отказе одного сервиса

| Не работает | Последствия |
|---|---|
| `access` | 30 секунд — как обычно, затем изменения отклоняются; чтение — до 5 минут |
| `buildings` | нельзя ставить и перемещать объекты; списки, карточки, правка свойств работают |
| `catalog` | объекты работают по сохранённым схемам; каталог не правится |
| `people` | карточки без имён ответственных (пометка «данные неполные») |
| `journal` | события копятся в шине и попадают в журнал после запуска |
| `planning` | нет вариантов; учёт, кабинет и редактор работают |
| `import` | нельзя загружать чертежи и выгружать чертёж с объектами |
| `nats` | изменения выполняются, события уходят после восстановления шины |

## Резервные копии

```bash
deploy/backup.sh                 # в TWIN_BACKUP_DIR (по умолчанию deploy/backups/<дата-время>/)
deploy/backup.sh /mnt/backup     # или в указанный каталог
```

В копию входят все базы (сервисов и Keycloak, по файлу `<база>.dump`) и
хранилище файлов (`s3.tar.gz`). Система при этом работает. Хранятся
последние `TWIN_BACKUP_KEEP` копий (по умолчанию 14), старые удаляются.

Для ежедневной копии — строка в cron:

```
30 2 * * *  /путь/к/репозиторию/deploy/backup.sh >> /var/log/twin-backup.log 2>&1
```

События в пути (в шине) в копию не входят. После восстановления
расхождения между сервисами устраняет сверка: сервис «Доступ» сверяет
автоматические права при запуске и каждые 10 минут.

Копируйте каталог копий и `deploy/.env` за пределы сервера.

## Восстановление

### На том же сервере

Базы и файлы **заменяются** содержимым копии:

```bash
deploy/restore.sh deploy/backups/20261005-151506
```

Скрипт останавливает сервисы, пересоздаёт базы, восстанавливает их и
хранилище файлов и запускает стек.

### На чистом сервере

1. Установите Docker, получите репозиторий.
2. Положите `deploy/.env` **с прежнего сервера** (в нём `TWIN_SECRET`,
   секрет клиента Keycloak, пароли баз и адрес системы) и каталог копии.
3. Выполните `deploy/restore.sh <каталог копии>`.
4. Войдите администратором и откройте «Состояние системы»: все сервисы
   должны отвечать.

Адрес системы лучше оставить прежним. При смене адреса поправьте
`TWIN_PUBLIC_URL` (и `TWIN_SITE`) в `deploy/.env` и перезапустите стек:
`kc-init` при запуске выставляет клиенту `twin` адреса возврата по
`TWIN_PUBLIC_URL`. Если вход всё же не работает, проверьте адреса клиента
`twin` в консоли Keycloak.

## Обновление

Перед обновлением снимите резервную копию. Затем — один сервис или весь стек:

```bash
git pull
docker compose -f deploy/docker-compose.yml up -d --build <сервис>
docker compose -f deploy/docker-compose.yml up -d --build            # весь стек
```

При обновлении одного сервиса остальные продолжают работать. Миграции базы
сервис применяет сам при запуске. Запросы к нему во время перезапуска
получают ответ 503, события дожидаются в шине.

## Чего пока нет

- Копилота (ИИ-помощника) и его настройки внешней модели — этап 9 не сделан.
- Маршрутов, зон и кабельных трасс — не начаты. Инженерные системы
  (видеонаблюдение, освещение, Wi-Fi, пожарная сигнализация, СКУД, СКС) —
  слои редактора с зонами действия оборудования; ссылки для просмотра без
  учётной записи выдаёт администратор здания в «Доступе».
- В интерфейсе нет удаления и переименования здания и правки разделов
  каталога.
- В редакторе каталога не задаются обязательность свойства, цена, артикул
  и поставщик типа (цены используются в спецификации вариантов).
- Кнопки запуска сверки прав в интерфейсе нет — она идёт сама.
- Срок хранения журнала не задаётся из `deploy/.env`: сервис `journal`
  хранит события 5 лет (его переменная `TWIN_JOURNAL_KEEP_DAYS`, 1825 дней),
  но `docker-compose.yml` эту переменную не передаёт.
