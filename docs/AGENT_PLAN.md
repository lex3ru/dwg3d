# План: доступ ИИ-агента к объектам программы

> Состояние: этапы 1–3 сделаны в ветке `agent-tokens` (октябрь 2026), дальше — этап 4.

Цель: ИИ-агент (Claude Code, Claude Desktop, позже встроенный чат) читает
и меняет проектные данные — слои, объекты, помещения, отчёты — от имени
пользователя, с теми же правами и тем же аудитом, что и UI. Изменения агента
пользователь видит сразу и может принять, отклонить или отменить.

## Что уже есть и на что опираемся

| есть                                                        | где                    |
|-------------------------------------------------------------|------------------------|
| доменная модель: проект → чертежи → этажи → помещения; слои → объекты | `models.py`   |
| реестр типов слоёв (виды геометрии, категории каталога)     | `layers.KINDS`, `shapes.py` |
| пакетные правки «всё или ничего», версии строк, проверка `build` (409) | `viewdata.apply`, `POST …/objects:batch` |
| проверка прав по роли в проекте, гостевые ссылки            | `access.py`            |
| аудит: кто, что, до/после                                   | `audit_log`, `viewdata.audit_entry` |
| отчёты: оборудование, по помещениям, проверка пожарки       | `reports.py`           |

Чего нет: входа без браузера (только cookie-сессия), живого обновления UI
(вкладка не узнаёт о чужих правках), серверного расчёта пути маршрута
(считает браузер).

## Принципы

- **Один путь к данным.** Инструменты агента вызывают те же функции, что и API
  (`viewdata.apply`, `layers.*`, `reports.*`), с `auth.current` = пользователь.
  Отдельной логики «для агента» нет — те же права, проверки, аудит.
- **Язык домена, а не координат.** Агент оперирует помещениями, этажами,
  слоями и позициями каталога; геометрию (куда встать в помещении, ряд,
  покрытие камер) считает сервер.
- **Права на сервере.** Ограничения — в токене и в `access.check`, не в промпте.
- **Деструктивное — только человеком.** Удаление проекта/чертежа/слоя,
  новая ревизия DWG, участники, ссылки, экспорт в DWG агенту не доступны.

## Этапы

Каждый этап — отдельный коммит (миграция Alembic, где нужна); после этапа
приложение рабочее.

### 1. Токены доступа для агента
- Таблица `api_tokens` (миграция 0010): владелец, имя, хэш, `project_id`
  (обязателен — токен на один проект), режим `read | propose | write`,
  срок, `last_used_at`, отзыв.
- Middleware: `Authorization: Bearer …` → `auth.Me` владельца, роль в проекте
  урезается режимом токена (не выше `viewer` для `read`). Запросы к другим
  проектам — 404.
- Аудит: `actor` = `login (агент: <имя токена>)` — в истории видно, что
  правку сделал агент.
- UI: в настройках проекта вкладка «Доступ для агентов» — создать (токен
  показывается один раз), список, отзыв. Только для `owner`/`editor`.
- Тесты: доступ к чужому проекту, истёкший/отозванный токен, `read` не пишет.

Сделано (`tokens.py`, миграция 0010, раздел проекта «ИИ-агенты»). Отличия и уточнения:
- Таблица `agent_tokens`; токен `dwg3d_…`, срок 1–365 дней (по умолчанию 90).
- Выпустить токен может любой участник; `write` — только редактор или владелец.
  Список: свои токены, владелец видит все и может отозвать любой.
- Агенту запрещено на уровне HTTP (`tokens.agent_may`), что бы ни позволяла
  роль: участники, ссылки, токены, `/api/users`; из записи разрешены только
  объекты и метки (`/objects`, `/pins`, `:batch`), создание и изменение слоёв,
  но не их блокировка/разблокировка и не удаление.
- Токен работает и при `DWG3D_AUTH=off` (ограничения те же).
- Известное ограничение: Keycloak при запросах по токену не спрашивается —
  пользователь, отключённый в Keycloak, сохраняет доступ своих токенов до
  срока или отзыва (у сессий браузера это проверяется обновлением токенов).
  Варианты: требовать недавнего входа пользователя, или раз в N минут
  проверять пользователя через Admin API Keycloak.

### 2. MCP-сервер, только чтение
- Python SDK `mcp`, транспорт Streamable HTTP, смонтирован в FastAPI на
  `/api/mcp` (тот же процесс, тот же Caddy). Аутентификация — токен этапа 1.
- Инструменты (ответы компактные, координаты в метрах, этажи и помещения
  с именами и номерами, не только id):
  - `project_overview` — чертежи, этажи, слои (тип, видимость, число объектов);
  - `list_rooms(drawing, floor?, query?)` — номер, название, площадь, контур/центр;
  - `layer_kinds` и `search_catalog(query, category?)` — что куда можно ставить;
  - `query_objects(layer?, floor?, room?, item?, bbox?)`, `get_object(id)`;
  - `report(kind: equipment | by_room | checks, layer?)`;
  - `recent_changes(limit)` — из аудита.
- Обёртка вокруг вызова инструмента выставляет `auth.current` и
  `auth.method` (чтение/запись), чтобы `access.check` работал как для HTTP.
- `docs/AGENT.md`: как подключить Claude Code (`claude mcp add --transport http …`).
- Проверка: Claude Code, подключённый к локальному серверу, отвечает на
  «сколько камер на 2 этаже», «в каких помещениях нет розеток».

Сделано (`agent_mcp.py`, `docs/AGENT.md`): SDK `mcp` 2.x (`MCPServer`), без
состояния, ответы JSON со structured content. Маршрут `/api/mcp` вставлен в
приложение API напрямую (не mount), менеджер сессий — в lifespan API, заново
при каждом старте (запускается только один раз на экземпляр). Токен читается
из заголовков в каждом вызове (`ctx.headers`): контекст HTTP-запроса до
инструментов не доходит — сервер MCP исполняет их в своей группе задач.
Защита от DNS rebinding SDK выключена — доступ по токену, не по cookie.
Страница токена показывает команду `claude mcp add …`.

### 3. Запись: низкоуровневые правки
- `apply_changes(drawing, ops)` — тонкая обёртка над `viewdata.apply`:
  create / update / delete объектов, с `version` и `build`. При 409
  возвращать агенту текущие строки, чтобы он пересобрал правку.
- `create_layer(kind, name)`, `update_layer(id, visible?, locked?, name?)`.
- Лимиты: операций за вызов (например 200), вызовов записи в минуту на токен.
- Запрещено: заблокированные слои (`locked`), удаление слоёв.
- Доступно только токенам режима `write` (до этапа 5 — единственный способ писать).

Сделано: `apply_changes`, `create_layer`, `update_layer` в `agent_mcp.py`.
Ошибки данных и конфликты — ошибки инструмента, транзакция откатывается; при
конфликте агент получает текущие строки. id новых объектов, если агент их не
задал, создаются до вызова `apply` и возвращаются в ответе. Лимит частоты —
в памяти процесса (при нескольких процессах API — на каждый). Метки (pins)
через MCP не меняются — только объекты слоёв.

### 4. Живое обновление UI
Нужно и без агента (два пользователя в одном проекте), но с агентом без
него не обойтись — иначе правки не видны до перезагрузки.
- `GET /api/projects/{pid}/events` (SSE): после каждого успешного
  `apply`/изменения слоя — событие `{entity, ids, version, actor}`.
  Внутри процесса — очередь; при нескольких воркерах api — `LISTEN/NOTIFY`
  PostgreSQL.
- Фронтенд: подписка в `App.tsx`; по событию перечитывать изменившиеся
  объекты/слои (`useFurniture`, `useLayers`, `useShapes`). Чужая правка
  объекта, который сейчас редактируется, — предупреждение, не молчаливая
  перезапись; стек отмены не трогает чужие правки.
- Тост «Агент изменил 12 объектов» со ссылкой на список.

### 5. Предложения: предпросмотр → применить / отклонить
Основной режим для агента: он предлагает, человек решает.
- Таблица `proposals` (миграция 0011): проект, чертёж, автор (токен),
  описание от агента, `ops` (JSON, формат `viewdata.apply`), версии строк
  на момент предложения, статус `open | applied | rejected | stale`.
- Инструмент `propose_changes(drawing, summary, ops)` — проверяет ops
  так же, как `apply` (в транзакции с откатом), сохраняет, возвращает id.
  `proposal_status(id)` — чтобы агент узнал решение.
- UI: панель «Предложения» в доке — описание, список изменений, на плане
  и в 3D «призраки» (новые — полупрозрачные, удаляемые — красным,
  перемещения — стрелкой). Кнопки «Применить» / «Отклонить»; применение —
  `viewdata.apply` от имени пользователя, нажавшего кнопку, с пометкой
  «по предложению агента» в аудите. Устаревшее (строки изменились) —
  `stale`, применить нельзя.
- Режим токена `propose` (по умолчанию для новых токенов).

### 6. Высокоуровневые инструменты (то, ради чего всё затевается)
Считаются на сервере (shapely, `rooms.py`, `geometry.py`), результат —
набор ops, который идёт через `propose_changes` или `apply_changes`.
- `place_in_room(room, item, count?, where: center | along_wall | corners | grid)`
  с учётом контура помещения и уже стоящих объектов.
- `place_row(start, end, item, step | count)` — то же, что «Ряд…» в UI.
- `camera_coverage(floor | room)` — доля площади в поле зрения камер слоя
  «Видеонаблюдение», непокрытые участки.
- `check(kind)` — проверки (пожарка из `reports.fire_check`, далее новые).
- Маршруты: путь сейчас считает браузер (`viewer/routing.ts`). Варианты —
  перенести расчёт на сервер или давать агенту задавать только остановки
  (`props.stops`), а путь пересчитывать редактором при открытии, как после
  перестроения. Для начала — второй вариант.

### 7. Контекст и управление видом
- UI раз в изменение (с задержкой) сообщает серверу состояние вкладки:
  открытый чертёж, этаж, выделенные объекты, режим вида. Хранится в памяти,
  на сессию пользователя.
- `get_ui_context()` — агент понимает «вот это», «на этом этаже».
- `show(object | room | floor)`, `set_view_mode(...)`, `highlight(ids)` —
  команды в открытую вкладку через SSE этапа 4. Только вид, данных не меняют.

### 8. Встроенный чат (по результатам этапов 2–7)
- Панель в доке; бэкенд ведёт диалог с Claude API (tool runner), инструменты —
  те же функции, что в MCP. Ключ API на сервере, лимиты расхода на
  пользователя/проект, роль Keycloak `dwg3d.agent` для доступа к чату.
- Решать после того, как MCP-вариант проверен на реальных задачах.

## Порядок и минимальная версия

MVP — этапы 1–3: токены, чтение, низкоуровневая запись. Уже позволяет
подключить Claude Code и проверить, полезно ли это на практике.
Дальше 4 → 5 (без них запись агентом неудобна и рискованна для живых
проектов), затем 6 и 7 по мере надобности; 8 — отдельное решение.

## Проверка
- pytest на каждый инструмент: права (viewer/editor/гость, чужой проект),
  режимы токена, лимиты, 409 при устаревших версиях, аудит.
- Набор сценариев (10–20 запросов на естественном языке к тестовому проекту
  из `tests/make_sample.py`): ожидаемый результат — состояние данных после
  выполнения. Прогон через Claude Code, подключённый к локальному серверу;
  повторять после изменения описаний инструментов.

## Открытые вопросы
- MCP внутри api или отдельный сервис, ходящий в HTTP API? План исходит из
  первого (меньше кода, общие функции); второй проще изолировать и
  масштабировать.
- OAuth для MCP (вход через Keycloak прямо из клиента) вместо ручных
  токенов — удобнее, но сложнее; можно добавить после MVP.
- Гостевые ссылки заказчика: давать ли агенту режим только чтения по ссылке.
