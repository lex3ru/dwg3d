# Техническое задание: цифровой двойник здания

> Состояние: первая редакция от 05.10.2026. Этап 0 (каркас) сделан: общая основа
> сервисов, шлюз, шаблон сервиса, стек в Docker Compose — см. [README](../README.md).
> Решения, принятые в обсуждении, помечены «решено»; то, что ещё нужно
> согласовать, собрано в разделе 10.

## 1. Назначение

Система ведёт цифровой двойник здания: само здание (этажи, помещения),
мебель и оборудование в нём, люди, которые в нём работают.

- Здание создаётся из файла чертежа (DWG/DXF) — как в текущей версии.
- У пользователя есть личный кабинет: из него он видит объекты, к которым
  у него есть доступ (например, оборудование в своём помещении), и может
  править часть их свойств.
- Администратор здания добавляет мебель и оборудование, перемещает их,
  меняет свойства, назначает ответственных и выдаёт доступ.

Решено:

| Вопрос | Решение |
|---|---|
| Архитектура | микросервисы; автономные сущности реализуются независимо |
| Люди | справочник с привязкой к помещениям, без отслеживания местоположения |
| Данные с оборудования | только учёт; телеметрии в первой версии нет |
| Действия пользователя | просмотр и правка разрешённых свойств своих объектов |
| Масштаб | одна организация, несколько зданий |
| Данные текущей версии | не переносятся, новая система начинает с чистой базы |
| Обмен с 1С | не нужен; импорт и экспорт — Excel |
| QR-метки | нужны в первой версии |
| Просмотр без учётной записи | остаётся: ссылки только на просмотр |
| QR-метка без входа | ничего не показывает: сначала вход, затем карточка при наличии прав |
| Вложенность объектов | один уровень: объект может находиться внутри другого объекта |
| Файлы объекта | фотографии и документы у экземпляра |
| Инвентаризация по QR | не в первой версии |
| Видимость здания | план и 3D всего здания с названиями помещений видны всем, у кого есть доступ к зданию; объекты и люди — только в своих помещениях |
| Справочник людей | человек виден тем, кто видит помещение, к которому он привязан |
| Правки ответственного | применяются сразу, пишутся в историю, администратор может откатить |
| Доступ к зданию | только у тех, кому он выдан; по умолчанию нового пользователя не видит ни одного здания |
| Уведомления | не нужны |
| Шина событий | NATS JetStream |
| Координаты | у каждого объекта, включая переносное оборудование (кроме вложенных — они берут место контейнера) |
| Переносное оборудование | признак «переносной» у типа; такие объекты перемещает и ответственный, стационарные — только администратор |
| Подразделения | только поле у человека и фильтр в списках; областью доступа не являются |
| Место объекта | объект всегда числится в помещении и стоит на плане; склад — обычное помещение; ремонт вне здания отражается только состоянием |
| Проектирование | переносятся варианты расстановки, маршруты и зоны, инженерные расчёты; копилот остаётся |
| Отчёты | список объектов в Excel, ведомость помещения (PDF), чертёж с объектами (DXF/DWG) |
| Состав здания | один или несколько чертежей (файл на этаж или на корпус), у каждого свои ревизии |
| Просмотрщик | переносится целиком: 2D/3D, этажи, поиск, прогулка и полёт, измерения и разрезы, карта и фасад, маршрут, метки и комментарии |
| 3D-вид объектов | условная фигура по габаритам или модель GLB, загруженная в каталог |
| 2D-редактор чертежа | остаётся: стены, проёмы, помещения |
| План без чертежа | рисуется с нуля в 2D-редакторе здания: несущие стены и перегородки, прямые и дуговые, двери, окна, витражи, проходы; помещения и их площади получаются из замкнутых стен; несущие стены переносятся на новый этаж; под этаж кладётся картинка плана с масштабом по двум точкам. Хранится в `import` как чертёж вида «нарисованный план» и собирается в этажи, помещения и 3D так же, как DWG. Загруженный чертёж переводится в такой план (стены, проёмы, помещения, колонны, лестницы его сборки), и здание продолжает те же этажи и помещения |
| Учёт | каждый предмет — отдельный объект; на учёте он с инвентарным номером, но стоять на плане может и без него (решено 15.10.2026: сначала предмет, потом учёт); учёта группой нет |
| Ответственный за помещение | есть: правит разрешённые свойства всех объектов помещения; перемещать объекты не может |

Вне первой версии: телеметрия и тревоги, местоположение людей, заявки на
ремонт, бронирование, уведомления, отчёт по срокам (ТО, гарантия, договоры), изоляция данных нескольких организаций, обмен с 1С,
инвентаризация по QR-меткам, файлы у типов каталога.

## 2. Роли

| Роль | Что может |
|---|---|
| Пользователь | видеть здания, помещения и объекты, к которым есть доступ; править разрешённые свойства объектов, за которые отвечает |
| Ответственный за помещение | то же, что ответственный за объект, — для всех объектов своего помещения; добавлять и списывать не может, перемещает только переносные |
| Администратор здания | всё в своём здании: чертежи, помещения, объекты, люди, доступ |
| Администратор системы | здания, каталог, назначение администраторов зданий, настройки |

Вход — через Keycloak. Роль «администратор системы» — клиентская роль
Keycloak; остальные права хранит сервис «Доступ» (раздел 4.6).

## 3. Понятия

- **Здание** — этажи и помещения, полученные из одного или нескольких чертежей.
- **Ревизия** — очередная загрузка чертежа здания. Этажи и помещения
  сохраняют идентификаторы между ревизиями.
- **Тип** — позиция каталога: «стол 1400×700», «камера купольная».
- **Объект** — конкретный экземпляр типа: стоит в помещении, имеет
  состояние, ответственного и историю; на учёте — с инвентарным номером,
  без учёта — просто предмет на плане.
- **Человек** — запись справочника; может быть связана с учётной записью.
- **Назначение** — право человека на область: здание, этаж, помещение или объект.

## 4. Сервисы

Запросы и события каждого сервиса описаны в [CONTRACTS.md](CONTRACTS.md).
Таблицы каждого сервиса — в [DATA_MODEL.md](DATA_MODEL.md).

Общие правила:

1. У каждого сервиса своя база данных; чужие таблицы никто не читает.
2. Ссылки на чужие сущности — только по идентификатору (объект хранит
   `room_id`, но не геометрию помещения).
3. Чтение — HTTP с контрактом OpenAPI; изменения расходятся событиями через
   шину. Сервис обязан работать, если получатель события недоступен.
4. Идентификаторы — UUID, выдаёт сервис-владелец сущности.
5. Каждый сервис сам проверяет токен Keycloak и спрашивает права у «Доступа»;
   шлюзу на слово не верит.
6. Каждый сервис собирается, тестируется и выкатывается отдельно.

```
браузер ── шлюз ─┬─ Здание ──── Импорт чертежей
                 ├─ Каталог
                 ├─ Объекты
                 ├─ Люди
                 ├─ Доступ ──── Keycloak
                 ├─ Журнал
                 ├─ Проектирование
                 └─ Копилот
        все сервисы ══ шина событий
```

### 4.1. Здание

Владеет: здания, этажи, помещения (название, тип, площадь, контур),
ревизии, привязка к карте.

- Отдаёт дерево «здание → этаж → помещение», поиск помещений, геометрию
  для плана, ссылки на 3D-модель текущей ревизии.
- Принимает результат сборки от «Импорта» и сопоставляет новые этажи и
  помещения с прежними: идентификатор сохраняется, если помещение
  узнаётся (механизм привязки из текущей версии). Помещения, которые не
  нашлись, помечаются снятыми, а не удаляются.
- Здание собирается из одного или нескольких чертежей (файл на этаж или
  на корпус). Каждый чертёж обновляется своей ревизией; публикация ревизии
  одного чертежа не трогает этажи остальных. Взаимное положение чертежей
  (сдвиг, поворот, отметки этажей) задаёт администратор здания.
- Метки (входы, лифты, лестницы, свои) и комментарии на модели: привязаны
  к этажу и точке, видны тем, кто видит это место; комментарии можно
  оставлять к помещению и к объекту (по идентификатору).
- Привязка к карте и детальная модель фасада (GLB) — свойства здания.
- Ручные правки: переименовать помещение, сменить тип, объединить или
  разделить с указанием, какое помещение наследует идентификатор.
- События: `building.created`, `revision.published`, `room.changed`,
  `room.retired`, `room.merged`.

### 4.2. Импорт чертежей

Владеет: загруженные файлы, очередь сборок, артефакты (glTF, IFC, OBJ, DXF).

- Принимает DWG/DXF, разбирает (текущий конвейер: извлечение → геометрия →
  семантика → этажи → 3D), складывает артефакты в S3.
- Хранит настройки разбора чертежа и правки 2D-редактора (стены, проёмы,
  контуры помещений); правки переносятся на новую ревизию чертежа.
- Не знает про объекты, людей и права; результат отдаёт «Зданию».
- События: `build.started`, `build.progress`, `build.finished`, `build.failed`.

### 4.3. Каталог

Владеет: разделы и типы (габариты, 3D-модель, параметры, артикул,
поставщик, цена), описание свойств типа.

- Для каждого типа задаётся схема свойств экземпляра: название свойства,
  вид значения, единица, обязательность и **кто может править** —
  администратор или ответственный.
- Схема собирается из **наборов свойств**, общих для нескольких типов
  («Учёт», «Медицинское изделие», «Мебель»), и собственных свойств типа.
  Изменение набора меняет схемы всех типов, которые его используют.
- 3D-вид типа: условная фигура по габаритам и цвету раздела или модель
  GLB, которую администратор системы загружает в интерфейсе каталога
  (с поворотом и проверкой размера).
- Признаки типа: «контейнер» (в объект можно вкладывать другие) и
  «переносной» (объект может перемещать ответственный).
- Свойства самого типа (габариты, регистрационное удостоверение,
  расходные материалы) хранятся в каталоге один раз и показываются в
  карточке каждого экземпляра. Примеры схем — в приложении А.
- **Модели типа.** Тип говорит, *что* это — «Монитор 27″», его габариты и
  схема; модель — *какой марки и модели* конкретный объект: Dell P2723DE,
  LG 27UL550 — с артикулом, поставщиком и ценой по прайсу. У типа может быть
  сколько угодно моделей; объект называет свою модель или не называет.
  Цена типа — ориентировочная, для планирования без выбранной модели;
  вариант размещения считается по модели, когда она указана, иначе по
  цене типа. Модель, на которую ссылаются объекты, не удаляется, а
  архивируется. События: `product.created`, `product.changed`,
  `product.archived`.
- События: `type.created`, `type.changed`, `type.archived`. Тип, на который
  ссылаются объекты, не удаляется, а архивируется.

### 4.4. Объекты

Владеет: экземпляры мебели и оборудования.

Поля объекта: тип (`type_id`), модель типа (`product_id`, необязательно),
здание, этаж, помещение, координаты и угол
на плане, высота установки, инвентарный (необязательно) и серийный номер, состояние
(в работе / неисправен / в ремонте / на складе / списан), ответственный
(`person_id`), значения свойств по схеме типа, примечание, версия.

- Предмет и учёт — разные вещи. Объект ставится на план с инвентарным
  номером или без: без номера он **не на учёте** — стоит в помещении,
  рисуется, имеет свойства, состояние и QR-код, но списать его нельзя.
  «Поставить на учёт» даёт ему номер (свой или следующий свободный для
  типа); с этого момента он на учёте: номер занят навсегда, снять с учёта
  можно только списанием. Объект не на учёте администратор здания может
  **удалить** со сцены насовсем (с файлами и историей); объект на учёте не
  удаляется никогда — только списывается.
- Операции: создать, поставить на учёт, переместить (в пределах помещения
  или в другое), изменить свойства, сменить модель, сменить состояние,
  сменить ответственного, списать (на учёте), удалить (не на учёте).
  Массовые: импорт из Excel (строка без номера — объект без учёта),
  расстановка нескольких сразу (с номерами подряд или без учёта).
- Каждое изменение сохраняется в историю объекта: кто, когда, что было и стало.
- Перемещение: стационарный объект перемещает администратор здания.
  Переносной — также ответственный за объект и ответственный за помещение,
  в котором объект находится; переместить можно в любое помещение, которое
  перемещающий видит. Роль ответственного за объект при этом сохраняется,
  перемещение пишется в историю.
- Правки ответственного применяются сразу. Администратор здания может
  откатить любое изменение из истории объекта; откат — тоже запись истории.
- Одновременная правка — оптимистичная блокировка по версии.
- Вложенность — один уровень: объект может находиться внутри другого
  объекта (шкаф → коммутатор). Вложенный объект не имеет своих координат,
  перемещается вместе с контейнером и сам контейнером быть не может.
  Может ли тип быть контейнером — задаётся в каталоге. При списании
  контейнера вложенные объекты остаются в помещении с отметкой «требует
  размещения».
- Файлы: к объекту прикладываются фотографии (в том числе снимок с
  телефона из карточки) и документы (паспорт, инструкция, гарантийный
  талон, акт). Хранятся в S3; ограничения на размер и виды файлов
  настраиваются. Добавление и удаление файла попадает в историю объекта.
  Видит файлы тот, кто видит объект; прикладывает — ответственный и
  администратор.
- QR-метка: у каждого объекта постоянная короткая ссылка на его карточку;
  сервис отдаёт метки для печати — по одной и листом на помещение или
  выборку (PDF, размер наклейки настраивается). Ссылка не меняется при
  перемещении объекта и не содержит данных о нём. Без входа в систему
  ссылка ведёт на страницу входа; после входа открывается карточка, если
  у пользователя есть право на объект, иначе — «нет доступа». Гостевые
  ссылки на просмотр по QR-метке карточку не открывают.
- Объект всегда числится в помещении. Склад — обычное помещение на плане;
  состояние «на складе» ставится вручную. Объект, вывезенный в ремонт,
  остаётся на своём месте на плане с состоянием «в ремонте».
- Реагирует на события: `room.retired` — объекты остаются привязаны к
  снятому помещению и помечаются «требует размещения», пока администратор
  не переставит их; `room.merged` — переезжают в наследника;
  `type.changed` — проверка свойств по новой схеме.
- События: `asset.created`, `asset.registered`, `asset.moved`, `asset.changed`,
  `asset.retired`, `asset.deleted`.

### 4.5. Люди

Владеет: справочник людей (ФИО, должность, подразделение, контакты,
связь с учётной записью Keycloak), привязка к помещениям и рабочим местам.

- Источник: ручной ввод, импорт из Excel; учётная запись связывается с
  человеком при первом входе по почте или вручную администратором.
- Видимость: запись человека (ФИО, должность, подразделение, контакты)
  видна тому, кто видит помещение, к которому человек привязан;
  администратору здания — все люди здания. Имя ответственного в карточке
  объекта видно всем, кто видит объект. Гостям по ссылке люди не видны.
- Персональные данные — минимум, нужный для работы.
- События: `person.created`, `person.changed`, `person.left`,
  `person.assigned` (к помещению).

### 4.6. Доступ

Владеет: назначения «субъект — роль — область».

- Область: здание, этаж, помещение или объект. Право на область действует
  на всё внутри неё.
- Роли в области: просмотр, ответственный (правка разрешённых свойств и
  состояния, файлы), администратор. Ответственный за помещение — роль
  «ответственный» на области «помещение»; за объект — на области «объект».
- Доступ к зданию без назначений внутри даёт план и 3D всего здания с
  названиями и типами помещений, но без объектов и людей.
- Права выдаются человеку из справочника, а не учётной записи: пользователь
  без записи в справочнике не видит ничего.
- Вопрос к сервису: «может ли субъект S сделать действие A над R?» и
  «какие области видит S?». Ответы кешируются у сервисов на короткое время.
- Назначение может создаваться автоматически: человек привязан к
  помещению → получает просмотр помещения; назначен ответственным за
  объект → получает роль ответственного на нём.
- Ссылка для просмотра без учётной записи: администратор здания выдаёт
  ссылку на область (здание, этаж, помещение); по ней гость видит план,
  3D и объекты области без персональных данных. У ссылки есть срок, её
  можно отозвать; все открытия пишутся в журнал.
- События: `grant.created`, `grant.revoked`, `share.created`, `share.revoked`.

### 4.7. Журнал

Владеет: неизменяемая лента событий всех сервисов.

- Подписан на всю шину; хранит событие, автора, время, область.
- Отдаёт ленту по зданию, помещению, объекту, человеку — с учётом прав.
- Срок хранения настраивается.

### 4.8. Проектирование

Владеет: варианты расстановки, маршруты людей и зоны, кабельные трассы,
расчёты (Wi-Fi, освещение, извещатели, обзор камер), спецификации.

- Вариант — набор предполагаемых изменений к фактическому состоянию.
  «Применить вариант» превращает его в операции сервиса «Объекты»; новый
  объект без инвентарного номера встаёт на план без учёта.
- Сравнение вариантов и спецификация с ценами из «Каталога».
- Переносится из текущей версии; реализуется после сервисов 4.1–4.7.

### 4.9. Копилот

- ИИ-помощник; работает только через API остальных сервисов от имени
  пользователя и с его правами. Своих данных о здании не хранит (только
  беседы и предложения).
- Ничего не меняет сам: всё — предложением на одобрение, которое
  пользователь видит (объекты — на плане этажа) и применяет. Проверки и
  расчёты (план, расстановка, извещатели, камеры, аудит учёта) выполняет
  код сервисов; модель выбирает инструмент и объясняет.
- Модель — любая с OpenAI-совместимым API, локальная или внешняя; задаётся
  администратором системы. Сделан 13.10.2026: [COPILOT.md](COPILOT.md).

### 4.10. Шлюз и интерфейс

- Шлюз: единая точка входа, вход через Keycloak, маршрутизация к сервисам,
  сборные ответы для интерфейса (карточка объекта = объект + тип +
  помещение + ответственный), поток событий в браузер.
- Отчёты собирает шлюз из данных сервисов, с учётом прав запросившего:
  - **список объектов в Excel** — любая выборка из списка (здание, этаж,
    помещение, тип, состояние, ответственный) со всеми свойствами;
  - **ведомость помещения** (PDF) — объекты помещения с инвентарными
    номерами, состоянием и ответственными, люди помещения, место для подписи;
  - **чертёж с объектами** (DXF/DWG) — исходный план с объектами блоками
    с атрибутами; чертёж пишет «Импорт чертежей», объекты ему передаёт шлюз.
- Интерфейс — одно приложение с разделами: личный кабинет, просмотрщик
  (2D/3D), администрирование.
- Просмотрщик переносится из текущей версии целиком: 2D и 3D, лестница
  этажей, поиск помещений, карточки, режимы обзора, полёта и прогулки,
  рулетка и площадь, секущие плоскости, разнос этажей, карта под зданием,
  фасад, время суток, маршрут между помещениями, метки и комментарии,
  ссылка на текущий вид. Всё показывается с учётом прав: объекты и люди —
  только в доступных помещениях.

## 5. Сценарии

### 5.1. Личный кабинет

1. После входа пользователь видит свои здания и помещения и список
   объектов в них; отдельно — объекты, за которые он отвечает.
2. Поиск и фильтры: по названию, инвентарному номеру, типу, помещению, состоянию.
3. Карточка объекта: свойства, состояние, ответственный, помещение,
   история; кнопка «Показать на плане» открывает просмотрщик на объекте.
   Карточка открывается и по QR-метке с телефона.
4. Ответственный правит свойства, разрешённые схемой типа, и состояние.
5. В просмотрщике пользователь видит всё здание с названиями помещений;
   объекты и люди показаны только в помещениях, на которые есть право.
6. В своих помещениях пользователь видит людей, которые к ним привязаны.

### 5.2. Администратор здания

1. Создаёт здание, загружает чертёж, проверяет результат разбора, публикует ревизию.
2. Ставит объекты на план из каталога или импортирует из Excel; заполняет свойства.
3. Перемещает, меняет свойства и состояние, назначает ответственного, списывает.
4. Ведёт справочник людей, привязывает их к помещениям.
5. Выдаёт и отзывает доступ к зданию, этажу, помещению, объекту; выдаёт
   ссылки для просмотра без учётной записи; печатает QR-метки.
6. Загружает новую ревизию чертежа: видит, какие помещения изменились или
   пропали, и решает судьбу объектов, оставшихся без места.
7. Смотрит журнал изменений.

### 5.3. Администратор системы

Ведёт каталог (типы и схемы свойств), создаёт здания, назначает
администраторов зданий.

## 6. Интерфейс

Решено 05.10.2026: интерфейс строится от объектов и помещений, а не от 3D-сцены;
каркас один для всех ролей.

### 6.1. Каркас

- **Левое меню** — одно на всю систему. Сверху здание (если доступно одно — просто
  название, без выбора). Разделы: «Кабинет», «Помещения», «Объекты», «Люди», «План».
  Блок «Управление» (чертежи, доступ, журнал, редактор) виден администратору здания;
  «Здания», «Каталог», «Состояние системы» — администратору системы. Раздела,
  сервиса которого ещё нет или на который нет прав, в меню нет вовсе.
- **Верхняя строка** — где я нахожусь («2 этаж › Кабинет 214»), поиск, пользователь.
- **Центр** — содержимое раздела.
- **Правая панель** — карточка выбранного (помещение, объект, человек). Открывается
  поверх любого раздела; у открытой карточки свой адрес, которым можно поделиться.
- **Телефон** — меню заменяют четыре вкладки внизу (главная, помещения, план, я);
  карточка открывается отдельной страницей; на плане выбранное показано плашкой снизу.
- **Редактор** — тот же каркас: меню свёрнуто до значков, в центре сцена (2D/3D),
  слева дерево здания и каталог, справа свойства выбранного. Доступен
  администратору здания; сотрудник его не видит.

### 6.2. Экраны сотрудника

1. **Кабинет** — поиск и сканер QR, «требует внимания» (неисправное, требующее
   размещения или заполнения), мои помещения, объекты, за которые я отвечаю.
2. **Помещения** — список по этажам с поиском; страница помещения: план с
   подсвеченным помещением и объектами, список объектов, люди.
3. **Карточка объекта** — фото, состояние, свойства (разрешённые правятся на месте),
   файлы, история, «показать на плане». Одна и та же из списка, с плана, по QR.
4. **План** — упрощённый 2D-план этажа: переключатель этажей, поиск, выбор
   помещения и объекта. 3D — по кнопке, для тех, у кого есть редактор.

### 6.3. Правила

- Язык — русский. Работает в актуальных Chrome, Firefox, Edge; светлая и тёмная тема.
- Телефон — полноценный сценарий: все экраны сотрудника работают при ширине 360 пикселей.
- Недоступного действия на экране нет (а не серая кнопка).
- Состояние объекта видно одинаково в списке, на плане и в карточке.
- Изменения других пользователей появляются без перезагрузки страницы.
- У каждого экрана и открытой карточки есть адрес; ссылка открывает то же место.

## 7. Нефункциональные требования

- Масштаб: до 20 зданий, до 50 000 объектов и 5 000 человек на установку.
- Отказ одного сервиса не останавливает остальные: без «Проектирования» и
  «Копилота» учёт работает; без «Импорта» нельзя только загружать чертежи.
- Развёртывание — Docker Compose на одном сервере; у каждого сервиса свой образ.
- Резервные копии баз и хранилища файлов — ежедневно, с проверкой восстановления.
- Все изменения — с автором и временем; доступ к персональным данным — по правам.
- Контракты сервисов (OpenAPI, схемы событий) лежат в репозитории и
  проверяются тестами при сборке.

## Приложение А. Схемы свойств на примерах

Кто правит: **А** — администратор здания, **О** — ответственный (за объект
или помещение) и администратор.

### Набор «Учёт» — у всех типов

| Свойство | Вид | Правит |
|---|---|---|
| Инвентарный номер | текст, обязателен, уникален в организации | А |
| Серийный (заводской) номер | текст | А |
| Дата ввода в эксплуатацию | дата | А |
| Гарантия до | дата | А |
| Состояние | в работе / неисправен / в ремонте / на складе / списан | О (списание — только А) |
| Примечание | текст | О |

Ответственный, помещение и положение на плане — поля объекта, не свойства
схемы; их меняет администратор.

### Набор «Медицинское изделие»

| Свойство | Вид | Где хранится | Правит |
|---|---|---|---|
| Производитель, модель | текст | тип | система |
| Регистрационное удостоверение (номер, срок) | текст, дата | тип | система |
| Год выпуска | число | объект | А |
| Дата последнего ТО | дата | объект | О |
| Дата следующего ТО | дата | объект | О |
| Организация, проводящая ТО | текст | объект | А |
| Договор на ТО (номер, срок) | текст, дата | объект | А |

### Аппарат КТ

Наборы: «Учёт», «Медицинское изделие». Стоит на плане по габаритам,
привязан к стене не обязательно. Может быть контейнером (консоль,
инжектор — вложенные объекты).

| Свойство | Вид | Правит |
|---|---|---|
| Число срезов | число | тип |
| Потребляемая мощность | кВт | тип |
| Наработка трубки | число (сканов или секунд) | О |
| Дата замены трубки | дата | О |
| Дата контроля эксплуатационных параметров | дата | О |
| Следующий контроль параметров | дата | О |
| Санитарно-эпидемиологическое заключение на кабинет (номер, срок) | текст, дата | А |

### Гастроскоп

Наборы: «Учёт», «Медицинское изделие». Переносной: стоит на плане с
координатами, как любой объект; тип помечен «переносной», положение на
плане меняет ответственный.

| Свойство | Вид | Правит |
|---|---|---|
| Вид (видео / фибро) | выбор | тип |
| Диаметр вводимой части, рабочая длина | мм | тип |
| Диаметр инструментального канала | мм | тип |
| Число проведённых исследований | число | О |
| Дата последней проверки на герметичность | дата | О |
| Число ремонтов | число | А |

### Набор «Мебель»

| Свойство | Вид | Где хранится | Правит |
|---|---|---|---|
| Габариты | мм | тип (у объекта можно переопределить) | А |
| Материал, цвет | текст | объект | А |
| Износ | новый / хороший / изношен / под замену | объект | О |

### Рабочий стол

Наборы: «Учёт», «Мебель». Может быть контейнером (компьютер, тумба).

| Свойство | Вид | Правит |
|---|---|---|
| За кем закреплён | человек из справочника | А |
| Регулировка высоты | да / нет | тип |

### Кушетка

Наборы: «Учёт», «Мебель».

| Свойство | Вид | Правит |
|---|---|---|
| Вид (смотровая / массажная / процедурная) | выбор | тип |
| Допустимая нагрузка | кг | тип |
| Обивка допускает дезинфекцию | да / нет | тип |

### Кресло посетителя

Наборы: «Учёт», «Мебель». Собственных свойств нет. Каждое кресло —
отдельный объект с инвентарным номером; несколько одинаковых ставятся
массовой расстановкой с номерами подряд.

### Что из этого следует для модели

- Виды значений: текст, число с единицей, дата, да/нет, выбор из списка,
  ссылка на человека.
- У свойства три признака: где хранится (тип или объект), кто правит
  (система, А, О), обязательно ли.
- Нужны наборы свойств, общие для типов.
- Каждый предмет — отдельный объект с координатами и инвентарным номером;
  для однотипной мебели нужна массовая расстановка и выдача номеров подряд.
- Свойства-даты «следующее ТО», «гарантия до», «срок договора» позволят
  позже сделать отчёт по срокам; в первой версии по ним работает только
  фильтр в списке объектов.
