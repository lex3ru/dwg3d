# Архитектура

## Назначение

Система для учреждения (пример данных — «Поликлиника»): здание строится и смотрится в 2D и 3D,
по нему расставляются мебель, оборудование, камеры и светильники, считаются обзор камер и
освещённость; параллельно ведётся учёт имущества — единицы, остатки, документы движения,
стоимость, инвентаризация по QR-меткам с телефона. Требования и сценарии С1–С22 — `docs/TZ.md`.

Роли (`server/app/core/actor.py`):

- **admin** — видит и меняет всё;
- **viewer** («просмотр») — видит только выданные здания, без цен; чужое здание для него «не найдено»;
- **guest** — гость по ссылке, без учётной записи: только план и 3D здания. Маршрут открыт гостю,
  только если объявлен с `AnyActor`; по умолчанию закрыт (`CurrentActor`).

## Окружение

- **Браузер** на компьютере и телефоне — единственный клиент. QR-метки сканирует камера телефона
  прямо в браузере (`jsqr`); метка ведёт на `/q/<код>`.
- **Caddy** — HTTPS перед приложением. `CADDY_TLS=internal` — свой сертификат для локальной сети
  (корневой отдаётся по `http://<сервер>/ca.crt`), адрес почты — Let's Encrypt.
- **LibreDWG `dwg2dxf`** — внешняя программа, переводит DWG в DXF (`APP_DWG2DXF`; в образ
  собирается из исходников). Без неё читаются только DXF.
- **Keycloak** (OpenID Connect) — предусмотрен ТЗ 2.4, не подключён. Сейчас вход по паролю
  (Argon2), сеанс в cookie; способ входа отделён от ролей и прав (`access/api.py`).
- Брокера, кэша и внешних API нет: очередь задач и рассылка изменений живут в PostgreSQL.

## Компоненты

Модульный монолит (ТЗ 9): один код, два процесса, одна база.

| Компонент | Каталог | Ответственность |
| --- | --- | --- |
| Приложение | `server/app/main.py` | FastAPI: `/api/*`, WebSocket `/api/ws`, собранный интерфейс (остальные адреса — `index.html`) |
| Обработчик задач | `python -m app worker` | фоновые задачи из очереди в базе, по расписанию — тоже |
| Ядро | `server/app/core` | настройки, транзакция, кто действует, задачи, события, поиск, печать PDF/Excel |
| journal | `server/app/modules/journal` | журнал всех изменений; публикует, что изменилось |
| access | `…/access` | учётные записи, вход, сеансы, выдача зданий, ссылки для гостя |
| files | `…/files` | файлы по содержимому (sha256) в `APP_DATA_DIR/files` |
| system | `…/system` | настройки установки, состояние резервных копий, срок хранения журнала |
| building | `…/building` | здания, этажи, план, помещения, подложки, перевод чертежей (`drawing/`) |
| catalog | `…/catalog` | слои, характеристики, типы, модели, назначения помещений, 3D-модели; базовый каталог — `base.xlsx`, `models3d/` |
| planning | `…/planning` | расстановка предметов на плане |
| inventory | `…/inventory` | единицы и остатки, склады и места, документы, стоимость, инвентаризация, метки |
| link | `…/link` | связь предмета на плане с инвентарной единицей |
| calc | `…/calc` | расчёты на плане: обзор камер, освещённость |
| projects | `…/projects` | предлагаемые изменения расстановки, сравнение и применение |
| reports | `…/reports` | отчёты и ведомости, главная, полная выгрузка |
| transfer | `…/transfer` | перенос здания на другую установку ZIP-пакетом |
| Интерфейс | `web/src` | SPA на React; данные — React Query; редактор `editor/`: план в SVG, 3D на three.js |

Уровни модулей снизу вверх (`server/app/modules/__init__.py`):
journal → access, files, system → building, catalog → planning, inventory → calc, link, projects → reports, transfer.

Модуль вызывает только модули ниже и только через их `api.py`. Когда нижнему модулю нужно
сообщить о событии верхнему, верхний подписывается на крючок нижнего при сборке приложения
(`setup` в `module.py`): например, `link` слушает `planning.on_items_changed`,
`inventory.on_units_changed` и `building.on_plan_saved`.

## Данные

- **PostgreSQL 16**, одна база. Таблицы модуля — в схеме с его именем, служебные таблицы ядра
  (очередь задач) — в схеме `core`. Внешние ключи — только к своим таблицам, ядру и модулям ниже.
- **Одна транзакция на запрос** для всех модулей: операция, задевающая несколько модулей,
  выполняется целиком или никак. Журнал (`journal.api.record`) пишется в той же транзакции.
- **План этажа** — документ в JSONB (миллиметры, X вправо, Y вверх). Формат описан дважды:
  `server/app/modules/building/plan.py` и `web/src/editor/plan.ts` — менять оба. Помещения —
  отдельные строки, выводятся из плана при сохранении и сопоставляются со старыми по подписям.
- **Файлы** (чертежи, подложки, фото, 3D-модели, файлы документов) — на диске
  `APP_DATA_DIR/files/<aa>/<bb>/<sha256>`, в базе — только запись о файле. Файл не меняется.
- **Документы учёта**: черновик → проведён. Проведённый не правится, ошибка исправляется отменой
  — обратным документом со ссылкой на исходный. Место, состояние и остатки меняются проведением
  документов; исключение — объединение помещений на плане: единицы и остатки переходят к
  продолжающему помещению событием `room_merge` без документа (`inventory.api.rooms_continued`).
  Номера и остатки меняет один сеанс за раз: создание документа, проведение, отмена,
  проведение инвентаризации и `rooms_continued` встают в очередь учёта
  (`inventory.documents.lock` — `pg_advisory_xact_lock`), документ и карточка единицы при
  изменении читаются `FOR UPDATE` (ADR-0003). Новый код, меняющий остатки или выдающий номера,
  тоже берёт `lock`. Документ по единице — не раньше её последнего события, расход — не больше
  наименьшего остатка на любую дату с даты документа; история единицы («на дату», отмена) — по
  порядку проведения (ADR-0004).
- **Остаток** хранится по позиции «место + тип + модель» (`inventory.stock_move`); «без
  модели» — тоже позиция. Всё, что считает или выравнивает остаток, работает с позицией, в том
  числе пересчёт при инвентаризации (`inventory.count_stock`, ADR-0005).
- **Миграции** — Alembic, `server/migrations/versions/`; `serve` и `migrate` применяют их под
  `pg_advisory_lock`, чтобы приложение и обработчик не мигрировали одновременно.

## Потоки

1. **Чертёж → план (С1).** Администратор загружает DWG/DXF → файл сохраняется, ставится задача
   `building.analyze_drawing`. Обработчик переводит DWG в DXF, читает его ezdxf и делит лист на
   части-этажи. Затем `building.convert_drawing` распознаёт слои, стены, проёмы, колонны и номера
   помещений, совмещает этажи друг над другом и пишет планы. Ход задачи виден в интерфейсе
   (`web/src/lib/jobs.tsx`), с экрана можно уйти.
2. **Действие в редакторе.** Поставить, передвинуть или убрать предмет — одна пачка изменений
   `planning`: одна транзакция, одна запись журнала. Отмена — такая же пачка с обратными
   изменениями. Если связанный предмет перенесли в другое помещение, `link` в той же транзакции
   проводит «Перемещение» единицы.
3. **Живые обновления.** Журнал при записи шлёт `pg_notify('app_changes', …)` — только ссылки на
   изменённое, без данных. Приложение слушает канал и раздаёт сообщения в `/api/ws` тем, кому
   можно видеть здание; интерфейс перечитывает затронутые запросы (`web/src/lib/live.ts`).
   Гостю обновления не приходят.
4. **Фоновые задачи.** `tasks.enqueue(...)` в транзакции модуля → задача появляется, только если
   транзакция зафиксирована. Обработчик берёт по одной (`FOR UPDATE SKIP LOCKED`) и выполняет
   в своей транзакции. Задачи: разбор и перевод чертежа, полная выгрузка, загрузка здания из
   пакета; по расписанию — удаление истёкших сеансов и очистка журнала.
5. **Расчёты на ходу.** Редактор шлёт расстановку как на экране (и пока предмет тащат), сервер
   считает обзор и освещённость и возвращает простые фигуры; редактор рисует их, не зная, что
   за расчёт. Новый расчёт добавляется в `calc` без изменения редактора.
6. **Обход с телефона (С18, 6.7 п. 1).** Метки, ручные отметки и пересчёт остатков
   ведомости — очередь в `localStorage` телефона (`web/src/inventory/queue.ts`), досылка по
   одной и по порядку, раз в 4 с и после каждой отметки. Отметка уходит из очереди, только когда
   сервер её принял или отказал по ней самой (4xx). Нет связи, 5xx, 408, 429, 409
   «обновите и повторите» — ждать и повторить. 401 и 403 — стоять до входа: после входа
   `?next=` возвращает на ведомость, и очередь досылается. Повтор безвреден: отметка на сервере —
   «ведомость + единица», пересчёт — значение позиции. «Провести» недоступно, пока очередь
   устройства не пуста.

## Развёртывание и эксплуатация

- **Установка** — `deploy/install.sh` → Docker Compose `deploy/compose.yml`: `db` (PostgreSQL),
  `app` (`serve`), `worker`, `caddy`, `backup`. Образ `deploy/Dockerfile` собирает интерфейс,
  сервер и LibreDWG. Подробно — `docs/INSTALL.md`.
- **Настройки** — переменные `APP_*` (`server/app/core/config.py`), на установке — `deploy/.env`
  (создаёт `install.sh`). Процессов приложения — `APP_WORKERS`, по умолчанию 4.
- **Резервные копии** — сервис `backup`: `pg_dump` и файлы (жёсткие ссылки на прошлую копию),
  по расписанию `BACKUP_AT`, хранение `KEEP_DAILY`/`KEEP_MONTHLY`. Итог пишет в `last.json`,
  его показывает модуль `system`. Восстановление — `deploy/restore.sh`.
- **Логи** — stdout процессов (`docker compose logs`). Внутренняя ошибка отдаётся с кодом,
  тот же код — в логе. Проверка живости — `GET /api/health`. Метрик нет.
- **Защита запросов**: меняющие запросы к `/api/` принимаются только с заголовком
  `X-Requested-With: app`; cookie сеанса — только по HTTPS (`APP_SECURE_COOKIES`).

## Известные ограничения и техдолг

- Вход через Keycloak не сделан — только свои учётные записи (ТЗ 2.4).
- Гость видит план на момент открытия: живые обновления ему не приходят.
- Новый предмет ставится на план только мышью или касанием, не с клавиатуры.
- Замеры производительности (ТЗ 8.2) делались на компьютере разработчика, а не на эталонном
  рабочем компьютере и не на телефоне в сети учреждения.
- Сканирование QR камерой телефона вживую не прогонялось.
- Полная выгрузка всех зданий на стенде объёмов идёт около минуты, в фоне.
- У отправки из очереди отметок нет тайм-аута: зависший запрос (полуоткрытое соединение на
  телефоне) держит очередь без сообщения, пока браузер его не оборвёт (R-049).
- `legacy/` и `legacy2/` — прежние версии, только для справки; код не переносится (ТЗ 9.1).
