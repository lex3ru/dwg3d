# Этап 1. Ядро и архитектура

Прочитано целиком: `app/core/*` (750 строк), `main.py`, `__main__.py`, `models.py`,
`modules/__init__.py`, все `modules/*/module.py`, `journal/api.py`, `tests/test_architecture.py`.

## Итог

- **R-009 (К):** обработчик фоновых задач собирается без связей модулей — повторный перевод
  чертежа ломает привязку предметов и учёта к помещениям. Подтверждено на работающем
  обработчике.
- Устройство ядра простое и последовательное: одна транзакция на запрос с фиксацией до ответа,
  очередь задач в PostgreSQL со `SKIP LOCKED`, события без данных через `NOTIFY`, ошибки
  человеческим языком с кодом для поиска в логе.
- Правило модулей 9.2 в коде соблюдено, но тест его почти не охраняет (R-010).
- Журнал пишется почти везде; пробелы — проекты и черновики документов (R-011).

## Что проверено

| Тема | Вывод |
|---|---|
| Транзакции (`core/db.py`) | Сессия на запрос, `Depends(scope="function")` — фиксация до ответа: ошибка фиксации видна человеку. READ COMMITTED. Блокировки строк только у единиц при проведении, плана этажа, учётных записей |
| Пул соединений | `pool_size=10` (+10 сверх) на процесс; 4 процесса + обработчик + слушатели `LISTEN` → до ~90 соединений при `max_connections=100`; пул (20) меньше пула потоков FastAPI (40) — лишние запросы ждут до 30 с. Проверить под нагрузкой — этап 9 |
| Ошибки (`errors.py`, `main.py`) | `AppError` → `{"error": {code, message, field}}`; прочее → 500 с кодом, полный стек в логе. Проверка полей — «Проверьте поле «…»» |
| CSRF | изменяющие `/api/*` требуют `X-Requested-With: app`; CORS не открыт. Cookie сеанса — этап 2 |
| Фоновые задачи (`tasks.py`) | Очередь в `core.job`, `FOR UPDATE SKIP LOCKED`, задача — одной транзакцией, ход — отдельными; прерванные — снова в очередь (до 3 раз), но все сразу (R-013) |
| События (`events.py`) | `pg_notify` без данных, ссылки урезаны до 40 (лимит 8000 байт); отбор по правам — по `building:…` (R-012) |
| Сборка (`main.py`, `module.py`) | Модули подключаются из `INSTALLED`, связи — через `setup(app)`; в обработчике `setup` не вызывается (R-009) |
| Правило 9.2 | В коде нет относительных импортов, импорта пакетов модулей, `importlib` к модулям, SQL к чужим схемам, использования чужих ORM-классов. Тест ловит 1 из 5 видов нарушений (R-010) |
| Журнал в той же транзакции | `journal.record` пишет запись и `NOTIFY` в сессии вызывающего. Скрипт нашёл 12 изменяющих функций без журнала; после разбора 5 — пробелы (R-011), остальные — служебное (код метки двери, файл до привязки, отметки обхода с автором и временем) |
| Отчёты (`report.py`) | Все значения в HTML для PDF экранируются — внедрение HTML в WeasyPrint через отчёты невозможно. Другие построители PDF — этап 2 |
| Раздача интерфейса | `/{path}` — защита от выхода из каталога есть (`resolve` + проверка родителя) |

## Для следующих этапов

- **Этап 2:** другие построители PDF (`building/export.py:311`, `inventory/printing.py:26,84`,
  `projects/api.py:754`) — экранируют ли данные (WeasyPrint по умолчанию читает `file://` и
  `http://`); Excel — строки с `=` становятся формулами (`openpyxl`); `/api/docs` открыт без
  входа; `forwarded_allow_ips="*"` — проверить, что порт 8000 наружу не открыт.
- **Этап 3:** остаток (количественный учёт) не блокируется — два одновременных расхода
  могут увести его в минус; номера документов и единиц (`max+1`) при гонке дают 500 вместо
  понятной ошибки (уникальность в базе есть).
- **Этап 4:** воспроизвести R-009 по API: перевод чертежа → предметы и учёт → повторный перевод.
- **Этап 9:** пул соединений под нагрузкой.
- **Этап 11:** журнал по зданию, этажу, единице, документу (5.7.3) — в интерфейсе ссылки
  только по предмету, помещению, пользователю.
