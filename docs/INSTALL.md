# Установка и обслуживание

Инструкция для администратора сервера (ТЗ 8.5, 8.7 п. 3). Система ставится на один
сервер в учреждении и работает в его локальной сети.

## Что нужно

- Linux-сервер (Ubuntu 22.04+, Debian 12+ или похожий): 4 ядра, 16 ГБ памяти, SSD 1 ТБ под
  данные и **отдельный диск** (или сетевое хранилище) под резервные копии (9.5).
- Docker Engine 24+ с Docker Compose v2 (команда `docker compose`), bash.
- Доступ в интернет — только на время установки и обновления (скачать образы и
  библиотеки). Работает система без него.
- Свободные порты 80 и 443 (или другие — см. ниже).

## Установка

```bash
git clone <адрес репозитория> planuchet && cd planuchet
git checkout v1.2.0        # версия — тег; последняя: git tag --sort=-v:refname | head -1
./deploy/install.sh
```

Скрипт определит адрес сервера, создаст `deploy/.env` (пароль базы, адрес, порты, каталог
копий), соберёт и запустит систему, сделает первую резервную копию и заведёт администратора
`admin`. В конце он печатает адрес системы и **временный пароль** администратора; при первом
входе система попросит придумать свой.

Адрес можно задать явно (IP или имя, под которым сервер известен в сети):
`./deploy/install.sh 192.168.1.10`. Порты и каталог копий при первой установке — переменными:

```bash
HTTP_PORT=8080 HTTPS_PORT=8443 BACKUP_DIR=/mnt/backup/planuchet ./deploy/install.sh
```

Позже настройки меняются в `deploy/.env`; после правки снова запустите `install.sh`.

`PUBLIC_URL` — постоянный адрес системы: на него перенаправляется `http://` и по умолчанию
ведут ссылки в QR-метках (ТЗ 5.4.7). Указывайте адрес, который открывается с телефонов в
сети учреждения, — не `localhost`. Другой адрес для меток можно задать в интерфейсе:
«Настройки» → «Учёт имущества» → «Адрес системы для QR-меток» (ADR-0016).

## Сертификат (HTTPS)

Система работает только по HTTPS (8.4 п. 1).

- **В локальной сети** (`CADDY_TLS=internal`, по умолчанию) сертификат выпускает сама
  система. Браузер предупредит о нём, пока на устройство не поставлен корневой сертификат
  системы. Скачайте его по адресу `http://<сервер>/ca.crt` и установите как доверенный:
  в Windows — двойной щелчок → «Установить» → «Доверенные корневые центры»; на iPhone —
  открыть файл, затем «Настройки › Основные › Об этом устройстве › Доверие сертификатам»;
  на Android — «Настройки › Безопасность › Установить сертификат».
- **Доступ извне** (8.5 п. 3): серверу нужно имя в интернете и открытые наружу порты 80 и
  443. В `deploy/.env`: `SITE_ADDRESS=имя.учреждения.ru`, `PUBLIC_URL=https://имя.учреждения.ru`,
  `CADDY_TLS=адрес@почты` — сертификат Let's Encrypt выпустится и будет обновляться сам.

## Размер загрузок

Наибольший размер файла по видам (ТЗ 7.3 п. 4) меняется в интерфейсе: «Настройки» →
«Загрузка файлов». Сервер проверяет вход и лимит до приёма файла (ADR-0012). Caddy
дополнительно не пропускает тело запроса больше 301 МиБ — это общий предел файла (300 МБ)
с запасом на форму. Пакету переноса здания Caddy разрешает до 10 241 МиБ. Если перед
системой стоит свой прокси, его лимит тела запроса должен быть не меньше этих чисел.

## Обновление

Версии отмечаются тегами `vX.Y.Z` (ADR-0023): что изменилось и нужно ли что-то сделать
руками — в описании тега (`git tag -n20 v1.3.0`).

```bash
git fetch --tags
git checkout v1.3.0        # новая версия
./deploy/install.sh
```

Скрипт печатает, с какой версии на какую идёт обновление, и делает резервную копию —
если она не удалась, обновление не начинается; путь копии виден в выводе. Данные
переносятся сами (8.3 п. 5). Установленная версия — в `deploy/.version`.

## Если обновление не удалось

Новая версия могла не собраться (нет сети, не скачался образ) или не запуститься (ошибка
переноса данных). `install.sh` в обоих случаях завершается ошибкой и печатает команды
отката — с прежней версией и путём копии перед обновлением.

- **Не собралась** — система работает на прежней версии, данные не тронуты. Верните код
  прежней версии: `git checkout v1.2.0`. Причину (сеть, место на диске) устраните и
  повторите обновление.
- **Не запустилась** — система стоит, а данные могли быть перенесены наполовину. Перенос идёт
  только вперёд, поэтому прежней версии нужна база до обновления — копия, сделанная
  `install.sh`:

  ```bash
  cd deploy && docker compose logs --tail 500 app worker > update-failed.log  # для разработчиков
  git checkout v1.2.0                       # прежняя версия
  docker compose build                      # её образ
  ./restore.sh /mnt/backup/planuchet/daily/2026-11-02_101500   # копия перед обновлением
  ```

  `restore.sh` переспросит, заменит базу и файлы копией и запустит прежнюю версию. Пока шло
  обновление, система не работала, поэтому после копии ничего не теряется. Журнал
  `update-failed.log` передайте разработчикам; следующую попытку — с исправленной версией.

Откат проверен на стенде (DWG3D-18): обновление со сломанным переносом данных, затем
команды выше — прежняя версия работает с данными на момент обновления.

## Резервные копии

- Делаются каждую ночь (`BACKUP_AT`, по умолчанию в 02:00) в каталог `BACKUP_DIR`:
  `daily/<дата>` — база (`db.dump`) и файлы (`files/`); первая копия месяца остаётся в
  `monthly/<год-месяц>`. Хранятся 30 ежедневных и 12 ежемесячных копий (`KEEP_DAILY`,
  `KEEP_MONTHLY`). Файлы, которые не менялись, в копиях — жёсткие ссылки и места заново не
  занимают.
- **`BACKUP_DIR` должен быть на другом диске**, чем Docker (`/var/lib/docker`), — иначе
  копия погибнет вместе с данными (8.3 п. 3).
- Копия сейчас: `./deploy/backup-now.sh`.
- Когда была последняя копия и сколько места занято — в системе: «Настройки › Состояние
  сервера» (8.5 п. 4).

## Восстановление

```bash
./deploy/restore.sh /mnt/backup/planuchet/daily/2026-10-16_020000
```

Скрипт переспросит, остановит систему, заменит базу и файлы содержимым копии и запустит её
снова. Раз в квартал восстановление проверяется на отдельном сервере (8.3 п. 4): поставить
систему там же `install.sh`, затем `restore.sh` с копией боевого сервера.

## Производительность

Приложение работает несколькими процессами (`APP_WORKERS` в `deploy/.env`, по умолчанию 4 —
по числу ядер сервера): долгий отчёт или выгрузка не задерживают остальных. На сервере с
двумя ядрами поставьте 2, с восемью — можно 6–8; после правки — `install.sh`.

Процесс обслуживает одновременно до `APP_DB_POOL` запросов (по умолчанию 10); остальные под
пиком ждут очереди, а не получают ошибку (ADR-0020). Соединений с базой под пиком —
`APP_WORKERS × (APP_DB_POOL + 3) + 10`: по 3 у процесса — сокетам изменений и слушателю, 10 —
обработчику фоновых задач, резервной копии и `psql` администратора. При значениях по
умолчанию это 62, при восьми процессах — 114; база пускает 200 (`max_connections` в
`deploy/compose.yml`). Если не помещается, приложение при запуске пишет об этом в журнал —
уменьшите `APP_DB_POOL` или `APP_WORKERS` или увеличьте `max_connections`.

Фоновые задачи — разбор и перевод чертежей, полная выгрузка, загрузка здания — выполняются
по одной в каждой из двух полос: чертежи и всё остальное (ADR-0011). Процесс задачи в Linux
получает до `APP_TASK_MEMORY_MB` (по умолчанию 4096) сверх того, что занял обработчик:
испорченный чертёж за минуту съедает десятки гигабайт, а на сервере и база. Не хватило —
задача завершится с причиной «не хватило памяти». `APP_DWG2DXF_MEMORY_MB` (4096) — то же
для чтения DWG. Оба значения задаются в `deploy/.env`; на сервере нужно памяти на две задачи
сразу.

## Тестовые здания и стенд объёмов

- «Поликлиника» (ТЗ 7.2) — три этажа по придуманной планировке:
  `cd deploy && docker compose exec app python -m app sample polyclinic`.
- **Стенд объёмов 8.1** — для итоговой приёмки быстродействия (10.3), **только на отдельной
  установке**, не на рабочей: 20 зданий, около 10 000 помещений, 200 000 предметов (на
  одном этаже — 2 000), 50 000 единиц, 5 000 позиций остатков, 20 000 документов за год, 100
  учётных записей. `docker compose exec app python -m app sample volume` — около 10 минут.
  Замеры 8.2 на нём — `e2e/tests/volume.spec.ts` (`E2E_VOLUME=1`, README в `e2e/`).

## Базовые образы (для разработчиков)

Образ собирается из закреплённых частей, чтобы каждая установка и каждое обновление
собирали ту же систему, что проверена (R-038, ADR-0022):

- базовые образы — по дайджесту, `тег@sha256:…`, в `deploy/Dockerfile`,
  `deploy/backup/Dockerfile` и `deploy/compose.yml`; тег — для человека, скачивается то, что
  под дайджестом. Debian — 13 (trixie);
- архив LibreDWG сверяется с `LIBREDWG_SHA256` до распаковки: с неверной суммой сборка
  падает;
- uv — одной версии в `deploy/Dockerfile` и `UV_RELEASE` в `.gitlab-ci.yml`;
- в контекст сборки идёт белый список из `.dockerignore`: код сервера и интерфейса, без
  данных разработки, тестов и настроек.

Обновлять — отдельным MR, раз в месяц или при новости о дыре в безопасности: в новых
образах — исправления Debian, Python, PostgreSQL, Caddy.

```bash
docker buildx imagetools inspect python:3.12-slim-trixie | grep -m1 Digest
```

Дайджест из ответа (у многоплатформенного образа — дайджест списка, а не одной платформы)
заменяет прежний после `@`; у `postgres` — в `compose.yml` и `backup/Dockerfile` вместе
(pg_dump не старше сервера). Новая версия LibreDWG — новая сумма: скачать архив и подпись
`.sig` из релиза, проверить подпись (`gpg --verify`, ключ сопровождающего — Reini Urban),
взять `sha256sum` архива. Новая версия uv — `UV_RELEASE`, `UV_RELEASE_SHA256` и образ uv в
Dockerfile вместе. Согласованность проверяет `server/tests/test_deploy.py`; после замены —
сборка образа, проверки как в CI и e2e на собранном образе (`e2e/README.md`).

## Если что-то не так

- Состояние: `cd deploy && docker compose ps`; журнал работы:
  `docker compose logs --tail 200 app worker`. Ошибка, которую видел пользователь, содержит
  код — найдите его в журнале работы: `docker compose logs app | grep <код>`.
- Забыт пароль, а сбросить его некому (единственный администратор):
  `cd deploy && docker compose exec app python -m app reset-password admin` — печатает
  временный пароль; сброс записывается в журнал.
- Остановить систему: `cd deploy && docker compose stop`; запустить: `docker compose up -d`.
