# 0019. Дерево мест — готовым JSON из базы, помещения не проходят через Python

- Статус: предложено
- Дата: 2026-10-29
- Задача: DWG3D-17 · MR: !17
- Участники: Yury Mikhailov; готовил: Claude Code / Claude Opus 5.5

## Контекст

`GET /api/inventory/places` — здания → этажи → помещения и склады с ячейками для выбора места
(5.4.1) на экранах «Имущество», «Склад», «Инвентаризация», «Отчёты». На объёмах 8.1 — 20
зданий, 429 этажей, 10 000 помещений, ответ 1,5 МБ. После того как дерево стало собираться
тремя запросами вместо ≈ 450 (R-036), в базе помещения стоят 5 мс, а остальное — Python:
получить 10 000 строк, собрать словари, сериализовать JSON — ≈ 0,1 с счёта под GIL на
запрос. При 20 одновременных пользователях (8.1) дерево отвечало 0,66–1,09 с при норме 1 с
(8.2) — на границе.

## Рассмотренные варианты

1. **JSON собирает база** (`json_agg`, `json_build_object`) из подзапросов, которые отдаёт
   `building.api` (как в ADR-0018), маршрут отдаёт готовый текст — плюсы: API и интерфейс не
   меняются, Python почти не работает; минусы: форма ответа описана в SQL, маршрут обходит
   сериализацию FastAPI, браузер по-прежнему получает 1,5 МБ.
2. **Помещения этажа — по требованию**: дерево без помещений, помещения и поиск — отдельным
   запросом (предложение ревью) — плюсы: мало и серверу, и браузеру; минусы: меняются API,
   `PlacePicker` и шесть экранов, где он используется (там и поиск по всем помещениям), —
   объём отдельной задачи.
3. **Кэш дерева в процессе** — плюсы: просто; минусы: администратор, только что заведший
   склад или помещение, может его не увидеть, а сбросить кэш согласованно в четырёх процессах
   приложения непросто.

## Решение

Вариант 1, выбран с пользователем. `building.tree_sql(actor)` — подзапросы видимых зданий,
этажей и живых помещений (подпись — `room_title_sql`); `places.buildings_json` собирает из
них JSON одним запросом и получает его текстом (иначе драйвер разберёт его в объекты Python);
склады — их единицы — по-прежнему `warehouse_views`; маршрут склеивает части и отдаёт
`Response` с `application/json`.

## Последствия

- Ответ на стенде 8.1: 0,10 → 0,06 с одиночный, 20 одновременных — 0,34–0,42 с.
- Форму дерева теперь задаёт SQL; что она та же, что прежде, проверяет `test_registry.py`
  (ответ сравнивается с собранным прежним кодом — у администратора и «просмотра»), а что
  число запросов не зависит от этажей и складов — подсчёт запросов там же.
- JSON из PostgreSQL — с пробелами вокруг «:» (1,57 МБ вместо 1,45 МБ); в установке Caddy
  сжимает ответы, в сети разницы почти нет.
- Браузер на каждом экране с выбором места по-прежнему получает и разбирает всё дерево.
  Помещения по требованию (вариант 2) — отдельной задачей.
- Отрисовка `PlacePicker` — `<select>` на 10 000 помещений — стоит ~0,35 с, а в строках
  «Ввода остатков» он на каждой строке. Пока дерево шло 0,9 с, пауза приходилась на время
  после показа экрана; когда оно стало приходить сразу, переход на «Документы» вышел за 1 с.
  Выбрано с пользователем: до обращения к полю (наведение, нажатие, фокус) в списке пустой
  пункт и выбранное место, весь список — при обращении (а не «дорисовать сразу после показа
  экрана» — пауза та же, только позже). Список остаётся обычным `<select>`; e2e, выбирающие
  место через `selectOption`, сначала ставят фокус в поле.
