# 0023. Версии — теги vX.Y.Z; откат — прежний тег и копия перед обновлением

- Статус: принято
- Дата: 2026-10-29
- Задача: DWG3D-18 · MR: !18
- Участники: Yury Mikhailov; готовил: Claude Code / claude-opus-5-5

## Контекст

R-037: обновление — `git pull && ./deploy/install.sh`. Перед ним делается резервная копия, но
если новая версия не собралась или не запустилась (ошибка миграции), `install.sh` завершается
ошибкой и система стоит. Что было установлено до обновления, нигде не записано; как вернуться —
не описано. Миграции идут только вперёд, отката схемы в установке нет. Версий у системы нет:
`version` в `pyproject.toml` и `package.json` — 0.1.0 с начала, тег `v1-monolith` отмечает
первую, прежнюю версию системы (`legacy/`).

## Рассмотренные варианты

Как отмечать версии:

1. **Без тегов: `install.sh` запоминает хеш коммита** — плюсы: не нужен порядок выпуска;
   минусы: администратор видит хеши, не знает, какой коммит проверен и что в нём изменилось.
2. **Семантические теги `vX.Y.Z`** — плюсы: по номеру видно, нужно ли что-то делать руками и
   есть ли перенос данных; описание тега — заметки к выпуску; минусы: надо договориться, что
   какой цифрой считается.
3. **Теги по дате `vГГГГ.ММ.ДД`** — плюсы: видно, насколько стара установка; минусы: номер
   ничего не говорит о совместимости и ручных шагах.

Как откатываться:

1. **Миграции вниз (`alembic downgrade`)** — плюсы: не нужна копия; минусы: перенос данных
   обратим не всегда, путь вниз не проверяется, а прежний код не знает новых ревизий.
2. **Прежний тег и копия перед обновлением (`restore.sh`)** — плюсы: копию делает
   `install.sh`, восстановление уже проверяется раз в квартал (8.3 п. 4); пока шло обновление,
   система не работала, терять нечего; минусы: пересобрать прежний образ (из кэша — быстро).
3. **Держать прежний образ под своим тегом** — плюсы: откат без сборки; минусы: имена образов
   по версиям в `compose.yml`, чистка старых; выигрыш — минуты.

## Решение

Семантические теги `vX.Y.Z` (выбор пользователя) и откат прежним тегом с копией перед
обновлением (вариант 2). Главная причина: откат собирается из того, что уже есть и проверено, —
копии `install.sh` и `restore.sh`.

- **X** — обновление требует действий администратора сверх `install.sh` (новая обязательная
  настройка в `deploy/.env`, переезд PostgreSQL на новую версию) или несовместимо меняет
  формат выгрузки (`docs/EXPORT.md`); **Y** — новые возможности и переносы данных
  (миграции); **Z** — исправления без миграций.
- Тег ставит сопровождающий на коммит `main` с зелёным CI, аннотированный:
  `git tag -a v1.3.0 -m "<что изменилось; что сделать руками>" && git push origin v1.3.0`.
  Номер версии — только тег; `version` в `pyproject.toml` и `package.json` не используется.
- `install.sh` берёт версию из `git describe --tags --match 'v[0-9]*.[0-9]*.[0-9]*'`
  (`v1-monolith` не подходит), после удачного запуска пишет её в `deploy/.version`, при
  обновлении печатает «прежняя → новая» и путь копии, при сбое — команды отката с ними.
- Обновление и установка — `git checkout <тег>`, а не `git pull`: рабочая копия всегда на
  известной версии, откат — та же команда с прежним тегом.

## Последствия

- `docs/INSTALL.md`: «Обновление» — по тегам, «Если обновление не удалось» — команды отката.
  Откат проверен на стенде (DWG3D-18).
- Перед `git checkout` прежнего тега администратор сохраняет журнал `app` и `worker`:
  пересборка пересоздаёт контейнеры, и причина сбоя пропадёт.
- `restore.sh` восстанавливает копию в отдельную базу, пока система работает, затем меняет
  базы переименованием (одной транзакцией) и удаляет прежнюю только после удачного запуска
  (`deploy/backup/restore-db.sh`). Было: `pg_restore --clean` поверх текущей — удалял только
  объекты из копии, и таблица, созданная неудачной версией, не давала удалить схему; на
  стенде откат падал на полпути. Отвергнуто: пересоздавать базу пустой перед восстановлением —
  битая копия стоила бы данных. Цена — место ещё на одну базу на время восстановления.
- Выпуск — шаг сопровождающего после merge; без тега `install.sh` покажет хеш, и откат всё
  равно сработает.
- Первый тег — `v0.1.0` после merge этого MR (как `version` в `pyproject.toml`); `v1.0.0` —
  версия, принятая заказчиком (10.3). До неё — `0.Y.Z` по тем же правилам.
- Пересмотреть, если обновления пойдут чаще, чем раз в неделю (тогда — образы в реестре по
  версиям, вариант 3), или если появятся установки без доступа к репозиторию.
