# 0024. Архивы полной выгрузки — срок из «Настроек», уборка по расписанию, вне резервной копии

- Статус: предложено
- Дата: 2026-10-30
- Задача: DWG3D-19 · MR: !19
- Участники: Yury Mikhailov; готовил: Claude Code / Claude Opus 5.5

## Контекст

Полная выгрузка (7.4) — ZIP почти со всеми файлами системы: фото, чертежи, 3D. Задача
`reports.full_export` пишет его в `data/exports/<id задачи>.zip`, и удалять архив было
некому (R-027). Резервная копия (`deploy/backup/backup.sh`) копирует `/data` целиком, так что
архив попадал в копии и жил там ещё до года: ежемесячные копии хранятся 12 месяцев. Если
выгрузка падала или её отменяли, недособранный архив тоже оставался. Регулярные выгрузки
«для хранения отдельно» постепенно займут диск данных и диск копий.

## Рассмотренные варианты

1. **Срок из «Настроек» и уборка по расписанию; `exports/` вне копии** — плюсы: работает
   на механизмах, которые уже есть (настройки модулей, задачи с `every=`, `on_fail`); диск
   растёт не больше, чем выгрузок за срок; минусы: архив, который не успели скачать за срок,
   придётся собирать заново; после восстановления копии старых архивов нет.
2. **Удалять архив сразу после скачивания** — плюсы: на диске ничего не залёживается;
   минусы: сервер не знает, докачался ли файл; второй раз скачать нельзя; архив, который не
   скачали, остаётся навсегда — срок всё равно нужен.
3. **Хранить N последних архивов** — плюсы: размер предсказуем по числу архивов; минусы:
   одна выгрузка «все здания» вытесняет архивы отдельных зданий, о которых администратор
   ещё помнит; размеры архивов отличаются в разы, так что предел по числу не ограничивает
   место.
4. **Архивы — в каталоге вне `/data` (отдельный том)** — плюсы: копия не видит их без
   правки скрипта; минусы: новый том в `compose.yml` и в установке, а удалять архивы по сроку
   всё равно нужно.

## Решение

Вариант 1: тот же способ, что у журнала (срок из «Настроек», уборка раз в сутки) и у
ведомостей стоимости (ADR-0021). Подробности:

- Настройка `export_days` «Срок хранения архивов полной выгрузки, дней», по умолчанию 30,
  от 1 до 365 (срок выбрал Yury Mikhailov). Модуль `reports` регистрирует её через
  `system.register`.
- Задача по расписанию `reports.purge_exports` (раз в час) удаляет: архивы готовых выгрузок
  старше срока; архивы упавших и отменённых выгрузок; архивы, у которых нет задачи. Архивы
  выгрузок, которые ждут очереди или собираются, не трогает. Сколько удалено, пишет в журнал.
- `on_fail` у `reports.full_export` запускает ту же уборку без срока, так что недособранный
  архив удаляется сразу, а не через час. Id задачи `on_fail` не получает (ADR-0011), но к
  моменту вызова статус задачи уже стоит, и уборка находит архив по нему.
- Из резервной копии исключён каталог `exports/`: `rsync --exclude=/exports/`.
- Если архива нет, в итог задачи пишется `deleted` (почему) и `deleted_at`. Так уборка
  помечает и выгрузки, чей архив пропал без неё, например после `restore.sh`.
  `GET /api/reports/exports/{id}` отвечает 404 с этим текстом. Тот же адрес отвечает на
  `HEAD`: карточка «Полная выгрузка» проверяет архив до скачивания и вместо «Скачать архив»
  показывает сообщение, а не сбой загрузки в браузере.

## Последствия

- Место на диске данных — не больше, чем занимают выгрузки за срок; в копиях архивов нет.
- Архив, который нужно сохранить, администратор скачивает и хранит сам — об этом говорят
  справка, карточка выгрузки и подсказка у настройки.
- `restore.sh` очищает `/data` целиком, поэтому после восстановления копии старых архивов
  нет; ссылки на них дают понятное сообщение.
- Публичный API: у адреса скачивания появился `HEAD`; скачать архив незаконченной выгрузки
  больше нельзя (раньше отдавался недособранный файл); в итоге задачи — поля `deleted`,
  `deleted_at`.
- Пересмотреть, если выгрузки станут регулярными по расписанию: тогда, возможно, нужно
  отдавать их во внешнее хранилище, а не держать в данных.
