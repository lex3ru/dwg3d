# 0007. В Windows приложение работает одним процессом

- Статус: предложено
- Дата: 2026-10-26
- Задача: DWG3D-8 · MR: !7
- Участники: Yury Mikhailov; готовил: Claude Code / claude-opus-5-5

## Контекст

Разработчики запускают сервер на Windows командой `python -m app serve` (`AGENTS.md`, быстрый
старт), e2e идут на нём через прокси Vite. `serve` запускал столько процессов uvicorn, сколько
задано в `APP_WORKERS`, по умолчанию 4 (`app/core/config.py`).

С несколькими процессами uvicorn в Windows берёт `SelectorEventLoop` (`uvicorn/loops/asyncio.py`)
и раздаёт процессам один слушающий сокет через `share`/`fromshare` (`uvicorn/server.py:139–154`).
py-spy показал: главный поток процесса стоит в `accept (socket.py:295)` внутри
`_accept_connection` по 3–64 с. За длительный прогон (2 полных e2e и 10 повторов «Вложения»,
25 мин) таких случаев было 58, во всех четырёх процессах по очереди. Пока процесс в `accept`, он
не обслуживает свои keep-alive-соединения от прокси и сокеты изменений: запросы ждут, пока к нему
не придёт новое соединение. e2e падали по тайм-ауту запроса — `apiRequestContext.put` в С6 и С8,
`apiRequestContext.post` в R-049, подготовка этажа в stage4 «Вложение» (R-051). Почему `accept`
блокируется на неблокирующем дескрипторе, не выяснено: проба показала, что режим у каждого
дескриптора свой и другие дескрипторы его не сбрасывают.

Рабочая установка — Docker на Linux (`deploy/`): там процессы наследуют сокет через fork, и CI
e2e на Linux этого не видит. Если ничего не делать, локальные e2e на Windows остаются
ненадёжными, а разработчик видит «зависший» интерфейс без ошибок в журнале.

## Рассмотренные варианты

1. **В Windows — один процесс, где бы ни было задано больше.**
   - Плюсы: один процесс — `ProactorEventLoop` без общего сокета, застревать негде. Правка в
     одном месте (`serve_workers` в `app/__main__.py`), Linux не затронут.
   - Минусы: в Windows долгий запрос (отчёт, выгрузка) задерживает остальные. Замеры 8.2 с
     несколькими процессами на Windows не сделать — но они и так для сервера на Linux.
2. **Оставить 4 процесса и ждать исправления в uvicorn.**
   - Плюсы: ничего не менять.
   - Минусы: локальные e2e ненадёжны неизвестно сколько. Причину в Winsock мы не нашли, внятно
     описать ошибку для uvicorn пока нечем.
3. **Другой ASGI-сервер в Windows (hypercorn, granian).**
   - Плюсы: можно оставить несколько процессов.
   - Минусы: новая зависимость, и разработка идёт на другом сервере, чем рабочая установка —
     ошибки одного не видны на другом.
4. **Разрабатывать в Windows только в Docker или WSL.**
   - Плюсы: среда как у рабочей установки.
   - Минусы: тяжелее для всей команды, быстрый старт в `AGENTS.md` перестаёт работать как есть.

## Решение

Вариант 1: в Windows `serve` запускает один процесс и пишет предупреждение, если задано больше.
Это самая маленькая правка, которая убирает зависания, и рабочую установку она не трогает.

## Последствия

- В Windows `--workers` и `APP_WORKERS` больше 1 не действуют — в журнале предупреждение R-051.
- Если понадобится рабочая установка на Windows или uvicorn исправит несколько процессов в
  Windows — пересмотреть.
- Открытый вопрос: почему `accept` в Windows блокируется на сокете, который asyncio сделал
  неблокирующим. Ответ нужен, чтобы сообщить об ошибке в uvicorn.
- Мониторы, которые часто открывают соединения к серверу, прячут это зависание: новое
  соединение выводит процесс из `accept`. Искать похожее — снимками стеков (py-spy), без
  соединений.
