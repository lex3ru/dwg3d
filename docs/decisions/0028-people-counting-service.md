# ADR-0028: отдельный сервис подсчёта проходов

Дата: 2026-11-03. Статус: предложено. Дополняет ADR-0027.

## Контекст

Нужен постоянный подсчёт входов и выходов независимо от открытого окна просмотра.
Пользователь предоставил прототип video/door_counter и согласовал отдельный сервис.
Ожидание видео уже приводило к блокировке запросов приложения; инференс нельзя
выполнять в HTTP-процессах основного приложения.

## Варианты

- Инференс в монолите: проще вызовы, но общие ресурсы, зависимости и отказы.
- Обязательная интеграция Frigate: дополнительная зависимость для первого этапа.
- Отдельный контейнер с HTTP-контрактом: изоляция и возможность переноса на GPU.

## Решение

Отдельный процесс аналитики использует алгоритм предоставленного прототипа.
Приложение хранит конфигурацию, версии и события; просмотр камер остаётся прежним.
Сервис опрашивает конфигурацию, постоянно читает камеры и отправляет события пакетами.
Доступ — служебный Bearer-токен; браузер не получает токен или адреса через этот API.
Настройки передаются без сохранения паролей в локальной очереди сервиса.
SQLite сервиса — очередь недоставленных событий с устойчивыми UUID; повторная доставка
не создаёт дублей в PostgreSQL. Событие содержит камеру, версию разметки, дверь,
направление и время прохода. Время получения хранится отдельно.
Первый этап — одна линия и направление входа на камеру, без слияния разных камер.
Подтверждение событий алгоритмом может отставать примерно на восемь секунд.

## Последствия

Сервис разворачивается отдельно, сначала на одном хосте с приложением. Для другого
хоста требуется защищённый канал. Нет прямого доступа сервиса к основной БД.
Рестарт трекера может терять незавершённые проходы; доставка уже записанных событий
переживает рестарт. Точность и производительность проверяются на реальной камере.
