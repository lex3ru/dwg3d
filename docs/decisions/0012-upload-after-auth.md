# 0012. Загрузка принимается после проверки прав, с лимитом своего вида из настроек

- Статус: принято
- Дата: 2026-10-28
- Задача: DWG3D-12 · MR: !12
- Участники: Yury Mikhailov; готовил: Claude Code / claude-opus-5-5

## Контекст

- **R-014.** FastAPI разбирает multipart (`UploadFile`) раньше зависимостей входа и прав.
  Без входа сервер принимает 300 МБ во временный файл и только потом отвечает 401.
  Несколько параллельных запросов заполнят диск, на котором стоит и база. В Caddy лимита
  тела нет.
- **R-040.** ТЗ 7.3 п. 4 задаёт лимиты по умолчанию для шести видов файлов: чертёж — 100 МБ,
  подложка — 50, Excel — 10, 3D — 20, фото — 15, документ — 25. Все они должны меняться в
  настройках. Сейчас настраиваются только фото и документ. Чертёж и подложка упираются в
  общий предел 300 МБ, у Excel лимита нет вовсе (файл разбирается в памяти), у 3D — константа.
- **Пакет переноса здания** несёт все файлы здания, а в 7.3 его нет. Единый лимит в Caddy по
  самому большому виду (предложение R-014: 110 МБ) сломал бы перенос.
- **Проба** (FastAPI 0.143, Starlette 1.8). Маршрут с `UploadFile` вытягивает из запроса без
  входа все 50 МБ. Маршрут, где файл принимает зависимость, объявленная после зависимости
  входа, — 0 байт.

## Рассмотренные варианты

1. **Лимит только в Caddy** (`request_body max_size`).
   - Плюсы: одна строка.
   - Минусы: без входа всё равно можно записать файл до предела. Без Caddy (разработка, e2e)
     защиты нет. Предел один на все виды, а лимитов из настроек Caddy не знает.
2. **Прослойка (middleware) перед маршрутами** проверяет `Content-Length` и вход до чтения
   тела.
   - Плюсы: ловит и будущие маршруты.
   - Минусы: ядро не знает о сеансах, и прослойке нужен распознаватель входа из модуля
     доступа. Лимит вида пришлось бы определять по пути запроса — нужна ещё одна таблица
     путей. Проверка прав (администратор) повторила бы проверки маршрутов.
3. **Файл принимает зависимость ядра — после зависимости входа.** Маршрут объявляет сначала
   `actor: Admin`, затем файл. Зависимость работает так:
   - `Content-Length` больше лимита вида — 413 до чтения тела;
   - иначе читает поток, считает байты и обрывает приём на лимите — это ловит и тело без
     `Content-Length`;
   - разбирает multipart во временный файл.
   - Плюсы: без прав тело не читается. Лимит вида проверяется до приёма. Права проверяют те же
     зависимости, что и сейчас.
   - Минусы: в каждом маршруте загрузки — зависимость вместо `UploadFile`, и поля формы
     (у загрузки имущества — здание и сопоставление) тоже берутся из неё. Важен порядок
     параметров.

## Решение

Вариант 3, а Caddy — вторая линия защиты. Только он гарантирует, что тело запроса без прав
не читается совсем, и проверяет лимит своего вида ещё до приёма.

- **Зависимость `core/uploads.py`.** Лимит вида в байтах ей передаёт маршрут, прочитав
  настройку: ядро настроек не знает. `files.store` проверяет лимит ещё раз, как сейчас.
- **Архитектурный тест:** в маршрутах нет `UploadFile`, `File` и `Form`. Новая загрузка не
  обойдёт проверку.
- **Семь настроек** в модуле `system`: шесть видов из 7.3 с умолчаниями ТЗ и пакет переноса —
  2048 МБ. Ключи `photo_max_mb` и `document_max_mb` прежние — сохранённые значения остаются.
  Верхняя граница для видов 7.3 — общий предел `uploads.MAX_FILE` (300 МБ, им же ограничено
  хранилище файлов), для пакета — 10 240 МБ.
- **Caddy:** `request_body max_size 301MiB` (общий предел и 1 МБ на форму) для всех путей,
  кроме `/api/transfer/check`, а для него — `10241MiB`, по верхней границе пакета.

## Последствия

- API загрузок не меняется: тот же multipart с полем `file` и полями формы, те же ответы.
  Новое — ответ 413 `too_large` до приёма. Описание тела загрузки в OpenAPI задаётся явно
  (`openapi_extra`): зависимость читает поток сама.
- JSON-запросы по-прежнему читаются до проверки входа — в память, а не на диск; их
  ограничивает Caddy. Меньший лимит для путей без загрузок не вводили: тогда список путей
  загрузок пришлось бы держать и в Caddyfile.
- Пересмотреть, если FastAPI научится проверять зависимости до разбора тела.
