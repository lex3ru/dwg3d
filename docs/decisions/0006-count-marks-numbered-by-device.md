# 0006. Отметки обхода нумеруются устройством, сервер пропускает опоздавшие

- Статус: предложено
- Дата: 2026-10-26
- Задача: DWG3D-5 · MR: !5
- Участники: Yury Mikhailov; готовил: Claude Code / claude-opus-5-5

## Контекст

Телефон отправляет отметки обхода из очереди (`web/src/inventory/queue.ts`) по одной и по
порядку. Это метки, ручные отметки, снятие отметки и пересчёт остатков. У отправки нет
тайм-аута. На телефоне соединение бывает полуоткрытым: после смены сети или при слабом Wi-Fi
запрос не получает ни ответа, ни ошибки, пока браузер сам его не оборвёт, а это минуты. Всё
это время очередь стоит без сообщения, и «Провести» недоступно (R-049, ТЗ 6.7 п. 1).

Тайм-аут с повтором сам по себе опасен: старый запрос может дойти до сервера позже нового.
Он застревает в сети или у Caddy, а сервер бывает занят. Тогда:

- «отметить» → «снять отметку» → опоздавшее «отметить» — вещь снова отмечена;
- пересчёт 7 → пересчёт 9 → опоздавший пересчёт 7 — записано 7.

Повтор безвреден, только пока он не обгоняет следующий запрос: отметка на сервере — «ведомость
+ единица», пересчёт — значение позиции. Тайм-аут делает обгон обычным делом.

## Рассмотренные варианты

1. **Устройство нумерует свои отметки, сервер помнит последний принятый номер.**
   - Плюсы: одно правило для всех четырёх видов отметок и для любого обгона запросов одного
     устройства. Часы телефона не нужны. Очередь и её правило ошибок (R-030) не меняются.
   - Минусы: новая таблица и два заголовка у запросов обхода. Порядок соблюдается внутри
     устройства, а не между устройствами.
2. **Версия у значения: сервер не принимает пересчёт или отметку старше записанных.**
   - Плюсы: понятия «устройство» нет.
   - Минусы: версия нужна каждой сущности отдельно. Снятая отметка удаляется, поэтому её версию
     пришлось бы хранить отдельно. Если версия — это время, нужны часы телефона, а им нельзя
     верить. Если номер, то его выдаёт сервер, а при обрыве ответа телефон этот номер не узнал.
3. **Очередь уходит одним запросом с номерами отметок.**
   - Плюсы: меньше запросов.
   - Минусы: опоздавший пакет так же надо отличать от нового, то есть номера нужны всё равно.
     Новый API и переделка очереди. Отказ по одной отметке (единица списана) нужно разбирать
     внутри пакета, а результат скана — для каждой метки.
4. **Только тайм-аут, без защиты.** Отвергнут: это как раз обгон из контекста.

## Решение

Вариант 1, согласован с Yury Mikhailov в задаче DWG3D-5. Главная причина: сервер точно знает,
какой из запросов устройства новее, и для этого не нужны ни часы, ни версии каждой сущности.

Как устроено:

- **Устройство и номер** (`queue.ts`). У браузера свой UUID v4 в `localStorage` (через
  `crypto.getRandomValues`: `crypto.randomUUID` есть только на HTTPS и localhost). Там же
  счётчик. Номер отметка получает при постановке в очередь, поэтому повтор после тайм-аута,
  5xx или входа уходит с тем же номером. Счётчик один на устройство, поэтому номера растут и
  внутри каждой ведомости. Отметкам, оставшимся в очереди от прежней версии, номера даются при чтении
  очереди, по порядку. Из очереди отметка убирается по номеру, а не первая по счёту: две
  вкладки одной ведомости больше не снимают чужую отметку.
- **Отправка.** Заголовки `X-Count-Device` и `X-Count-Seq` у четырёх запросов: скан,
  отметка, снятие отметки (`DELETE`, тела нет — поэтому заголовки, а не поле тела), пересчёт.
  Через 15 с запрос обрывается (`AbortController`) → «Нет связи». Очередь шлёт ту же отметку
  снова: раз в 4 с и после каждой новой отметки.
- **Сервер** (`server/app/modules/inventory/counts.py`). Таблица `inventory.count_device`:
  ведомость (внешний ключ, `ON DELETE CASCADE`), устройство, последний принятый номер; ключ —
  «ведомость + устройство». Номер проверяется в той же транзакции, что и изменение, до него:
  `INSERT … ON CONFLICT DO UPDATE SET last_seq = excluded.last_seq WHERE last_seq <
  excluded.last_seq RETURNING`. Если строка не вернулась, запрос пропускается: номер не больше
  принятого. Одновременные запросы одного устройства ждут друг друга на этой строке.
- **Ответ на пропущенный запрос — успех,** иначе очередь выбросит отметку с сообщением. Скан и
  отметка отвечают `{"result": "skipped"}`, снятие отметки и пересчёт — 204. Пропущенный скан
  проходит без звука и без «найдена»: ведомость просто обновляется.
- Отказ по самой отметке (4xx) откатывает транзакцию, и номер не занимается. Запрос без
  заголовков принимается как раньше, без проверки: API без устройства, вспомогательные
  запросы тестов. Неверный UUID или номер меньше 1 — ошибка 400.

## Последствия

- Зависший запрос держит очередь не дольше 15 с, дальше на экране «Нет связи». Медленный, но
  живой ответ (сервер под нагрузкой) тоже обрывается, и отметка повторяется. Это безвредно:
  какой из двух запросов дойдёт первым, тот и принят, второй пропущен.
- Опоздавший скан не даёт ни звука, ни результата на экране. Что вещь найдена, видно в списке
  места после обновления.
- Порядок — внутри устройства. Два телефона, отмечающие одну вещь, — это два человека, и
  принят последний, как и раньше.
- Если `localStorage` очищен, у браузера новое устройство. Очередь при этом пропадает так же,
  как и раньше.
- Любой новый клиент обхода (другое приложение, пакетная отправка) обязан слать те же
  заголовки, иначе на него защита не распространяется.
- Строк в `count_device` — по одной на телефон в ведомости; удаляются вместе с ведомостью.
