# 0002. Модульные тесты интерфейса — vitest; компоненты — в jsdom с Testing Library

- Статус: принято
- Дата: 2026-10-23
- Задача: DWG3D-2 · MR: !2
- Участники: Yury Mikhailov; готовил: Claude Code / claude-opus-5-5

## Контекст

Интерфейс проверялся только e2e (R-003): тестов `*.test.ts` в `web/src` не было, а скрипт
`"test": "node --test 'src/**/*.test.ts'"` модули интерфейса и не загрузил бы — они импортируются
без расширений и через `@/`, в них JSX. Чистая логика редактора (геометрия, прилипание, отмена)
проверялась через браузер.

R-007 показал, где e2e не хватает: после «Применить» итог в `ApplyDialog` подменялся вопросом,
когда приходил новый предпросмотр. В окружении задания `e2e` тест `stage8` проходил и без
исправления — гонка проявляется не всегда. А после исправления, когда новый предпросмотр
приходит, на экране ничего не меняется, и e2e может только подождать наугад. Нужен тест, где
порядок «итог → новый предпросмотр» задаёт сам тест.

## Рассмотренные варианты

1. **Только e2e** — плюсы: ничего нового; минусы: секунды на сценарий, гонки вроде R-007 не
   ловятся надёжно, чистые функции проверяются через интерфейс.
2. **`node --test`** — плюсы: без зависимостей; минусы: нет алиаса `@/`, импортов без
   расширений и JSX — нужны свои загрузчики, то есть второй способ сборки рядом с Vite.
3. **vitest: чистые функции — в node, компоненты — в jsdom с Testing Library** — плюсы: та же
   конфигурация, что у сборки (`vite.config.ts`: алиас, плагины); тест компонента — доли
   секунды, ответы API подменяются (`vi.mock("@/lib/api")`), порядок событий задаёт тест;
   минусы: 4 dev-зависимости; jsdom — не настоящий браузер (раскладка, canvas, WebGL).
4. **vitest в браузере (Playwright)** — плюсы: настоящий браузер; минусы: в задании `web`
   нужен образ с браузерами, медленнее, а для логики и состояния компонентов браузер не нужен.

## Решение

Вариант 3: `npm test` — `vitest run`, тесты лежат рядом с кодом (`*.test.ts`, `*.test.tsx`),
окружение по умолчанию — node, файл с компонентом объявляет `// @vitest-environment jsdom`.
Главная причина: тест задаёт порядок событий сам, поэтому гонки вроде R-007 воспроизводятся
каждый раз, а настраивать отдельную сборку не нужно.

## Последствия

- Задание `web` в CI запускает `npm test` перед сборкой.
- jsdom — версии 29: jsdom 30 требует Node ≥ 24.15, у разработчиков бывает 24.14.
- Компонент, который проверяется отдельно, не должен тянуть за собой редактор и 3D: поэтому
  `ApplyDialog` вынесен из `ProjectPage.tsx` в свой файл.
- Раскладка, контраст, canvas, 3D и сценарии целиком остаются за e2e.
- Чистые функции редактора проверяются рядом с кодом (`web/src/editor/*.test.ts`): геометрия,
  привязки и правка стен, прилипание к стене, размеры до стен, предупреждения, ряды, постановка
  и пачка изменений для сервера, отмена и повтор, черновик в браузере.
- Пересмотреть, если понадобится проверять в модульных тестах то, чего нет в jsdom (раскладку,
  canvas), — тогда вариант 4 для этих тестов.
