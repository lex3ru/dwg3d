# План перестройки архитектуры

Цель: проект — контейнер, в нём несколько DWG-чертежей и набор слоёв
(мебель, видеонаблюдение, маршруты людей и т. д.). Вход через Keycloak,
данные в PostgreSQL, всё разворачивается в Docker.

Каждый этап — отдельная миграция Alembic; между этапами приложение рабочее.
Пайплайн разбора DWG (extract / geometry / semantics / floors) не переписываем.

## Целевая модель данных

```
Project ─┬─ ProjectMember (user, role: owner | editor | viewer)
         ├─ ShareLink     (токен только на просмотр, срок, отзыв)
         ├─ Drawing[]     (DWG-файл, ревизии)
         │    └─ Build ── Floor ── Room   (этажи и помещения сохраняют id между пересборками)
         └─ Layer[]       (kind, variant_group, variant, visible, locked)
              └─ LayerObject (floor_id, room_id, item_id, geom, props JSONB)
```

`LayerObject.geom` — геометрия в координатах плана (м) одного из видов:

| вид       | примеры                                             |
|-----------|-----------------------------------------------------|
| point     | мебель, камера, розетка, датчик, точка доступа Wi-Fi |
| polyline  | маршрут человека, трасса кабеля, путь эвакуации      |
| polygon   | зона (чистая/грязная, зона доступа СКУД)             |

Тип слоя (`kind`) задаёт: какие виды геометрии и категории каталога в нём
допустимы, схему `props`, способ отрисовки, отчёты и правило экспорта в DWG.
Типы описываются в коде реестром, новый тип слоя — это новая запись в реестре,
без новой таблицы.

Рекомендация: образ `postgis/postgis` вместо `postgres` — пространственные
запросы (объект в помещении, пересечение маршрутов, покрытие) делаются в SQL.

## Этапы

### 0. Контейнеры
- Dockerfile: `api`, `worker` (LibreDWG собран в образе), `web` (статическая сборка Vite).
- `docker-compose`: `proxy` (Caddy: HTTPS, `/` → web, `/api` → api, `/auth` → keycloak),
  `db`, `keycloak`, `minio`, `backup` (pg_dump + зеркало MinIO по расписанию).
- ODA File Converter в образ не вшиваем (лицензия): подключается томом, если есть.
- Режим разработки: override-файл с горячей перезагрузкой api и web.

### 1. Проект → проект + чертежи
- Новая таблица `drawings`; `builds`, `jobs`, `floors` переезжают с проекта на чертёж.
- Существующий проект становится проектом с одним чертежом.
- Новая ревизия DWG загружается в тот же `Drawing`; этажи переносятся якорями, как сейчас.

### 2. Файлы в MinIO
- DWG, glb, планы, экспорты — в S3; api и worker работают через S3 API.
- Миграция существующих `data/jobs/*`.

### 3. Слои (ядро)
- Таблицы `layers`, `layer_objects`; реестр типов слоёв.
- `placements` → слой «Мебель», объекты с `fov/range` → слой «Видеонаблюдение».
- `pins` остаются отдельно (комментарии к проекту, не проектные данные).
- **Помещения с постоянным id**: таблица `rooms`, сопоставление между пересборками
  по номеру/названию и положению (как у этажей). Нужна для привязки объектов
  к помещениям и для маршрутов.
- Автоматическое заполнение `room_id` у объектов → спецификации по помещениям.

### 4. Keycloak, права, ссылки для заказчика
- Keycloak в compose, realm хранится в репозитории (импорт при старте).
- Вход через OIDC, api — BFF: токены на сервере, в браузере HttpOnly-cookie.
- `users` — зеркало по `sub`; свои пароли и сессии удаляются.
- Глобальная роль в Keycloak: `catalog_admin`. Роли в проекте — `project_members`.
- **Ссылка только на просмотр** (`share_links`): хэш токена, срок, отзыв,
  ограничение на выбранные чертежи/слои. Без учётной записи.

### 5. Интерфейс
- Список проектов → проект (чертежи, участники, ссылки) → просмотрщик.
- Панель слоёв: видимость, блокировка, порядок, активный слой для редактирования.

### 6. Функциональные слои: маршруты людей
- Маршрут = последовательность точек-остановок (помещения или точки плана),
  например «вход → регистратура → кабинет → касса → выход».
- Путь между остановками строится автоматически (A* по сетке проходимости —
  уже есть в `frontend/src/viewer/route.ts`, учитывает мебель), между этажами —
  через лестницы/лифты.
- Хранится замысел (остановки) и кэш рассчитанного пути с метриками:
  длина, время, число смен этажей.
- Пересчёт при изменении мебели или новой ревизии чертежа; маршрут, который
  стал непроходимым, помечается.
- Категории потоков (пациенты, персонал, чистый/грязный) и **поиск пересечений
  потоков**, которые не должны пересекаться — актуально для медицинских объектов.
- Для экспорта и отчётов расчёт пути нужен и на сервере: решим на этапе,
  портировать A* в Python или сохранять путь, рассчитанный клиентом.

### 7. Варианты
- Слой можно скопировать как вариант («Мебель — вариант Б»); варианты одного
  слоя образуют группу, в просмотре активен один.
- Сравнение двух вариантов: различия на плане и в спецификации (количество, стоимость).

### 8. Экспорт в DWG по слоям
- Каждый слой проекта → слой DWG: мебель и оборудование — блоками, камеры —
  с секторами обзора, маршруты и трассы — полилиниями, зоны — штриховкой.
- Основа — существующий `dxf_writer`; DXF → DWG через ODA/LibreDWG.

### 9. Новые типы слоёв
На механике этапа 3, каждый — запись в реестре, каталог и отчёт:
- СКС и электрика: розетки, трассы кабелей (polyline), длины кабеля.
- Пожарная сигнализация: извещатели, зоны.
- СКУД: считыватели, зоны доступа (polygon).
- Wi-Fi: точки доступа, оценка покрытия с учётом стен.

## Отложено
- Расчёт покрытия видеонаблюдения с учётом стен и зон DORI (EN 62676-4).
- Совместная работа в реальном времени (LISTEN/NOTIFY + SSE).
- Шаблоны помещений.
- Проверки по нормам.
