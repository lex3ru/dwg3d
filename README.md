# DWG → 3D

Поэтажные планы AutoCAD (DWG/DXF) → автоматическая 3D-модель здания (glTF, IFC, OBJ) →
интерактивный просмотр в браузере: вращение камерой, изоляция этажа, срез
«до этажа», разнос этажей, секущие плоскости, прогулка от первого лица, рулетка,
поиск и подсветка помещений, 2D-редактор для ручных исправлений.

## Инженерные системы

Типы слоёв со своими разделами каталога (новые разделы добавляются в
существующий каталог при старте сервера, правки каталога не трогаются):

| Слой | Каталог | Что считается |
|---|---|---|
| СКС и электрика | розетки RJ-45 и 220 В, блоки медконсолей, телеком-шкафы, щиты | **кабельные трассы** — полилинии на плане (витая пара, оптика, силовой, слаботочный, лоток) с запасом в %; метры по типам кабеля — в спецификации (единица «м») |
| Пожарная сигнализация | дымовые и тепловые извещатели, ИПР, оповещатели, табло «Выход», ППК | защищаемая площадь извещателя (радиус, ограничен стенами) на плане; проверка «помещения, где извещателей меньше, чем нужно по площади» на странице проекта |
| СКУД | считыватели, замки, кнопки выхода, турникеты, контроллеры | в спецификации |
| Wi-Fi | точки доступа потолочные и настенные (мощность, дальность) | покрытие: модель затухания с расстоянием и потерей ~7 дБ на каждую стену; тёмная зона — хороший сигнал (≥ −67 дБм), светлая — рабочий (≥ −75 дБм) |
| Освещение | потолочные панели, линейные, точечные, настенные, аварийные и напольные светильники (световой поток, мощность, угол луча, цветовая температура) | зона освещения каждого светильника на плане: тёмная — не меньше 300 лк, светлая — не меньше 100 лк на рабочей плоскости (0,8 м от пола); считается по потоку, углу луча и высоте установки, ограничена стенами |

Предмет из раздела системы ставится в слой своего типа (создаётся при
первом предмете). Покрытие Wi-Fi и извещателей показывается вместе с обзором
камер (меню мебели → «Обзор камер, покрытие Wi-Fi, извещателей и освещения»); трассы
рисуются в панели «Маршруты, зоны, трассы». Параметры позиций каталога —
`params: {radio: {tx, range}}`, `params: {detect: {radius}}` и
`params: {light: {flux, power, beam, cct}}` (лм, Вт, градусы, К).

## Экспорт чертежа со слоями

«Здание и этажи» → «Сохранить DXF / DWG»: исходный чертёж с правками
2D-редактора и объектами показанных слоёв проекта. Каждый слой проекта —
отдельный слой чертежа `3D_<название>`:

- мебель и оборудование — блоками `3D_<id позиции каталога>` (контур по
  габаритам, отметка лицевой стороны) с атрибутами `NAME`, `ARTICLE`, `NOTE`
  — их можно посчитать и выгрузить средствами AutoCAD (извлечение данных);
- камеры — дополнительно сектором обзора (угол и дальность);
- маршруты — полилиниями цвета потока с пронумерованными остановками;
- зоны — контуром со штриховкой и подписью.

Координаты переводятся обратно в систему чертежа каждого листа (масштаб и
выравнивание этажа), так что объекты встают на свои места. DWG пишется
через ODA File Converter; экспериментальный писатель LibreDWG с такими
файлами не справляется — без ODA скачивайте DXF.

## Варианты слоёв

«Вариант» у слоя на странице проекта — копия слоя со всеми объектами
(«Мебель — вариант 2»). Варианты можно менять независимо; в просмотрщике из
вариантов одного слоя показывается один (выбор — в меню «Слои проекта»).
«Сравнить…» показывает, что добавлено, убрано, перемещено и изменено от
одного варианта к другому (с переходом к объекту на плане), и спецификацию
обоих с разницей в количестве и стоимости
(`GET /api/projects/{id}/layers/compare?a=&b=`).

## Маршруты людей и зоны

Функциональные слои (кнопка «Маршруты людей и зоны» на нижней панели):

- **Маршрут** — путь человека по остановкам: точка на плане или помещение,
  на любых этажах (вход → регистратура → кабинет → касса). Путь между
  остановками строится по плану (обход стен и мебели, через дверные
  проёмы), между этажами — через лестницу или лифт, которые есть на обоих
  этажах; выбирается самый быстрый вариант. Считаются длина, время
  (1,3 м/с, лестница 15 с на этаж, лифт 30 с ожидания + 4 с на этаж) и
  число этажей. У маршрута — поток: пациенты, персонал, посетители, чистый,
  грязный, инфекционные пациенты, грузы.
- **Зона** — область этажа: чистая, грязная, стерильная, с ограниченным
  доступом.
- **Проверки**: потоки, которые не должны встречаться (чистый × грязный,
  пациенты × грязный, инфекционные × остальные…), не должны пересекаться
  или идти рядом; потоки не должны заходить в запрещённые им зоны (грязный —
  в чистую и стерильную, посетители — в стерильную и ограниченную…).
  Нарушения — в панели и красными значками на плане, число — на кнопке.

Путь хранится вместе с маршрутом. После перестроения или новой ревизии
чертежа остановки переезжают вместе с этажами, а пути пересчитываются при
следующем открытии панели редактором; после перестановки мебели — кнопкой
«Пересчитать». Правила потоков и зон — в `backend/dwg3d/shapes.py`.

## Возможности просмотрщика

Полноэкранная 3D-сцена, управление — панелями поверх неё:

- **Сверху:** «?» — справка по управлению; чип здания (переключение между
  обработанными чертежами) и поиск по помещениям и зданиям; рулетка
  (расстояние / площадь контура), меню «Отображение», переключатель
  **2D | 3D** (2D — ортографический вид сверху на активный этаж), «Карта»,
  настройки (этажи и слои; карта и детальная модель).
- **Слева — «лестница этажей»:** номер этажа делает его активным (этажи выше
  скрываются, камера подлетает), «+» — всё здание.
- **Справа:** время суток (день / вечер / ночь), зум «+»/«−», «вписать здание»,
  легенда цветов типов помещений. Слева внизу — оси X/Y/Z.
- **Снизу — панель инструментов:** режим навигации (Обзор / Полёт / Прогулка),
  маршрут по этажу, панель «Здание и этажи» (список этажей, 2D-редактор,
  сохранение чертежа, экспорт, предупреждения), метки (входы, лифты,
  лестницы, свои метки), мебель, комментарии. Справа внизу — панель
  режима навигации со скоростью и «сбросом».
- **Отображение:** прозрачные стены, только активный этаж, цвета типов
  помещений, разнос этажей (анимация 400 мс), подсветка текущего этажа;
  качество 3D — авто (по GPU и частоте кадров) / высокое / экономное /
  реализм (мягкие тени, освещение от окружения); подсветка фасада —
  авто / будни / праздники (видна вечером и ночью); слои и разрезы.
  Настройки хранятся в localStorage.
- **Ссылки:** состояние вида — в адресе:
  `#/f/<job>/floor_<id>/<2d|3d>?e=1&o=1&x=1` (разнос, только активный,
  прозрачные стены); «назад» в браузере работает.
- **Помещения:** подписи лежат на полу (размер по площади, перенос по ширине
  помещения, затухание при удалении), тип по названию — цвет пола;
  наведение подсвечивает, клик открывает карточку (название, тип, площадь,
  этаж, маршрут отсюда/сюда).
- **Навигация:** обзор (orbit, шаг зума настраивается), полёт (WASD /
  стрелки, E/Q — вверх/вниз, мышь, колесо), прогулка от главного входа
  (pointer lock, столкновения, подъём по ступеням).
- **Карта:** при привязке задачи к точке (широта, долгота, азимут, масштаб)
  под зданием — обесцвеченная карта OpenStreetMap с атрибуцией; источник
  тайлов можно заменить. Без привязки — нейтральная сетка. Небо-градиент.
- **Детальная модель:** к задаче можно загрузить GLB (фасад, мебель);
  узлы `floor_<номер этажа>` (или по высоте) попадают на этажи и
  подчиняются тем же переключателям; узлы с «furniture»/«мебель» в имени —
  слой мебели.
- **Маршрут:** путь между двумя точками / помещениями одного этажа (A* по
  растру плана с проходами через двери), длина и время пешком.
- **Метки и комментарии** хранятся на сервере вместе с задачей.
- **Мебель и оборудование** (кнопка 🛋 внизу): каталог для медицинских
  центров — 73 предмета в 10 категориях (регистратура и ожидание, кабинет
  врача, процедурная, стоматология, диагностика и лаборатория — в т. ч.
  КТ и МРТ с пультом, шкафами электроники и инжектором, — палата, санузел,
  хранение, инженерное оборудование, видеонаблюдение) с поиском. Предмет
  перетаскивается из каталога на план активного этажа (или щелчок по
  предмету, затем щелчок на плане) — в 2D и в 3D. Предметы «к стене»
  (шкафы, кушетки, раковины…) прилипают спинкой к ближайшей стене и
  доезжают в угол; Alt — без привязки. Поставленный предмет двигается
  мышью, R / Shift+R — поворот на 90°, Q / E — на 15°, стрелки — сдвиг на
  5 см (Shift — 50 см), Del — удалить, Ctrl+D — копия, Ctrl+Z — отмена. В
  карточке — размеры, угол, примечание (артикул), «Ряд…» (N предметов
  вдоль ширины с зазором). Проверки: предмет в стене, пересечение
  предметов, перекрытый дверной проём или створка, занятая зона
  обслуживания (показывается зелёным перед предметом); список предметов
  по помещениям. Расстановка хранится на сервере (таблица `placements`, в
  координатах плана). При перестроении модели оборудование, метки и
  комментарии переносятся на «свои» этажи так же, как правки редактора: этаж
  узнаётся по листу чертежа, даже если сменился его номер или выравнивание.
  Оборудование, чей лист пропал, не теряется — оно ждёт в панели «без этажа»
  (перенести на текущий этаж или удалить) и возвращается само, если лист
  найдётся при следующей сборке. Во время перестроения правки расстановки
  не принимаются, а сохранение со страницы, открытой до перестроения,
  отклоняется с просьбой обновить страницу. Мебель — препятствие для
  прогулки и маршрута. Модели: обычная мебель (диваны, кресла, стулья,
  столы, шкафы, сантехника, растения) — GLB из Kenney Furniture Kit 2.0
  (CC0, www.kenney.nl, `frontend/public/catalog/kenney/`), медицинское
  оборудование — процедурные модели по габаритам (свободных CC0-моделей
  медтехники нет). Любой предмет каталога может ссылаться на GLB (`model`,
  путь от `frontend/public/catalog/`, фасад к +Z) — он масштабируется до
  габаритов предмета.
- **Каталог оборудования** (⚙ → «Каталог оборудования…», роль
  «администратор каталога»): категории, позиции с габаритами, процедурной
  моделью, цветом, зоной обслуживания, параметрами камеры, артикулом,
  поставщиком и ценой; загрузка своей GLB-модели (масштабируется до
  габаритов). Позиции не удаляются, а снимаются с продажи: из выбора они
  пропадают, уже расставленные остаются на плане. Изменения сразу видны в
  панели «Мебель и оборудование». Хранится в PostgreSQL (`catalog_categories`,
  `catalog_items`), загруженные GLB — в `data/catalog/`;
  `backend/dwg3d/catalog_seed.yaml` загружается только в пустую базу.
- **Спецификация оборудования** (⚙ → «Спецификация оборудования…», любая
  роль): по зданию — количество по этажам, цены и суммы; «Все проекты» —
  сводная с количеством по каждому зданию. «Скачать XLSX» — та же таблица в
  Excel с формулами (количество × цена, итоги). Позиции без цены
  перечисляются, но в сумму не входят; суммы считаются по валютам.
- **Видеонаблюдение** (категория каталога): купольная, цилиндрическая
  настенная, узкоугольная для коридоров, панорамная 360° и поворотная
  камеры, видеорегистратор, пост охраны. У камеры в карточке — угол обзора,
  дальность, высота установки; направление — поворотом предмета. Обзор
  рисуется на полу этажа и конусом от объектива: лучи через каждый градус
  останавливаются стенами, перегородками, колоннами и высокой мебелью
  (от 1,7 м), дверные проёмы считаются открытыми, остекление — прозрачным;
  тёмная часть — зона, где различимы лица. В панели — доля площади каждого
  помещения в поле зрения камер (и доля с различимыми лицами); меньше 60 % —
  оранжевым. Показ обзора — «Обзор камер» в меню 🛋 и в панели.
- **2D-редактор этажа:** клик по проёму — сменить тип (дверь / окно / витраж /
  проход / заделать / убрать), клик по помещению — переименовать; инструменты
  «Стена», «Стереть», «Проём». Правки хранятся в конфиге (`edits`) и
  применяются при каждом перестроении.
- **Сохранение чертежа с правками (DXF / DWG):** правки из 2D-редактора
  вносятся в исходный чертёж — стёртые участки и новые проёмы вырезаются из
  линий стен с торцами, новые стены добавляются контуром, окна/витражи/двери
  рисуются условными обозначениями (дверь — полотно + дуга), переименованные
  помещения меняют подпись. Новые объекты — на слоях `Стены_правки`,
  `Окна_правки`, `Витражи_правки`, `Двери_правки`, `Текст_правки`, поэтому
  файл, загруженный повторно, даёт ту же модель. DWG пишется через ODA File
  Converter; LibreDWG умеет это лишь экспериментально (на сложных чертежах
  падает — тогда сохраняйте DXF, AutoCAD его открывает).
- **Экспорт:** GLB, OBJ (zip с MTL), IFC4 (этажи, стены/перегородки, колонны,
  перекрытия, двери, окна, лестницы, помещения с площадями).

## Установка

```bash
# DWG-конвертер (один из двух):
#  a) LibreDWG — ставится локально в проект, sudo не нужен
conda create -y -p .tools/libredwg -c conda-forge libredwg
#  b) ODA File Converter (точнее для новых версий DWG) — скачать с opendesign.com,
#     положить в PATH или указать путь в переменной DWG3D_ODA

cd backend && uv sync            # Python 3.12+
cd ../frontend && npm install

# PostgreSQL 16 (нужен серверу и тестам); схема применяется при старте API
docker compose up -d db
```

DXF можно загружать и без конвертера.

## Запуск

```bash
# production: UI на http://localhost:8765; процессов может быть несколько
cd frontend && npm run build
cd ../backend && uv run uvicorn dwg3d.api:app --port 8765 --workers 2

# разработка: API на 8765 + Vite (проксирует /api)
cd backend && uv run uvicorn dwg3d.api:app --port 8765 --reload
cd frontend && npm run dev
```

CLI без UI:

```bash
cd backend
uv run python -m dwg3d analyze plan.dwg              # слои, найденные этажи
uv run python -m dwg3d build plan.dwg -o out/        # model.glb + metadata.json + debug/*.png
uv run python -m dwg3d build plan.dwg -o out/ -c my.yaml
uv run python -m dwg3d db upgrade                     # схема БД до последней версии
uv run python -m dwg3d catalog dump catalog.yaml     # каталог из БД в YAML (копия, перенос)
uv run python -m dwg3d catalog load catalog.yaml     # импорт YAML по id; --prune снимет с продажи остальные
uv run pytest                                        # тесты на синтетическом чертеже
```

`out/debug/floor_*.png` — 2D-реконструкция каждого этажа (стены, проёмы,
помещения), `overlay.png` — все этажи друг на друге (проверка выравнивания).

## Как это работает

1. **DWG → DXF**: ODA File Converter, иначе LibreDWG `dwg2dxf`.
2. **Чтение** (`extract.py`): все сущности, включая вложенные блоки (слой «0»
   внутри блока наследует слой вставки), дуги/сплайны/полилинии с bulge
   аппроксимируются; всё сразу переводится в метры.
3. **Единицы** (`units.py`): `$INSUNITS`, иначе эвристика — типичная толщина
   стены (расстояние между параллельными линиями), длины сегментов, габарит.
4. **Слои** (`default_config.yaml`): роли `walls / columns / windows / doors /
   rooms / grid / ignore` задаются шаблонами имён; в UI роль любого слоя
   меняется выпадающим списком.
5. **Этажи** (`floors.py`): блоки-этажи → листы с собственной геометрией →
   кластеры в пространстве модели. Название/номер — из подписи «План 3-го
   этажа», имени листа (по видовому экрану) или атрибута блока; подвал, техэтаж,
   кровля распознаются. Отметки (`+4,150`) дают высоты этажей. Выравнивание —
   по подписанным осям, иначе голосованием по положениям осей и колонн, иначе
   по габариту.
6. **Лестницы и двери** (`features.py`): марш = ≥5 параллельных равных линий с
   шагом 0,2–0,42 м на любом неигнорируемом слое (ступени не попадают в стены,
   в 3D строятся ступенями); дуга ~90° радиусом 0,5–1,5 м у проёма = дверь с
   полотном. Утеплитель/облицовка приклеивается к стене, у проёмов вырезается.
   Слои перегородок (`wall_types.partition`) идут отдельным мешем и в IFC как
   `PARTITIONING`.
7. **Геометрия** (`geometry.py`): узлование линий, закрытие микроразрывов
   (snap / продление концов), полигонизация; «тонкие» грани = стены, поэтому
   двойные стены, стены с осевой линией на том же слое и многослойные стены
   не задваиваются. Непарные линии: пара параллельных → стена, одиночная →
   стена толщиной по умолчанию. Проёмы: разрывы между торцами стен
   (с линиями окон → окно, иначе дверь), а также блоки дверей/окон на сплошной
   стене (вырезаются). Помещения = внутренний контур минус стены и проёмы,
   названия — из текстов внутри.
8. **3D** (`model3d.py`): экструзия; проёмы в 2.5D — стена без проёма на всю
   высоту + подоконная часть и перемычка над проёмом (эквивалент булева
   вычитания, но без хрупких mesh-booleans); стекло, перекрытия, кровля.
9. **glTF** (`gltf.py`): GLB с иерархией `floor_<id>` → `_walls / _partitions /
   _columns / _slab / _stairs / _doors / _glass / _room_N`, контурные линии
   считаются на сервере (`*_edges`, LINES), метаданные в `extras` и
   `metadata.json`; 2D-планы этажей для редактора — `plans/floor_<id>.json`.
10. **IFC** (`exports.py`): стена — сплошное тело на всю высоту, двери и окна
    сидят в `IfcOpeningElement`, который вырезает стену-хозяина
    (`IfcRelVoidsElement`) и заполняется элементом (`IfcRelFillsElement`).
    Ограничение: «стена» в IFC — связный контур стен одной категории, а не
    отдельная прямая стена по оси; проём-«проход» остаётся просто разрывом.
11. **Проверка правдоподобия**: результат со статусом «Готово» может быть
    распознан неверно (не те слои или единицы, лист не является планом).
    `quality.status = suspect` и список причин показываются в UI отдельной
    карточкой: стен почти нет, стены занимают >50% площади, площадь этажа
    <10 или >200 000 м², нет помещений, этаж в 4 раза больше/меньше типичного.

### Инкрементальное перестроение

Разобранный чертёж и 2D-план каждого этажа кэшируются (`out/cache/*.pkl`).
Ключ кэша — файл, секции конфига, от которых зависит этап, и хеш исходников
пакета, поэтому смена эвристики сбрасывает кэш сама. Правка в 2D-редакторе
пересчитывает только свой этаж. Отладочные PNG в API рисуются по запросу из
кэша (в CLI — сразу, если нет `--no-debug`).

## Настройка

Любой параметр `backend/dwg3d/default_config.yaml` переопределяется YAML/JSON
(`-c` в CLI, поле `config` при загрузке, `POST /api/drawings/{id}/rebuild`).
Ручное назначение этажей:

```yaml
floors:
  items:
    - {candidate: c3, name: "3 этаж", level: 3, height: 4.2}
    - {candidate: c13, include: false}
    - {candidate: c7, offset: [0.5, 0]}     # доп. сдвиг, м

edits:                                    # то же, что делает 2D-редактор
  c3:
    add_walls:    [{a: [1, 2], b: [6, 2], thickness: 0.2}]
    erase_walls:  [{a: [3, 5], b: [4, 5], width: 0.6}]
    add_openings: [{a: [8, 0.1], b: [9.5, 0.1], kind: window}]
    openings:     [{at: [5.1, 3.4], kind: none}]   # door|window|vitrage|passage|wall|none
    rooms:        [{at: [2, 5], name: "Холл"}]
```

### Типы помещений, входы

```yaml
room_types:                     # первое совпадение по имени (glob, без учёта регистра)
  pool: {label: "Бассейн", color: "#5dade2", names: ["*бассейн*"]}
building:
  entrances:                    # пусто = автоматически (наружные двери первого этажа)
    - {at: [12.5, 0.2], name: "Главный вход", main: true}
geometry:
  room_label_ignore: ['^Д[А-Я]{0,5}[-\d]']   # тексты, которые не являются названиями помещений
```

Неназванное помещение, в основном занятое лестничным маршем, — «лестничная
клетка». Подпись помещения ставится в центр наибольшей вписанной окружности
вдоль самой длинной хорды.

### Привязка правок к листам

Id этажа (`c3`, `l0`, `b2`) — это порядковый номер при распознавании, и он
меняется при смене ролей слоёв, `cluster_gap` или эвристик. Координаты правок
заданы после выравнивания этажей. Поэтому сервер сохраняет вместе с правками
`_anchor`: лист (layout, handle блока этажа, габарит в координатах листа) и
смещение выравнивания на момент правки. При каждой сборке правки
переназначаются на текущий id и сдвигаются на изменение смещения
(`edits.py`). Если лист не найден или на один лист претендуют две группы
правок, правки не применяются к случайному этажу: они уходят в
`edits_unmatched`, о них предупреждает UI, и при каждой сборке делается новая
попытка их сопоставить. Правки без `_anchor` (написанные руками, старые
задачи) применяются по id и при первой сборке получают якорь. Так же
привязываются `floors.items`.

## Вход, участники, ссылки

Вход — через Keycloak (OpenID Connect, realm `dwg3d`, сервис `keycloak` в
`docker-compose.yml`, консоль администратора — `/auth/admin/`).
Пользователей заводят в Keycloak; в приложении пользователь появляется при
первом входе. API сам ведёт вход (authorization code + PKCE): токены
Keycloak хранятся в базе, в браузере — только случайный токен сессии в
cookie `HttpOnly`. Раз в 5 минут сессия сверяется с Keycloak: выход,
отключение или смена ролей там сразу действуют и здесь.

Глобальные роли — роли realm в Keycloak:

| Роль | Может |
|---|---|
| — (любой вошедший) | создавать проекты; работать в проектах, где он участник |
| `catalog_admin` | + менять каталог оборудования |
| `admin` | + видеть и менять все проекты (как владелец) |

Роли в проекте (`project_members`):

| Роль | Может |
|---|---|
| `viewer` — просмотр | открывать чертежи, модели, планы, слои, отчёты, журнал |
| `editor` — редактор | + загружать и перестраивать чертежи, править 2D, слои, объекты, метки, привязку к карте |
| `owner` — владелец | + участники, ссылки для просмотра, удаление проекта |

Автор проекта становится его владельцем. Участника добавляют по логину или
e-mail; e-mail того, кто ещё не входил, — приглашение: оно срабатывает при
его первом входе. Проект, к которому нет доступа, для пользователя не
существует (`404`); нехватка роли — `403`. В проекте должен остаться хотя бы
один владелец.

**Ссылка для просмотра** (владелец): доступ к проекту без учётной записи —
только чтение, при желании только к части чертежей и слоёв, со сроком
действия; ссылку можно отозвать. Токен показывается один раз, в базе — его
хеш. Открытие ссылки (`#/s/<токен>`) кладёт токен в cookie.

Для разработки без Keycloak: `DWG3D_AUTH=off` (все — администраторы).

## Хранение

Проекты, сборки, этажи и очередь сборок лежат в PostgreSQL, файлы — на диске:

| Таблица | Что хранит |
|---|---|
| `projects` | здание: исходный файл, конфиг правок, привязка к карте (`site`), детальная модель (`detail`), номер текущей сборки |
| `builds` | результат каждой успешной сборки (`result`, JSONB) и конфиг с переякоренными правками |
| `floors` | этаж с постоянным ключом: `anchor` (лист + выравнивание) сопоставляется с каждой новой сборкой, `candidate` — его id в текущей (`c0`, `c3`…), `NULL`, если лист пропал |
| `jobs` | очередь: `queued → running → done/error`; не больше одной активной задачи на проект |
| `placements` | расставленный предмет: этаж (`floor_id`), позиция каталога, координаты плана, поворот, переопределения размера/высоты/обзора камеры, `version` |
| `pins` | метка или комментарий: этаж (`NULL` — для всего здания), координаты glTF, текст, `version` |
| `audit_log` | кто и что поменял: пользователь, объект, действие, состояние до и после |
| `users`, `sessions` | пользователи (логин, имя, роль, хеш пароля scrypt) и открытые сессии |
| `catalog_*` | каталог мебели и оборудования |

При пересборке строки этажа сопоставляются с новыми листами, и его
предметы и метки сдвигаются вместе с ним (изменение выравнивания, отметки
и центра модели) — это не правка пользователя, версия не меняется.
Предметы этажа, лист которого не найден, остаются на месте и видны в
панели «Мебель и оборудование» как «без этажа»; когда лист вернётся, они
встанут на него сами.

Одновременная работа: интерфейс отправляет только изменённые предметы
(`POST …/placements:batch`) с версией, от которой делалась правка. Если
предмет уже поменял или удалил другой человек, запрос отклоняется целиком
(`409`), интерфейс показывает, что именно изменилось, и загружает текущее
состояние. Ctrl+Z работает так же: откатывает свои изменения, а если
предмет с тех пор менял кто-то другой — сообщает об этом.

`data/jobs/<id чертежа>/` по-прежнему содержит исходный чертёж (и его ревизии), `out/` (модель, планы,
экспорт, сконвертированный DXF) и `detail.glb`.

Сборки выполняют потоки в каждом процессе API (`DWG3D_WORKERS`) и, при
желании, отдельные процессы `python -m dwg3d worker -n 2`: задача берётся из
таблицы через `SELECT … FOR UPDATE SKIP LOCKED`, так что одну очередь делят
любые процессы. Работающая сборка раз в 15 с отмечается в базе; если процесс
упал, через 2 минуты задача помечается ошибкой.

## API

Проект — контейнер; в нём чертежи (каждый — загруженный DWG/DXF со своими
сборками, этажами, мебелью и метками).

| | |
|---|---|
| `GET /api/projects` | проекты с их чертежами |
| `POST /api/projects` | `{name, description?}` → новый проект, `201` |
| `GET/PATCH/DELETE /api/projects/{id}` | проект; изменение названия и описания; удаление (скрывается сразу) |
| `POST /api/projects/{id}/drawings` | multipart `file` (+ `name`, `config` JSON) → чертёж, ставится в очередь |
| `GET /api/projects/{id}/audit?limit=100&drawing=` | журнал изменений проекта (или одного чертежа) |
| `GET /api/drawings?project=` | чертежи (переключатель зданий) |
| `GET /api/drawings/{id}` | статус, прогресс, результат (этажи, помещения с типами, входы, метки) |
| `DELETE /api/drawings/{id}` | удаление чертежа |
| `POST /api/drawings/{id}/revision` | multipart `file` — новая ревизия DWG: этажи сопоставляются по листам, правки, мебель и метки остаются на них |
| `GET/PUT /api/drawings/{id}/view` | настройки просмотра без перестроения: название, привязка к карте, выравнивание детальной модели (`GET` — вместе с объектами и метками) |
| `GET /api/layer-kinds` | типы слоёв: какие объекты и категории каталога они принимают |
| `GET/POST /api/projects/{id}/layers` | слои проекта (с числом объектов) / новый слой `{kind, name?}` |
| `POST /api/projects/{id}/layers/{lid}/copy` | вариант слоя: копия со всеми объектами (`{name?}`) |
| `GET /api/projects/{id}/layers/compare?a=&b=` | сравнение двух вариантов: объекты (добавлен / убран / перемещён / изменён) и спецификация |
| `PATCH/DELETE /api/projects/{id}/layers/{lid}` | `{name, visible, locked, sort, props, version?}`; удаление — вместе с объектами (заблокированный — `409`) |
| `GET /api/drawings/{id}/objects?floor=c1&layer=` | объекты слоёв на чертеже (`items`, с `version`, `layer`, `room`) и объекты без этажа (`unplaced`) |
| `POST /api/drawings/{id}/objects` | новый объект `{id?, layer?, floor, item, at, angle, …, build}` → `201`; без `layer` — слой по категории предмета (камеры — «Видеонаблюдение») |
| `PATCH /api/drawings/{id}/objects/{rid}` | `{version, build, …изменённые поля}`; `layer` переносит в другой слой; `null` снимает переопределение |
| `DELETE /api/drawings/{id}/objects/{rid}?version=&build=` | `204`; уже удалённый — тоже `204` |
| `POST /api/drawings/{id}/objects:batch` | `{build, ops: [{op: create/update/delete, id, version, …}]}` — всё или ничего |
| `GET /api/drawings/{id}/rooms` | помещения: `id` сохраняется между сборками и ревизиями |
| `GET /api/projects/{id}/checks` | проверки инженерных слоёв: помещения, где не хватает пожарных извещателей |
| `…/pins`, `…/pins/{rid}`, `…/pins:batch` | то же для меток и комментариев (`kind`: `marker` / `comment`) |
| `POST/DELETE /api/drawings/{id}/detail`, `GET …/detail.glb` | детальная модель (только GLB) |
| `POST /api/drawings/{id}/rebuild` | JSON-переопределение конфига → перестроение |
| `GET /api/drawings/{id}/drawing.dxf` / `.dwg?layers=all\|none\|<id>,<id>` | исходный чертёж с внесёнными правками и объектами слоёв проекта |
| `GET /api/drawings/{id}/files/model.glb` | модель; также `model.ifc`, `model_obj.zip`, `metadata.json`, `plans/*.json`, `debug/*.png` |
| `GET /api/catalog` | каталог мебели и оборудования: `{categories, items}` (снятые — с `active: false`) |
| `POST /api/catalog/items`, `PATCH /api/catalog/items/{id}` | новая позиция / изменение полей (`null` очищает необязательное) — `catalog_admin` |
| `POST /api/catalog/items/{id}/model` | загрузка GLB (до `DWG3D_MAX_CATALOG_GLB_MB`, 50 МБ); отдаётся по `GET /api/catalog/models/{file}` |
| `POST /api/catalog/categories`, `PATCH /api/catalog/categories/{id}` | категории: `{id, name, color}` |
| `GET /api/reports/equipment?project=&layer=&by=floor\|room&format=json\|xlsx` | спецификация проекта (по этажам всех его чертежей или `by=room` — по помещениям), одного слоя, или сводная по всем проектам |
| `POST /api/auth/login` | `{login, password}` → пользователь, cookie сессии; `401` — неверно, `429` — слишком много попыток |
| `POST /api/auth/logout`, `GET /api/auth/me` | выход; текущий пользователь (`401` — нужно войти) |

Ответ `409` на построчные запросы: `{detail, conflicts: [{id, current}]}` —
`current` — строка на сервере (`null`, если удалена); без `conflicts` — модель
перестроена после сборки `build`, нужно перезагрузить данные. Этажи
передаются id текущей сборки (`c0`, `c3`…); неизвестный этаж или предмет
каталога — `400`.

Конфиг из запросов проверяется по структуре `default_config.yaml`: неизвестные
ключи, неверные типы и значения вне допустимых диапазонов дают `400`.

### Эксплуатация

| Переменная | По умолчанию | |
|---|---|---|
| `DWG3D_DATA` | `<проект>/data` | каталог задач |
| `DWG3D_DATABASE_URL` | `postgresql+psycopg://dwg3d:dwg3d@127.0.0.1:5432/dwg3d` | PostgreSQL (сервис `db` из `docker-compose.yml`); без базы сервер не стартует |
| `DWG3D_AUTH` | oidc | вход через Keycloak; `off` — без входа |
| `DWG3D_OIDC_ISSUER` | — | issuer realm, как его видит браузер: `https://…/auth/realms/dwg3d` |
| `DWG3D_OIDC_INTERNAL` | = issuer | тот же realm по внутреннему адресу (`http://keycloak:8080/auth/realms/dwg3d`) |
| `DWG3D_OIDC_CLIENT_ID`, `DWG3D_OIDC_CLIENT_SECRET` | dwg3d, — | клиент в realm |
| `DWG3D_PUBLIC_URL` | из запроса | адрес сайта для возврата из Keycloak |
| `DWG3D_SECRET` | случайный | ключ подписи состояния входа (задайте, если процессов API несколько) |
| `DWG3D_SESSION_DAYS` | 14 | сессия истекает через N дней без запросов |
| `DWG3D_TEST_DATABASE_URL` | как выше | сервер для тестов: они создают и удаляют временную базу `dwg3d_test_*`; если сервер недоступен, тесты с БД пропускаются |
| `DWG3D_MAX_UPLOAD_MB` | 200 | лимит загрузки |
| `DWG3D_WORKERS` | 2 | потоков сборки в каждом процессе API (0 — только отдельные `dwg3d worker`) |
| `DWG3D_CORS_ORIGINS` | — | разрешённые чужие origin через запятую; собранный UI и прокси Vite работают с того же origin и CORS не требуют |
| `DWG3D_RETENTION_DAYS` | 0 | удалять проекты (строки и папку), не менявшиеся N дней (0 — хранить всегда) |
| `DWG3D_CONVERTER_MEM_MB` | 4096 | лимит памяти для LibreDWG (плюс лимит CPU-времени для всех конвертеров) |

Ограничения, о которых нужно помнить:

- **Вход обязателен** (`DWG3D_AUTH=oidc` по умолчанию): без него API отдаёт
  только `/api/health`. Сессия хранится в базе, в браузере — случайный токен
  в cookie `HttpOnly; SameSite=Lax` (с `Secure`, если запрос пришёл по HTTPS,
  в том числе через прокси с `X-Forwarded-Proto`). Публикуйте сервер только
  по HTTPS. `DWG3D_AUTH=off` отключает вход (все — администраторы) —
  только для сервера во внутренней сети или локальной разработки.
- Подбор паролей, блокировки, политика паролей — забота Keycloak
  (в realm включена защита от перебора).
- Всё состояние — в PostgreSQL и `DWG3D_DATA`: процессов uvicorn может быть
  несколько (и на разных машинах, если папка данных общая). Сборка,
  прерванная падением процесса, помечается ошибкой через 2 минуты.
- DWG разбирается внешним конвертером. Лимиты rlimit снижают, но не
  устраняют риск от вредоносных файлов; для публичного сервиса нужна изоляция
  (контейнер или отдельный пользователь без доступа к данным).
- Стектрейсы пишутся в лог и в `jobs.trace`, но клиенту не отдаются.
- Схема базы меняется только миграциями Alembic (`backend/dwg3d/migrations`);
  новая миграция: `cd backend && uv run alembic revision --autogenerate -m "..."`.
  Резервная копия — `pg_dump` плюс папка `data/`.
