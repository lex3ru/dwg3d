# access

Доступ: кто что может в каком здании, на этаже, в помещении, над объектом.

Права выдаются **человеку из справочника** (`person_id`), а не учётной записи: связь
«учётная запись ↔ человек» сервис узнаёт из событий `people`. Учётная запись, которой
нет в справочнике, не имеет никаких прав. Администратор системы (роль Keycloak
`twin.admin`) может всё; другой сервис со своим токеном читает всё и ничего не меняет.

Назначение: `{person_id, role, scope: {kind, id}, building_id, origin}`.

| Роль | Что даёт в области |
|---|---|
| `viewer` | видеть объекты и людей |
| `responsible` | то же + править разрешённые свойства, состояние, перемещать переносное |
| `admin` | всё; на области «здание» — администратор здания |

Любое назначение внутри здания открывает план здания (`plan`). Иерархию «помещение →
этаж → здание» сервис не хранит: спрашивающий присылает цепочку областей (`chain`).

## Как сервисы проверяют права

Сервис один раз спрашивает области того, кто обратился (`GET /me/scopes` с его токеном),
помнит ответ 20 секунд и решает сам — правило одно на всех, `twin_chassis.access.decide`.
Поэтому выданное и отозванное право действует везде не позже чем через 30 секунд. Если
`access` недоступен, чтение идёт по последним известным областям до 5 минут, изменения
отклоняются с понятным сообщением.

## Запросы

`/api/access/v1` — `contracts/openapi/access.v1.json`.

| Запрос | Что делает | Кому |
|---|---|---|
| `GET /me/scopes` | назначения спрашивающего и здания, план которых ему виден | всем |
| `GET /scopes?person_id=` | то же для человека | сервисам |
| `POST /check` | можно ли выполнить действия над областями | всем |
| `GET /grants?building_id=` | назначения в здании | администратору здания |
| `POST /grants`, `DELETE /grants/{id}` | выдать, отозвать | администратору здания |
| `POST /reconcile` | сверить автоматические назначения с их источниками (см. ниже) | администратору системы, сервисам |

Администратор здания выдаёт права только в своём здании; чужое для него не существует (404).

## События

| Публикует | Когда |
|---|---|
| `access.grant.created` / `.revoked` | право выдано / отозвано |

| Получает | Реакция |
|---|---|
| `people.person.linked` / `.unlinked` | запомнить / забыть, чья учётная запись |
| `people.person.left` | отозвать все права человека |
| `people.person.assigned` / `.unassigned` | `viewer` на помещение (`origin: assignment`) выдать / отозвать |
| `assets.asset.responsible_changed` | `responsible` на объект (`origin: responsible`) новому, отозвать у прежнего |
| `assets.asset.retired`, `buildings.room.retired`, `buildings.building.deleted` | отозвать назначения на объект, помещение, здание |
| `assets.asset.moved` в другое здание | перенести назначения на объект в то здание |

Автоматическое назначение и выданное вручную на ту же область — разные записи: уход одного
не трогает другое.

## Сверка

Событие может потеряться или быть обработано не так: раз в `TWIN_RECONCILE_S` секунд (по умолчанию
600) и на старте сервис спрашивает у `people` все привязки и у `assets` всех ответственных (со своей
учётной записью `twin-svc-access`) и приводит автоматические назначения к ним — недостающие выдаёт,
лишние отзывает, с событиями. Это единственное, зачем `access` обращается к другим сервисам;
права при их недоступности не страдают — сверка просто откладывается.

## Запуск и тесты

```bash
docker compose -f deploy/docker-compose.yml up -d db db-init nats
cd services/access
uv run python -m twin_chassis.migrate && uv run uvicorn app.main:build --factory --port 8000
uv run ruff check . && uv run pytest
```

В тестах сервис `people` заменяют его события.
