# Взять задачу

ID задачи (вида `ABC-123`) бери из сообщения пользователя, иначе из имени текущей ветки. Нет ID — спроси.
Основную ветку бери из `AGENTS.md` (обычно `main`).

## 1. Найди задачу

- Если подключён MCP-сервер Plane — прочитай задачу: название, описание, комментарии, статус, исполнитель.
- Если у задачи есть родительская (поле `parent`), прочитай и её: там общий контекст, требования ко всем подзадачам и что вне рамок.
- Если MCP нет — попроси пользователя вставить описание задачи (и родительской, если есть) или ссылку на неё.
- Найди файл задачи `docs/tasks/<ID>-*.md`: сначала в текущей ветке, затем после `git fetch` — в удалённых ветках (`git branch -r --list "*<ID>*"`).

## 2а. Задача уже начата (файл задачи есть)

1. Выполни `git fetch` и переключись на ветку из шапки файла задачи: `git switch <branch>`. Если в рабочей копии есть незакоммиченные изменения — остановись и спроси пользователя.
2. Прочитай файл задачи целиком. Главное — блоки «Handoff», «Решения и находки» и «План».
3. Посмотри, что уже сделано: `git log --oneline origin/main..HEAD` и `git diff --stat origin/main...HEAD`.
4. Если доступен `glab` — прочитай обсуждение MR: `glab mr view <branch> --comments`.
5. Если в коммитах есть трейлер `Entire-Checkpoint` и установлен Entire, сессию можно посмотреть: `entire checkpoint explain <id>`. Открывай транскрипт, только если handoff непонятен.
6. Выполни команды из «Как проверить» в handoff и убедись, что состояние совпадает с описанием.
7. Расскажи пользователю: что сделано, что дальше, какие открытые вопросы и где handoff расходится с реальностью. Дождись подтверждения следующего шага.
8. Обнови шапку файла задачи: `owner` — текущий человек (`git config user.name`), `updated` — сегодняшняя дата.

## 2б. Новая задача (файла нет)

1. Создай ветку от свежей основной: `git fetch` и `git switch -c <ID>-<kratko-latinicey> origin/main`.
2. Создай `docs/tasks/<ID>-<kratko>.md` из `docs/tasks/_template.md`. Заполни шапку, «Цель» и «Критерии готовности» по задаче из Plane. Чего нет в задаче — спроси, не выдумывай.
3. Изучи код, который затронет задача. Составь «План» из 3–10 проверяемых шагов.
4. Покажи план пользователю. Если задача дольше часа, не пиши код, пока план не подтверждён.
5. Закоммить файл задачи с сообщением `docs(<ID>): план задачи` и запушь ветку.
6. Если доступен `glab` — создай черновой MR: `glab mr create --draft --title "<ID>: <название>" --description "Задача: <ссылка на Plane>. План и журнал: docs/tasks/<файл>"`. Ссылку на MR впиши в шапку файла задачи (`mr:`).
7. Если подключён Plane MCP — переведи задачу в работу и оставь комментарий со ссылками на ветку, MR и файл задачи.

## 3. В любом случае

- Добавь запись в «Журнал сессий» (новые сверху): дата · кто · агент / модель · «начало сессии».
- По ходу работы отмечай пункты плана и сразу записывай решения в «Решения и находки», а не в конце.
- В конце сессии используй навык `handoff`.
